# 球员库 5 万张卡查询验证

日期：2026-10-23。环境：本机隔离 MySQL `127.0.0.1:3307/efootball_catalog_verify`；50,000 张卡、每张 2 个发布版本，共 100,000 条版本记录、500 个球员包。基准脚本每项测 12 次，列出 p50/p95；数据按精确 ID 自动删除并复查。以下数值只代表本机，不代表生产环境。

| 查询 | 查询下推初版、未加索引 p50 / p95 | 当前版 p50 / p95 |
| --- | ---: | ---: |
| 列表首页 | 121.5 / 138.1 ms | 2.2 / 4.5 ms |
| 下一页 | 121.0 / 132.0 ms | 1.6 / 1.9 ms |
| 深页（约 80% 处） | 未测 | 1.4 / 2.7 ms |
| 筛选 | 80.5 / 98.1 ms | 1.7 / 2.3 ms |
| 包含搜索 | 51.4 / 52.8 ms | 50.9 / 165.8 ms |
| 卡片详情 | 26.3 / 31.5 ms | 4.8 / 9.4 ms |
| 球员包列表 | 409.3 / 1533.7 ms | 546.6 / 3459.1 ms |

`EXPLAIN`：查询下推初版对 100,000 条版本全表扫描并 `Using filesort`；当前列表使用 `player_card_versions_catalog_order_idx`，预计约 50,000 条符合状态的索引记录，但首页可以按索引顺序提前结束，`Extra` 不再出现 `Using filesort`。较深页通过游标限定范围。`NOT EXISTS` 使用已有的 `(player_card_id, release_sequence)` 唯一索引。

新 SQL 每次最多取 `limit + 1` 个版本 ID，再只读取这些版本行；不会把全库版本搬进 Node.js。球员/包详情按 ID 限定，包列表只向 Node.js 返回 `limit + 1` 包。日期降序在 MySQL 中自然把 `NULL` 放末尾，因此排序可直接使用顺序索引。

搜索仍是五个独立规范化字段的**包含**匹配（`%关键词%`），普通 B 树索引无法消除扫描。球员包列表需要对当前快照的有效卡分组并计数，5 万张数据下的尾部耗时较高；这两项在目标环境验收时应单独观察。尝试按球员包逐个做关联子查询的方案出现严重尾延迟，已撤回。若生产目标不接受当前搜索或包列表耗时，应另行设计倒排搜索索引及发布时维护的球员包摘要，不能靠缩小结果或改变匹配语义掩盖。

## 安全与发布顺序

1. 目标环境先运行只读 `pnpm db:status`，确认目标主机和库名。
2. 先应用 `20261023090000_player_card_version_search_fields`、`20261023110000_player_card_version_read_indexes`，再以目标 `DATABASE_URL` 运行 `pnpm --filter @efm/api player-catalog:backfill --dry-run`，核对数量后实际回填，确认 `normalized_card_name IS NULL` 为 0。
3. 回填完成后部署新 API。小程序及后台无界面代码改动。
4. 只读核对目标 API 的首页、下一页、筛选、卡详情和包列表；核对后台现役/已退出球队、球队详情及小程序“我的联赛”。

已对现有共享 CloudBase 连接执行只读 `pnpm db:status`：上述两项迁移均未应用。本次未对目标环境写入、迁移或部署；目标接口与前端的线上验收尚未完成。
