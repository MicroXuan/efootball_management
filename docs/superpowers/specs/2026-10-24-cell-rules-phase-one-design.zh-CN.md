# CELL 规则第一阶段设计

## 目标与边界

落地两条会直接改变球队资产或比赛资格的规则：明报成交后所有权立即转移、当季参赛阵容保持原队至下赛季；提名球员无人竞价时，以底价归最早有效提名者。提名上限使用现有 `NominationWindow.perTeamLimit` 配置，摘牌入队上限为 25 人。付款、群发帖、证据审核和手动录分维持线下流程。

## 现状

`LeaguePlayerOwnership.leagueTeamId` 同时供资产、工资、阵容查询使用。强报审核立即更新该字段，无法单独表示当季比赛资格。拍卖无人出价进入 `NO_BID`，现有审核无法将其转成提名者底价入队。撤回后重新提名会复用原记录的 `createdAt`，可能错误保留最早提名顺位。

## 方案

1. 为每赛季建立只读的比赛阵容资格快照，记录赛季、球队、球员和生效球员卡。开赛时从当时现役归属生成；明报及当季下放不修改本赛季快照。下一赛季建立快照时按新所有权生成。资产、工资和身价继续按实时所有权查询；本赛季获批准参赛者通过只读接口查询比赛资格快照。对迁移前已开赛而没有快照的赛季，先回填或在切换入口中拒绝使用快照，不静默混用实时所有权。
2. 提名记录增加有效提交时间。首次提交和撤回后的再次提交均重置这一时间；候选名单和无人竞价归属按有效提交时间、记录 ID 排序。保留原始创建时间以供审计。
3. 提名来源拍卖无人竞价时，审核页给出“底价归提名者”预览；审核确认时重新读取最早有效提名、未签约状态、球队人数和工资帽，使用现有入队事务。底价固定 10，起拍价和加价仍由拍卖批次配置；不属于提名拍卖的无人竞价保持流拍。
4. 当前系统在首次发布联赛组别赛程时将赛季由 `READY` 置为 `IN_PROGRESS`，因此在该事务里原子生成快照。重复请求不可重复写入；赛季取消或回退不自动篡改历史资格。

## 取舍

选择独立快照表，避免改写实时所有权的含义。另一种做法是在所有权上增加“当季参赛球队”字段，但历史赛季查询和多次转会会丢失原状态。快照增加一张表和受控迁移，换来明确的跨赛季可追溯性。

## 验收

- 明报后买方立即看到资产和标价权，原队仍在当季比赛阵容中；下赛季快照切换到买方。
- 当季下放不删除本赛季比赛资格；退役、消失等特殊状态仍依原有审核流程处理。
- 两队提名同一球员时最早有效提交者获无人竞价归属；撤回重提不沿用旧顺位。
- 有人竞价、普通流拍、重复审核、并发入队、25 人及工资帽边界均保持正确。
- 后台现役/已退出球队列表、球队详情、小程序“我的联赛”回归通过。

## 数据安全

所有 API 单元与端到端测试显式指定本机隔离 `DATABASE_URL`，库名含 `test` 或 `verify`。目标环境先核对迁移状态，再按受控流程部署迁移和新代码。
