# 联赛球队与赛事管理后台设计

**日期：** 2026-09-27  
**状态：** 待最终评审  
**范围：** 联赛级球队、球队阵容、后台账号、DT 工资、工资帽、转会窗口与财务流水

## 1. 背景与目标

现有系统把 `TeamProfile` 设计成用户唯一的全局长期球队。这与最新业务规则不符：球队应当归属于联赛，而不是直接跨联赛复用。

本设计的目标是：

- 一个微信用户在每个联赛内最多拥有一支球队；
- 同一支联赛球队可以连续参加该联赛的多个赛季；
- 用户加入新联赛时，需要在新联赛重新建立球队；
- 赛事管理员通过独立 Web 后台创建联赛、添加用户、建立球队和维护阵容；
- 小程序首版仅负责登录、身份展示以及联赛球队数据查询；
- 同一名真实球员在同一联赛内只能归属于一支球队；
- 每队最多 25 名球员，并受联赛工资帽约束；
- 球员购买、出售、转会和卡片升级均可审计、可追溯；
- 为后续资产、身价、财务、比赛阵容和更多后台角色保留扩展边界。

## 2. 产品边界

### 2.1 本期包含

- 平台管理员和联赛管理员账号密码登录；
- 平台管理员创建联赛、后台账号和联赛授权；
- 小程序用户公开数字编号；
- 管理员按编号将用户添加到联赛；
- 联赛球队创建、资料维护和固定球队编号；
- 全量球员卡保存、真实球员归并、自动加点结果和最优卡计算；
- 联赛内真实球员唯一归属；
- 球员买入、出售/释放、球队间转会和卡片升级；
- 每队 25 人上限；
- 联赛工资帽和可配置的 DT 工资档次；
- 赛季级多转会窗口和操作类型开关；
- 购买、出售、升级等金额流水；
- 审计日志、并发保护和历史快照；
- 小程序只读查看我的联赛球队、阵容、工资和流水。

### 2.2 本期不包含

- 小程序内发起购买、出售、转会或升级申请；
- 在线支付；
- 球队资金余额与可用资金校验；
- 身价对购买或工资帽的约束；
- 后台微信扫码登录；
- 用户自助创建联赛球队；
- 新卡发布后自动升级已持有卡片；
- 赛事实况截图 OCR。

购买行为在系统外完成，赛事管理员只在后台登记结果和金额。第一版财务模块记录流水，但不计算或限制可用余额。

## 3. 已确认业务规则

### 3.1 用户与联赛球队

- `User` 表示微信登录用户。
- 用户首次登录后获得容易记忆的六位纯数字公开编号，例如 `100069`。
- 公开编号仅用于管理员查找，不是登录凭证，也不能替代内部 UUID。
- 同一用户在同一联赛最多拥有一支 `LeagueTeam`。
- 用户加入不同联赛时，需要分别创建不同的 `LeagueTeam`。
- 联赛球队资料、阵容、工资和财务流水在不同联赛间完全隔离。

### 3.2 球队编号

- 球队编号由联赛管理员分配。
- 同一联赛内球队编号唯一。
- 球队编号在该联赛的所有赛季中保持不变，除非管理员主动调整。
- 历史赛季保存当时的球队编号快照，后续修改不影响历史记录。
- 球队编号、队名、用户编号和昵称分别存储，展示层可组合为 `24 · 巴西红牛` 和 `添（100069）`。

### 3.3 真实球员与球员卡

- `CanonicalPlayer` 表示真实球员，例如 Leonardo Bonucci。
- `PlayerCard` 表示该真实球员的某个具体卡片版本。
- 所有卡片版本均保存，不在采集阶段删除非最强卡。
- 每张卡执行自动加点，并保存加点明细、最大总评和算法版本。
- 系统比较同一真实球员的所有卡片，将自动加点后最大总评最高的卡标记为推荐最优卡。
- 后台以真实球员为搜索单位，默认选择推荐最优卡，同时允许查看全部卡片版本。
- 同一名真实球员在同一联赛只能归属于一支球队，无论其拥有多少张卡。
- 不同联赛可以分别拥有同一名真实球员。

核心数据库约束为：

```text
UNIQUE (league_id, canonical_player_id)
```

不能只对 `player_card_id` 做唯一约束，否则同一真实球员的不同卡片可能被分配给多支球队。

### 3.4 新卡与卡片升级

- 新卡同步后，系统可以重新计算该真实球员的推荐最优卡。
- 推荐最优卡变化不会自动替换球队已持有卡片。
- 已有球队继续持有原卡，原工资也不自动变化。
- 赛事管理员只能通过明确的“卡片升级”操作替换具体卡片。
- 卡片升级必须位于允许升级的转会窗口内，并重新校验工资帽。
- 升级记录必须保存旧卡、新卡、旧工资、新工资、金额、管理员、时间和原因。

### 3.5 阵容规模

- 每支联赛球队最多拥有 25 名有效球员。
- 买入和球队间转会必须检查接收球队的人数。
- 卖出或释放后球员解除联赛归属，可被同联赛其他球队再次购买。
- 球员卡升级不改变阵容人数和真实球员归属。

### 3.6 工资与工资帽

- 每个联赛设置一个统一工资帽，适用于该联赛全部球队。
- 球员工资根据具体卡片的 DT 能力值和联赛当前工资档次计算。
- 每个联赛可以修改自己的工资档次金额。
- 联赛初始化时使用以下默认档次：

| DT 能力值 | 默认工资 |
|---:|---:|
| 92 及以下 | 100 |
| 93 | 200 |
| 94 | 300 |
| 95 | 400 |
| 96 | 500 |
| 97 | 600 |
| 98 | 700 |
| 99 | 800 |
| 100 及以上 | 900 |

- 工资档次不允许区间缺失或重叠。
- 买入、球队间转会和卡片升级必须检查操作后工资总额不超过工资帽。
- 球员加入时保存 DT 值、工资档次版本和工资结果快照。
- 修改工资档次默认只影响之后的操作，不自动改变现有阵容工资。
- 管理员可以明确执行“按新规则重新核算现有阵容”，该操作需要二次确认和完整审计。
- 降低工资帽或重新核算后，已有球队可以进入 `OVER_CAP` 状态，但系统不自动删除球员。
- 超帽球队不能执行增加工资的操作，只能出售、释放或执行降低工资的卡片调整。

### 3.7 财务流水

- 第一版不设置必须存在的初始资金，也不校验余额。
- 用户在系统外完成购买，管理员在后台登记购买金额。
- 买入生成支出流水，出售生成收入流水，卡片升级可生成升级支出流水。
- 管理员人工调整必须填写原因并生成流水，不能直接覆盖历史金额。
- 流水与阵容变化在同一数据库事务中完成，不能出现只写入其中一部分的情况。

### 3.8 转会窗口

- 转会窗口属于具体赛季。
- 每个赛季可以配置多个窗口。
- 每个窗口保存名称、开始时间、结束时间、状态和创建者。
- 每个窗口分别配置是否允许：买入、卖出/释放、球队间转会、卡片升级。
- API 使用服务器时间强制判断窗口有效性，不能只依赖后台按钮隐藏。
- 赛事管理员只能在有效窗口内执行已允许的操作。
- 平台管理员的紧急修正必须填写原因并记录审计日志。

## 4. 角色与权限

### 4.1 小程序用户

- 使用微信登录；
- 查看和复制自己的公开数字编号；
- 查看自己加入的联赛；
- 查看各联赛球队、当前阵容、工资使用、工资帽、财务流水和转会窗口；
- 第一版没有阵容写权限。

### 4.2 平台管理员

- 使用独立后台账号密码登录；
- 创建、编辑、停用联赛；
- 创建、启用、停用后台管理员账号；
- 重置管理员密码；
- 给管理员分配一个或多个联赛；
- 查看全平台审计日志；
- 必要时执行有理由记录的紧急修正。

### 4.3 联赛管理员

- 仅能访问被授权的联赛；
- 按数字编号查找小程序用户；
- 把用户加入联赛并建立球队；
- 分配和修改球队编号、队名、简称和队徽；
- 管理赛季、工资帽、工资档次和转会窗口；
- 登记买入、出售、释放、球队间转会和卡片升级；
- 查看当前联赛的财务流水和审计日志。

第一版启用 `PLATFORM_ADMIN` 和 `LEAGUE_MANAGER` 两种后台角色，但使用可扩展的角色绑定模型，为财务、数据录入和只读角色预留空间。

## 5. 系统架构

### 5.1 客户端

新增 `apps/admin-web`：

- React；
- TypeScript；
- Vite；
- Ant Design；
- 复用 `packages/contracts`；
- 使用现有 NestJS API；
- 构建为静态资源，后续可部署至 CloudBase 静态托管。

保留 `apps/miniprogram`，但将球队维护入口收缩为只读查询。小程序不承载复杂后台操作。

### 5.2 后端

在现有 NestJS API 中增加或重构以下边界：

- `admin-auth`：后台账号登录、会话、密码修改和登录限制；
- `admin-accounts`：平台管理员维护后台账号和联赛授权；
- `league-teams`：联赛用户、球队资料和球队编号；
- `player-identities`：真实球员与卡片归并；
- `player-builds`：自动加点结果和推荐最优卡；
- `league-rosters`：球员归属、阵容和工资聚合；
- `salary-rules`：工资帽和 DT 工资规则版本；
- `transfer-windows`：赛季窗口和操作类型；
- `roster-transactions`：买入、出售、转会、升级与修正；
- `finance-ledger`：金额流水；
- `audit-log`：安全与业务审计。

所有写操作必须从认证身份计算权限范围，不能接受客户端传入的管理员权限声明。

## 6. 数据模型

### 6.1 User 调整

新增：

```text
publicUserNo String @unique
```

公开编号由独立序列或安全的编号分配器生成，显示为六位数字。内部主键继续使用 UUID。

### 6.2 AdminAccount

```text
id
username unique
displayName
passwordHash
status
failedLoginCount
lockedUntil
lastLoginAt
createdAt
updatedAt
```

密码使用 Argon2id 或 bcrypt 哈希保存，不保存明文。后台会话可撤销，并使用短期访问令牌。

### 6.3 AdminLeagueRole

```text
adminId
leagueId
role
grantedById
createdAt
revokedAt
```

一个管理员可绑定多个联赛。

### 6.4 LeagueTeam

```text
id
leagueId
ownerUserId
teamNumber
name
shortName
logoUrl
status
rosterStatus
version
createdAt
updatedAt
```

约束：

```text
UNIQUE (league_id, owner_user_id)
UNIQUE (league_id, team_number)
```

### 6.5 CanonicalPlayer 与 PlayerCard

`CanonicalPlayer` 保存真实球员身份和外部身份映射；`PlayerCard` 保存具体卡片版本及其 `canonicalPlayerId`。

归并应优先使用稳定的上游球员身份标识。无法可靠自动归并时进入人工待处理队列，不能只依赖显示名称强行合并。

### 6.6 PlayerCardAutoBuild

```text
playerCardId
algorithmVersion
allocationJson
maxOverall
dtRating
calculatedAt
```

同一卡片允许保留不同算法版本的结果。当前推荐结果由明确版本指针选择。

### 6.7 CanonicalPlayerBestCard

```text
canonicalPlayerId
playerCardId
autoBuildId
selectedAt
selectionReason
```

若多张卡最大总评相同，第一版依次比较 DT 能力值、卡片发布日期和外部卡片 ID：DT 能力值高者优先、发布日期新者优先，仍相同时选择外部卡片 ID 字典序较小者。系统把完整比较依据写入 `selectionReason`，不能依赖无序数据库结果。

### 6.8 LeaguePlayerOwnership

```text
id
leagueId
leagueTeamId
canonicalPlayerId
currentPlayerCardId
dtRatingSnapshot
salaryRuleVersionId
salaryAmount
acquiredAt
status
version
```

约束：

```text
UNIQUE (league_id, canonical_player_id)
```

### 6.9 LeagueSalaryRuleVersion

规则版本包含联赛工资帽、DT 档次集合、生效时间、创建者和状态。历史阵容引用具体版本。

### 6.10 TransferWindow

```text
id
seasonId
name
startsAt
endsAt
allowBuy
allowSell
allowTransfer
allowCardUpgrade
createdByAdminId
version
```

同一赛季允许多个窗口，但重叠窗口的操作权限取并集还是拒绝重叠，应采用简单、可预测的规则：第一版禁止时间重叠。

### 6.11 RosterTransaction

保存操作类型、真实球员、来源球队、目标球队、旧卡、新卡、旧工资、新工资、金额、原因、管理员和时间。交易一旦完成不可修改，只能用反向修正交易纠错。

### 6.12 FinanceLedgerEntry

保存球队、交易引用、方向、金额、类型、备注和时间。第一版不提供余额字段作为业务约束。

### 6.13 SeasonEntry 调整

`SeasonEntry` 改为引用 `LeagueTeam`，并继续保存球队编号、队名、队徽和用户资料快照。历史展示只读取快照，不回读可变的当前球队资料。

## 7. 后台页面架构

### 7.1 登录页

- 用户名和密码；
- 登录失败提示和限流；
- 停用、锁定状态提示；
- 第一版不提供自助注册和找回密码。

### 7.2 平台管理区

- 平台概览；
- 联赛管理；
- 管理员账号；
- 联赛权限分配；
- 全平台审计日志。

### 7.3 联赛管理工作台

管理员先选择已授权联赛，之后所有页面固定在当前联赛范围：

```text
联赛概览
用户与球队
球队阵容
球员库
赛季管理
转会窗口
工资规则
财务流水
操作日志
```

### 7.4 球队详情

顶部展示球队编号、队名、用户编号、阵容人数、当前工资和工资帽。下方提供当前阵容、买入、出售/释放、球队间转会、卡片升级、财务流水、操作历史和参赛赛季。

## 8. 关键业务流程

### 8.1 用户入联赛

```text
用户微信登录
→ 生成公开数字编号
→ 管理员按编号搜索
→ 添加到当前联赛
→ 分配球队编号和资料
→ 创建 LeagueTeam
→ 小程序显示该球队
```

### 8.2 球员买入

```text
选择球队
→ 搜索真实球员
→ 默认选择推荐最优卡
→ 填写购买金额和备注
→ 检查转会窗口
→ 检查联赛唯一归属
→ 检查 25 人上限
→ 按 DT 工资档次计算工资
→ 检查工资帽
→ 写入归属、交易、流水和审计日志
```

上述写入在同一数据库事务中完成。

### 8.3 球队间转会

球队间转会是一笔原子操作，不允许先删除再单独新增。事务同时更新球员归属、双方阵容记录、双方金额流水和审计日志。

### 8.4 卡片升级

真实球员归属保持不变，只替换具体卡片。系统重新读取 DT 能力值、计算工资并检查工资帽；历史卡片和工资不被覆盖。

### 8.5 工资规则变更

保存前提供影响预览。默认仅对新交易生效；重新核算现有阵容必须作为独立批量操作执行，并生成规则版本、调整记录和审计日志。

## 9. 并发、错误与安全

### 9.1 并发保护

- 球员买入和球队间转会必须依赖数据库唯一约束和事务锁；
- 同一真实球员的两个并发买入请求只能有一个成功；
- 球队人数和工资帽检查必须与写入处于同一事务；
- 所有后台写操作使用幂等键，避免重复点击产生重复交易；
- 可变资源使用版本号进行乐观并发控制。

### 9.2 业务错误

至少提供：

- `LEAGUE_PLAYER_ALREADY_OWNED`
- `TEAM_ROSTER_FULL`
- `TEAM_SALARY_CAP_EXCEEDED`
- `TRANSFER_WINDOW_CLOSED`
- `TRANSFER_OPERATION_NOT_ALLOWED`
- `PLAYER_DT_RATING_MISSING`
- `SALARY_TIER_NOT_CONFIGURED`
- `TEAM_NUMBER_ALREADY_EXISTS`
- `ADMIN_LEAGUE_ACCESS_DENIED`

错误响应应包含当前值和限制值，便于管理员修正。

### 9.3 安全

- 后台密码安全哈希；
- 登录限流和临时锁定；
- 管理员会话可撤销；
- 联赛权限在 API 层强制验证；
- 不向后台展示微信 `openid`；
- 用户编号查询限流并最小化返回信息；
- 财务和阵容历史不可直接删除；
- 敏感配置只保存在环境变量或部署密钥中。

## 10. 现有数据迁移

现有 `User.ownerTeamProfile` 与 `TeamProfile.ownerUserId @unique` 不符合新模型，采用新增、回填、切换、保留的迁移方式：

1. 新增联赛球队、管理员、工资、窗口、阵容、交易、流水和审计表；
2. 根据 `SeasonEntry → LeagueSeason → League` 为每个“用户＋联赛”生成 `LeagueTeam`；
3. 从原 `TeamProfile` 复制队名、简称和队徽；
4. 对无法推断的球队编号标记为待管理员分配，迁移阶段允许临时为空；
5. 给 `SeasonEntry` 增加 `leagueTeamId` 并回填；
6. 校验历史参赛记录、快照和引用完整；
7. API 和小程序切换到 `LeagueTeam`；
8. 停止旧 `TeamProfile` 写入；
9. 旧表至少保留一个版本周期，不做破坏性删除。

若当前环境只有可重建的本地演示数据，可以重新生成演示数据，但正式迁移脚本仍需支持非破坏性回填。

## 11. 测试与验收

### 11.1 API 与数据库

- 同一用户可以在不同联赛分别拥有球队；
- 同一用户不能在同一联赛拥有两支球队；
- 同一联赛球队编号不可重复；
- 同一真实球员不能被同联赛两支球队持有；
- 不同联赛可分别持有同一球员；
- 并发买入只有一个请求成功；
- 第 26 名球员被拒绝；
- 超工资帽操作被拒绝；
- 窗口外或未授权类型操作被拒绝；
- 卡片升级不改变真实球员归属；
- 工资规则变化不会静默改变旧工资；
- 转会、阵容、流水和审计日志原子提交或整体回滚；
- 联赛管理员不能访问未授权联赛；
- 历史赛季与比赛快照不受当前阵容变化影响。

### 11.2 后台

- 平台管理员可以创建联赛、账号和授权；
- 联赛管理员只能看到被授权联赛；
- 用户编号搜索和球队创建流程完整；
- 球员搜索以真实球员为单位，默认展示最优卡；
- 工资、人数和窗口限制在表单提交前提示，API 拒绝结果也能正确展示；
- 重复提交不会产生重复交易。

### 11.3 小程序

- 用户能查看和复制数字编号；
- 用户能查看不同联赛下的独立球队；
- 阵容、工资、工资帽、流水和窗口状态正确；
- 小程序不出现后台写操作入口。

## 12. 推荐实施顺序

1. 新契约和新增数据库模型；
2. 后台认证、管理员账号和联赛授权；
3. `LeagueTeam` 迁移与用户编号；
4. 真实球员归并、自动加点结果和推荐最优卡；
5. 工资规则、工资帽和球队阵容；
6. 转会窗口、交易事务、财务流水和审计日志；
7. Web 管理后台；
8. 小程序只读页面调整；
9. 数据回填、端到端验收和部署文档。

## 13. 完成标准

本阶段在满足以下条件时完成：

- 平台管理员能创建联赛、赛事管理员并分配联赛权限；
- 联赛管理员能按数字编号建立联赛球队；
- 同一球队可参加同联赛多个赛季，新联赛使用独立球队；
- 管理员能在允许的窗口内完成买入、出售、转会和升级；
- 系统可靠执行真实球员唯一性、25 人上限和工资帽约束；
- DT 工资档次可按联赛配置并保留版本；
- 金额流水和审计日志可追溯；
- 小程序能只读展示用户的联赛球队和阵容；
- 旧历史数据完成非破坏性迁移；
- lint、类型检查、单元测试、端到端测试和构建全部通过。
