# PESDATA 自动同步设计

## 1. 目标

在已获得 PESDATA 站方授权、但没有正式 API 文档和密钥的前提下，通过 PESDATA 网站当前使用的内部 JSON 接口自动获取球员卡列表与详情，并复用现有“导入批次 → 审核 → 发布”流程进入正式球员库。

成功标准：

- 开发者无需手工逐张录入或维护球员卡；
- 首次可以限定同步 100 条进行字段验收，验收后能够断点续传全部数据；
- 后续增量同步只补充新增或来源已更新的球员卡；
- 远端限流、短暂故障或进程退出不会产生半个导入批次，也不会丢失已完成进度；
- PESDATA 接口或签名规则变化时，同步明确失败并保留诊断信息，现有正式目录和小程序查询不受影响；
- 同步结果默认只生成待审核批次，不自动发布到小程序。

## 2. 前提与边界

### 2.1 前提

- 用户确认已获得 PESDATA 站方的数据获取授权；
- 站方未提供正式 API 文档、账号或 API 密钥；
- 当前网站公开页面使用同源 `/api/player/list` 和 `/api/player/detail` JSON 接口；
- 当前全量列表约 4.3 万张卡，实际数量以每次列表响应的 `count` 为准；
- 请求协议、签名参数和响应字段均可能随网站版本变化。

### 2.2 本阶段包含

- PESDATA 请求客户端与签名协议隔离；
- 球员卡列表分页读取；
- 球员卡详情按需补全；
- 字段映射和统一导入记录生成；
- 首轮抽样、全量、增量和断点续传命令；
- 限速、超时、重试、退避和运行状态保存；
- 生成现有 JSON 导入批次并输出审核摘要；
- 同步单元测试和使用文档。

### 2.3 本阶段不包含

- 小程序直接访问 PESDATA；
- 自动发布导入批次；
- 自动下架来源列表中暂时缺失的球员卡；
- 批量下载或镜像 PESDATA/KONAMI 图片；
- 绕过验证码、登录、WAF 或其他访问控制；
- Web 管理后台和定时任务平台；首版先提供可被 cron、CloudBase Job 或 CI 调用的命令。

## 3. 方案选择

采用“内部 JSON 接口 + 后端适配器 + 现有导入批次”的方案。

不采用 HTML 抓取，因为页面字段少于详情接口、解析脆弱且成本更高；不让小程序直接请求来源站，因为会暴露协议实现、缺少集中限速与重试，而且无法保证微信域名白名单和来源可用性。

PESDATA 特有逻辑全部位于独立客户端和映射器中。接口地址、版本、请求签名、响应解包或字段名改变时，只替换该边界，不修改正式目录、小程序 API 或发布逻辑。

## 4. 架构与职责

```text
PESDATA 列表/详情接口
          ↓
PesdataClient（请求、签名、限速、重试）
          ↓
PesdataMapper（来源字段 → RawImportRow）
          ↓
PesdataSyncService（分页、增量、检查点、汇总）
          ↓
现有 PlayerImportService（校验、差异、待审核批次）
          ↓
管理员人工发布
          ↓
公开球员库 API → 微信小程序
```

### 4.1 `PesdataClient`

- `listPlayers(query)` 请求列表接口，返回来源总数和摘要记录；
- `getPlayerDetail(playerId)` 请求详情接口并校验唯一结果；
- 统一添加网站版本、设备标识、时间戳、随机数和签名；
- 默认超时 15 秒；
- 默认每秒最多一个详情请求，同时只运行一个远端请求；
- 网络错误、HTTP 429 和 5xx 最多重试 5 次，采用带抖动的指数退避；
- 4xx 协议错误、签名错误和响应结构错误不盲目重试，立即中止运行并输出可诊断错误；
- 不输出完整签名材料、Cookie 或其他可能敏感的请求头。

### 4.2 `PesdataMapper`

将来源详情映射到现有导入字段：

- 卡片 `externalId` 使用 PESDATA `playerId`；
- 现实球员 `playerExternalId` 优先使用 `base_pes_id`，缺失时使用稳定的来源球员标识；
- 中、英、日名称保留在原始数据中，现有目录首版写入中英文展示名；
- `agentTitle + agentDate` 组成卡包稳定标识与展示信息；
- 位置、总评、卡片类型、比赛风格、状态、图片 URL 映射到现有一等字段；
- 能力值、身高、体重、年龄、惯用脚、状态持续性、增能器、多语言字段等写入 `attributes`；
- 球员技能映射到 `skills`；
- `sourceUpdatedAt` 优先使用详情的来源时间，无法获得可靠更新时间时使用详情内容校验值判断变化，不能用同步执行时间制造虚假更新。

映射器必须容忍未知字段，但必填字段缺失、类型不符或超出业务范围时生成无效导入记录，不能静默填造数据。

### 4.3 `PesdataSyncService`

同步模式：

- `sample`：从最新列表开始，最多补全 100 条详情，用于首次验收；
- `full`：遍历全部列表并补全全部详情；
- `incremental`：分页读取列表，仅对本地不存在、列表摘要变化或上次详情失败的卡片请求详情；
- `resume`：从指定未完成运行的检查点继续。

每次同步先创建运行记录，再逐页保存来源摘要和详情结果。所有成功映射的详情最终序列化为一个稳定排序的 JSON 内容，通过现有 `PlayerImportService.createBatch` 创建待审核批次。同步运行本身不直接写正式球员、卡片或发布版本。

## 5. 同步状态与断点续传

新增 `external_sync_runs`：

- 数据源、模式、状态；
- 来源总数、最大处理数、已扫描数、详情成功数、跳过数和失败数；
- 当前列表偏移量；
- 关联生成的导入批次；
- 启动、完成时间和失败摘要；
- 同一数据源最多一个 `RUNNING` 运行，由数据库租约避免重复执行。

新增 `external_sync_items`：

- 运行 ID、来源外部编号；
- 摘要校验值、详情校验值和状态；
- 标准化前的来源详情 JSON；
- 尝试次数和最后错误；
- 同一运行内来源外部编号唯一。

运行状态：

```text
PENDING → RUNNING → READY
              ├──→ PAUSED
              └──→ FAILED
```

- `READY` 表示已成功生成导入批次，不代表已经发布；
- 可恢复错误耗尽重试后将单项记为失败，运行在错误率不超过阈值时仍可完成，但生成摘要必须列出失败项；
- 签名、接口结构或授权类错误将整次运行标记 `FAILED`，避免大面积制造无效记录；
- `resume` 只重试未完成或失败项，不重复请求已成功详情。

## 6. 增量规则

- 列表摘要按来源外部编号保存稳定校验值；
- 本地从未出现的编号必须拉取详情；
- 摘要校验值变化必须重新拉取详情；
- 摘要未变化且最近一次详情成功的记录可以跳过；
- 上次详情失败或映射无效的记录必须重新尝试；
- 来源记录缺失不代表删除，首版不会自动将正式卡片设为下架；
- 同步生成的 JSON 按外部编号稳定排序，使相同数据得到相同批次校验值并复用现有幂等逻辑。

## 7. 命令接口

新增脚本入口：

```bash
pnpm --filter @efm/api sync:pesdata sample --actor <user-id> --limit 100
pnpm --filter @efm/api sync:pesdata full --actor <user-id>
pnpm --filter @efm/api sync:pesdata incremental --actor <user-id>
pnpm --filter @efm/api sync:pesdata resume <run-id> --actor <user-id>
pnpm --filter @efm/api sync:pesdata sample --actor <user-id> --limit 100 --dry-run
```

- `--actor` 必须拥有 `catalog.import.create` 权限；
- `--dry-run` 请求并映射数据、输出摘要，但不创建同步运行和导入批次；
- 输出 JSON，包含运行 ID、扫描数、详情成功/失败/跳过数、批次 ID和下一步发布命令；
- 命令正常结束不自动调用发布服务。

## 8. 配置

配置全部位于后端环境：

- `PESDATA_BASE_URL`，默认授权网站地址；
- `PESDATA_SITE_VERSION`，与当前网站客户端协议版本一致；
- `PESDATA_REQUESTS_PER_SECOND`，默认 `1`；
- `PESDATA_TIMEOUT_MS`，默认 `15000`；
- `PESDATA_MAX_RETRIES`，默认 `5`；
- 当前网站协议所需的签名材料由来源客户端封装，不能出现在小程序包、日志或公开 API 响应中。

部署前通过一次 `sample --dry-run` 验证协议。若站方以后提供正式 API，则在 `PesdataClient` 内切换认证实现，保持同步服务和导入格式不变。

## 9. 错误处理与可观测性

日志只记录运行 ID、接口类别、来源外部编号、HTTP 状态、尝试次数和错误代码，不记录完整响应与签名头。

错误分类：

- `PESDATA_NETWORK_ERROR`：连接、DNS 或超时，可重试；
- `PESDATA_RATE_LIMITED`：429，可按响应头或退避时间重试；
- `PESDATA_UPSTREAM_ERROR`：5xx，可重试；
- `PESDATA_PROTOCOL_ERROR`：签名、版本或响应结构改变，终止运行；
- `PESDATA_MAPPING_ERROR`：单条字段不合法，记录失败并继续；
- `PESDATA_SYNC_CONFLICT`：同一来源已有运行，拒绝重复启动。

首版不新增外部告警渠道，但命令必须以非零退出码结束失败运行，方便后续接入 CloudBase、CI 或通知系统。

## 10. 测试与验收

单元测试必须覆盖：

- 相同参数生成符合当前协议的请求签名；
- 列表和详情响应的结构校验；
- 卡片类型、位置、卡包、技能和完整属性映射；
- 未知字段容忍与必填字段错误；
- 分页到来源 `count` 后停止；
- `sample` 严格遵守最大数量；
- 429/5xx 重试，4xx 协议错误立即失败；
- 断点恢复不重复获取成功详情；
- 增量模式只补全新增、变化和失败项；
- 稳定排序和内容校验值保证幂等批次；
- 同步不会自动发布。

集成验收顺序：

1. 使用真实来源运行 `sample --dry-run --limit 2`，验证连通性和字段；
2. 运行 `sample --limit 100` 创建待审核批次；
3. 检查无效记录、名称、图片、能力、技能和卡包映射；
4. 人工发布该批次，在小程序检查列表、筛选和详情；
5. 运行一次中断与恢复测试；
6. 通过后再启动全量同步；
7. 全量完成并抽样验收后人工发布。

## 11. 安全与运营规则

- 仅在已获授权的范围内使用数据；授权范围发生变化时立即停用数据源；
- 尊重来源站实时 robots、可用性和限流信号；
- 不绕过验证码、登录、WAF 或其他访问控制；
- 用户代理标识本项目同步用途并提供可识别版本；
- 首版只保存图片 URL，不批量复制图片文件；
- 来源站不可用时继续提供最近一次已发布目录，不清空正式数据；
- 全量运行默认人工触发；日常增量调度在首轮全量验收后另行启用。
