# 微信机器人私聊管理与球队参与设计

日期：2026-10-26。状态：接入方式及角色分工已获用户确认；本书面设计待审阅。

## 1. 已确认需求与方案选择

使用专用个人微信号和常在线 Windows 电脑，复用仓库 Windows Bridge。管理员私聊机器人录入比分、录入晋级、录入转会、管理拍卖。球队负责人可以查询赛程和参与拍卖，不能通过机器人执行管理操作。

已讨论的替代方案是官方客服会话入口：可以作为其他消息渠道，但不是普通微信好友私聊及普通微信群的使用体验，最新接入资质和限制尚未核验。用户选择现有 Windows Bridge 路线。新建独立机器人业务数据库会重复维护赛程、财务和阵容规则，不采用。

本设计中的命令语法、确认时限、绑定流程和首版边界是实施建议，不冒充用户逐项确认的要求。

## 3. 角色和渠道

| 操作 | 管理员私聊 | 负责人私聊 | 授权微信群 |
| --- | --- | --- | --- |
| 赛程查询 | 管理范围内可查 | 绑定身份后查所属联赛公开赛程 | 保留公开赛程查询和绑定后的我的赛程 |
| 比分、晋级、转会 | 有权限者可操作 | 拒绝 | 拒绝管理操作，提示私聊 |
| 拍卖批次管理、审核 | 有权限者可操作 | 拒绝 | 不再接受管理命令 |
| 竞价 | 管理身份不赋予竞价资格 | 首版不接收私聊报价 | 已绑定且拥有该联赛有效球队者可报价 |

双重身份者按操作分别鉴权。已有小程序拍卖继续保留；每批使用既定单一竞价渠道，微信报价不得进入小程序渠道批次。

## 4. 身份绑定与作用域

球队负责人沿用小程序一次性验证码绑定 User。新增独立的管理员绑定流程：已登录后台的管理员在机器人设置中申请设备作用域的一次性验证码，私聊发送 `绑定管理 <验证码>`，关联真实 Admin 身份。不得凭昵称、手填管理员 ID、球队用户角色或设备令牌获得管理员权限。

建议验证码 5 分钟有效、哈希存储、单次消费、限制尝试频率；签发接口要求现有后台登录及适用权限。管理员可在后台撤销绑定；停用管理员、撤销权限或更换机器人身份立即阻止后续操作。绑定唯一性约束和审计应与现有用户绑定保持一致，但两个身份命名空间不能混用。

私聊上下文按设备、联系人存储当前联赛和赛季。`切换联赛`、`切换赛季`仅能选择该身份可访问范围；多项匹配时列候选，不猜测。单一可用范围可自动选中并明确回复。群查询仍从群绑定决定范围。确认时重新验证权限、实体所属联赛、赛季和状态，不信任旧上下文。

## 5. 命令与交互

首版采用确定性文本命令，不引入大模型、语音或图片识别。帮助按角色和渠道输出。

| 示例 | 语义 |
| --- | --- |
| `赛程 冠军杯` / `我的赛程` | 返回编号、赛事、轮次、主客队、时间、状态；支持分页 |
| `报分 M2133 2:1` | 按系统主客顺序录入，展示原结果及新结果后确认 |
| `晋级 M2133 T24 原因：对手弃权` | 按来源比赛定位杯赛对阵，以明确球队作为裁定胜者 |
| `转会 P102 T24 T41 500` | 精确定位球员卡/归属、转出与转入球队；金额使用现有系统单位并在预览注明 |
| `拍卖列表` / `拍卖 A12` | 查看批次及当前拍品 |
| `开始拍卖 A12` / `暂停拍卖 A12` / `继续拍卖 A12` | 私聊控制指定批次，群内接收业务公告 |
| `取消拍卖 A12 原因：…` | 预览影响并确认取消 |
| `审核成交 L12` | 展示计算结果、获胜球队、价格及实际结算影响，确认后调用现有审核服务 |
| `确认 K7` / `取消 K7` / `操作 K7` | 执行、取消或查询具体操作 |

短编号是持久化实体引用，不是查询结果行号，也不拼接两队编号。优先复用现有唯一编号；不足的比赛、拍品、球员卡等新增持久化映射及唯一约束。名称可辅助查找，重名必须返回候选。编号解析仍受授权范围约束。

写操作默认先预览再确认，确认有效期建议 2 分钟；查询和竞价无需确认。暂停拍卖作为紧急操作可由已授权管理员直接执行，其他管理状态变化仍预览确认。预览必须显示联赛、赛季、具体对象及影响；转会包括球员卡、双方、金额和现有规则计算的费用。不能用固定含糊的“操作成功”代替实际结果。

## 6. 业务边界

### 比分与晋级

报分复用管理员正式录分服务和现有积分/签表更新规则，明确主客顺序；更正已录比分展示旧值并要求原因，遵守下游比赛锁定规则。现有淘汰赛不接受平局，首版不借机器人隐式添加点球赛制。

正常比分产生晋级时沿用现有推进，不额外重复晋级。独立“晋级”命令用于杯赛来源对阵的人工裁定：新增带原因的裁定业务入口和持久化审计，以真实胜者推进签表，不伪造 1:0 等比分。复用赛事锁、下游锁定和后续阶段生成规则；若现有正式结果模型不能表示无比分裁定，应显式增加裁定类型与查询展示，不能只改 winner 字段。下一轮发布仍遵循现有发布流程。

首版“晋级”指杯赛对阵晋级，不包含跨赛季升降级或任意把球队插入其他赛事。批量分组晋级及新赛制不在本次范围。

### 转会

复用管理员转会服务及其窗口、余额、归属、阵容、费用和联赛权限规则。确认时重新校验预览依赖；报价或费用变化必须重新预览，不默默使用新金额。机器人不提供绕过规则的直接数据库修改。球队负责人仍可使用原小程序已有功能，本设计只限制机器人入口。

### 拍卖

首版私聊支持查看、开始、暂停、继续/故障恢复、取消，以及已有审核动作（确认、按原规则调整、作废；调整/作废需要原因）。批次创建、球员挑选排序、起拍价等复杂配置继续使用已有后台；聊天只操控准备好的批次。

批次确定目标群和竞价渠道，私聊管理员无需身处群聊。开始前验证设备、群、批次状态，向管理员展示目标；群里接收开拍、有效报价、倒计时和结果。使用当前服务端状态机和数据库时钟，不以消息送达时间判定成交。故障恢复沿用现有人工核对与恢复保护，不将 `继续拍卖` 作为跳过故障核对的捷径。

审核成交复用当前入队结算逻辑；不得再发起一次普通转会导致重复结算。流拍、调整和作废遵循现有业务规则，预览准确显示对应效果。后台仍可管理同一批次，并发变更使旧确认失效。

## 7. 技术结构与可靠性

微信 → Windows Bridge → 入站去重 → 渠道与身份鉴权 → 命令解析和实体定位 → 查询或待确认操作 → 业务服务 → 持久化回执与发件箱 → 原私聊回复/目标群公告。

Bridge 只采集允许的命令、转发和串行发消息，不持有管理员会话 JWT、不执行业务规则。设备凭证证明消息来源，不替代实际操作者授权。收发沿用版本检测、目标会话校验、消息回读和熔断。

建议新增管理员身份绑定、私聊上下文、待确认操作及必要的短编号映射。待确认记录包含设备/联系人、Admin、命令类型、目标实体、规范化参数、预览版本、到期时间、状态、执行结果引用。确认码绑定原操作者及私聊，不跨用户使用。

执行状态持久化：PENDING → EXECUTING → SUCCEEDED/FAILED，另有 CANCELLED/EXPIRED。同一确认只能领取一次；业务幂等键取持久化操作 ID。复用现有业务回执，新增业务也要在同一事务写入效果与回执。进程中断后根据回执恢复，不能仅因网络异常判失败并再次扣款。结果和发件箱可靠关联；回复失败只重试通知，不重做业务。无法确认送达时沿用 AMBIGUOUS 人工核对，避免盲目重发。

审计记录操作者、消息 ID、业务操作 ID、范围、原值/新值、原因和执行结果。不保留验证码明文和无关聊天。管理员私聊内容不自动转发到群；群只接收拍卖公开业务信息。

## 8. 实施顺序和验收

1. 管理员绑定、私聊解析、作用域、查询、确认与幂等基础。
2. 私聊报分及杯赛晋级裁定，与原结果和签表流程回归。
3. 私聊转会与费用预览、审计及并发校验。
4. 私聊拍卖管理/审核、移除群管理入口，保留群查询和竞价。
5. Windows 专用测试群和账号真实收发验收、受控上线。

自动验证覆盖越权、跨联赛、群内管理拒绝、验证码重放、确认过期/换人/重复、权限撤销、并发后台修改、业务成功但回复失败、进程中断恢复；业务验证覆盖积分、下轮签表锁、转会账目阵容一致性、拍卖单渠道和审核不重复结算。

所有 API 单元和端到端测试命令必须显式指定本机隔离 `DATABASE_URL`，库名包含 test 或 verify，不继承 .env。持久化测试数据自动清理并复查。旧验收文档中的无显式数据库目标命令不得照搬。

回归后台“现役球队/已退出”、球队详情、小程序“我的联赛”，以及结果展示、赛程、阵容、原拍卖入口。若修改小程序绑定 UI，按 AGENTS.md 在微信开发者工具检查窄屏和常见手机宽度、按钮正常/禁用态。

目标环境部署前核对 `pnpm db:status` 并受控应用迁移，再开放新代码流量；不得在共享库运行开发迁移、seed 或测试。真实 Windows 验收与本机自动测试分开报告，未验收部分明确列出。新增私聊管理功能使用开关灰度启用；紧急撤销设备/管理员绑定和停止发送不影响后台继续管理。
