# 联赛展示、当前赛季与管理员绑定设计

**日期：** 2026-09-29  
**状态：** 已确认，待实施  
**范围：** 联赛展示资料、当前赛季、参赛人数、后台球队绑定、小程序入口收敛

## 1. 目标

本次迭代把联赛、赛季、微信用户和联赛球队之间的操作边界统一起来：

- 后台维护联赛名称、图片、说明和国服/国际服类型；
- 赛季挂在联赛下，由管理员手动指定当前赛季；
- 小程序展示当前赛季和当前赛季实际入组球队数；
- 微信用户只负责登录并取得六位用户编号；
- 管理员通过后台为微信用户创建并绑定联赛球队；
- 首次绑定球队时自动报名并入组当前赛季；
- 游戏账号、个人资料编辑和用户自助球队编辑退出当前产品流程。

设计继续沿用现有 `League → LeagueSeason → LeagueTeam → SeasonEntry` 模型，不建立重复的联赛内容管理子系统。

## 2. 已确认业务规则

### 2.1 联赛资料

每个联赛保存并展示：

- 联赛名称与简称；
- 联赛图片；
- 联赛说明；
- 版本类型：国服或国际服；
- 管理员手动指定的当前赛季；
- 联赛状态。

版本类型是必选的联赛级属性，不再在球队表单中设置游戏平台或服务器区域。同一联赛下的全部球队继承联赛版本类型。

### 2.2 当前赛季

- 赛季必须属于一个联赛；
- 一个联赛同一时间最多指定一个当前赛季；
- 当前赛季由管理员手动指定，不根据日期或赛季状态自动推断；
- 切换当前赛季不自动把历史球队报名到新赛季；
- 管理员在赛季管理页选择已有联赛球队参加新赛季；
- 切换当前赛季必须记录审计日志。

### 2.3 参赛人数

小程序显示的“参赛人数”是当前赛季已报名并已入组的球队数量。

该数字由数据库中当前赛季 `status = APPROVED` 的 `SeasonEntry` 实时聚合，不写入联赛表，不统计：

- 仅有联赛球队但未参加当前赛季的用户；
- 待审核、已拒绝、已退出的报名；
- 历史赛季的参赛球队。

### 2.4 用户与联赛球队绑定

- 微信用户必须至少成功登录一次，系统才会生成用户记录与六位公开编号；
- 管理员使用公开编号查找用户；
- 同一用户在同一联赛最多拥有一支球队；
- 用户在不同联赛中可以拥有不同球队；
- 绑定时填写球队编号、名称、简称和队徽；
- 球队编号在同一联赛内唯一；
- 联赛没有当前赛季时禁止绑定，并提示先创建和指定当前赛季；
- 创建联赛球队和创建当前赛季报名记录必须位于同一数据库事务；
- 首次绑定创建的报名记录直接进入有效入组状态并计入参赛人数；
- 新赛季开始时，历史球队不会自动参赛，由管理员选择；
- 新赛季成为当前赛季后，新绑定的用户球队仍自动报名该当前赛季。

## 3. 数据设计

### 3.1 League

沿用现有 `name`、`shortName`、`description`、`logoUrl` 和 `status`，增加：

```text
edition          NATIONAL | INTERNATIONAL
currentSeasonId  String?
```

约束与关系：

- `edition` 最终为数据库非空枚举；
- `currentSeasonId` 可以为空，以支持刚创建但尚未建立赛季的联赛；
- 指定的当前赛季必须属于同一联赛；
- 删除或取消赛季前必须先解除其当前赛季引用。

现有 `defaultPlatform` 和 `defaultServerRegion` 退出新的联赛合同。迁移稳定前可在数据库中短期保留，但客户端、后台表单和新接口不再依赖它们。

### 3.2 LeagueSeason

继续使用现有赛季字段和生命周期。新增从 `League.currentSeasonId` 指向赛季的显式关系，不使用 `IN_PROGRESS` 等状态推断当前赛季。

### 3.3 LeagueTeam 与 SeasonEntry

`LeagueTeam` 继续作为用户在某一联赛中的长期球队。首次绑定时同时创建该联赛当前赛季的 `SeasonEntry`：

```text
LeagueTeam.ownerUserId = 被绑定微信用户
SeasonEntry.seasonId = League.currentSeasonId
SeasonEntry.leagueTeamId = 新球队
SeasonEntry.status = APPROVED
```

现有 `SeasonEntry.gameAccountId`、`gamePlatformSnapshot`、`serverRegionSnapshot` 和
`gamerTagSnapshot` 仍是必填字段。兼容迁移将这些字段改为可空，仅供历史记录读取；新报名不再创建或要求
`GameAccount`。新增 `leagueEditionSnapshot` 保存报名时的国服/国际服快照，新报名必须写入该值。

`SeasonEntry.teamProfileId` 保持可空，新流程只关联 `leagueTeamId`，不再创建或要求全局
`TeamProfile`。旧记录保留原关联，避免破坏历史赛季展示。

### 3.4 迁移策略

迁移分为兼容和清理两个阶段：

1. 增加 `edition` 和 `currentSeasonId`，回填已知旧值；
2. `GLOBAL`、`INTERNATIONAL` 映射为国际服；
3. `CN`、`CHINA`、`NATIONAL` 映射为国服；
4. 无法识别的旧值输出迁移报告并要求人工确认，不静默猜测；
5. 所有联赛完成回填后将 `edition` 收紧为非空；
6. 将 `SeasonEntry` 的旧游戏账号及其快照字段改为可空，并回填 `leagueEditionSnapshot`；
7. 客户端稳定后再单独删除旧游戏平台、服务器区域和游戏账号相关字段及表。

## 4. 后台管理设计

### 4.1 联赛管理

平台管理员的新建和编辑联赛表单包含：

- 联赛名称；
- 联赛简称；
- 联赛图片上传；
- 联赛说明；
- 国服/国际服必选项；
- 默认分组与升级规则；
- 联赛状态。

删除原“游戏平台”和自由输入的“服务器区域”。未选择国服/国际服时表单不能提交，API 同样拒绝请求。

### 4.2 图片上传

上传控件下方固定展示：

> 支持 JPG、PNG、WebP，图片大小不超过 2MB

前端在选择文件后立即校验，API 再校验文件大小和真实 MIME 类型。数据库只保存资源 URL，不保存图片二进制。

存储层提供统一接口：

```text
ObjectStorage.put(scope, file) -> StoredObject
ObjectStorage.delete(key)
```

本地开发使用本地文件存储适配器，正式环境使用 CloudBase 对象存储适配器。该接口后续复用于队徽和新闻图片。

### 4.3 赛季管理

联赛后台增加赛季管理入口：

- 查看该联赛全部赛季；
- 新建和编辑赛季；
- 手动设为当前赛季；
- 查看当前赛季已入组数量；
- 从已有联赛球队中选择本赛季参赛球队。

设为当前赛季时校验赛季归属，并使用版本号或事务锁避免并发覆盖。

### 4.4 用户与球队绑定

后台按六位用户编号搜索，展示足够确认身份的信息。管理员填写球队资料后提交：

1. 校验管理员联赛权限；
2. 锁定联赛并读取当前赛季；
3. 校验用户、球队编号和联赛内用户唯一性；
4. 创建 `LeagueTeam`；
5. 创建已批准的 `SeasonEntry`；
6. 写入审计日志；
7. 提交事务。

任何一步失败都回滚，不产生半绑定状态。

## 5. 小程序设计

### 5.1 联赛入口

底部“联赛”是完整联赛列表的唯一主入口，提供：

- 全部联赛；
- 我的联赛。

“我的联赛”表示管理员已为当前微信用户绑定球队的联赛。每张联赛卡展示：

- 联赛图片、名称和简短说明；
- 国服或国际服；
- 当前赛季名称；
- 当前赛季已报名并已入组的球队数；
- 已绑定时展示当前用户的球队编号和队名。

页面进入、恢复前台和下拉刷新时重新请求数据，使后台变更可及时显示，不引入长连接。

### 5.2 我的入口

底部“我的”收敛为只读身份和球队摘要：

- 微信登录状态；
- 六位用户编号与复制按钮；
- 已加入联赛数量；
- 按联赛展示已绑定球队摘要；
- 点击摘要跳转到“联赛 → 我的联赛”或对应联赛详情。

删除：

- 游戏账号列表及新增、编辑入口；
- 用户手动编辑个人名称、地区、头像链接；
- 用户自助新增或编辑球队资料。

### 5.3 联赛详情

联赛详情展示完整说明、版本类型、当前赛季、参赛数量和当前用户球队。阵容保持只读。积分榜、赛程、杯赛和财务继续通过独立模块扩展。

## 6. API 边界

核心接口按现有命名风格实现：

- 平台联赛创建、编辑接口支持 `edition`、说明和图片 URL；
- 联赛图片使用独立受保护上传接口；
- 联赛赛季列表、创建、编辑和“设为当前赛季”接口；
- 当前赛季参赛球队选择接口；
- 后台按公开编号查找用户接口；
- 创建联赛球队接口原子完成当前赛季报名；
- 公共/登录态联赛列表响应当前赛季摘要和参赛数量；
- “我的联赛球队”接口提供只读球队与当前赛季摘要。

所有后台写接口从管理员会话计算权限，不接受客户端声明权限范围；变更接口支持幂等键和审计记录。

旧游戏账号和个人资料写接口先停止客户端使用并标记弃用，待兼容观察期后删除。

## 7. 错误处理

面向管理员提供明确错误：

- 请先创建并指定当前赛季；
- 该用户已在本联赛绑定球队；
- 球队编号已被使用；
- 用户不存在，请让用户先登录小程序；
- 必须选择国服或国际服；
- 仅支持 JPG、PNG、WebP；
- 图片大小不能超过 2MB；
- 目标赛季不属于当前联赛；
- 数据已被其他管理员修改，请刷新后重试。

数据库唯一约束和事务作为并发情况下的最终一致性保护。

## 8. 验收标准

- 后台可创建并编辑带图片、说明和必选版本类型的联赛；
- 图片大于 2MB 或格式不合法时前后端均拒绝；
- 管理员可创建赛季并手动设为当前赛季；
- 当前赛季只能引用本联赛赛季；
- 首次绑定用户球队会自动、原子地加入当前赛季；
- 无当前赛季时不能绑定球队；
- 切换当前赛季不会自动报名历史球队；
- 管理员可选择历史球队参加新赛季；
- 小程序人数等于当前赛季有效入组球队数；
- 全部联赛和我的联赛展示正确；
- 我的页面只读，并且不再出现游戏账号和个人/球队资料编辑入口；
- 后台球队表单不再出现游戏平台和服务器区域；
- 权限、幂等、并发和审计行为有自动化测试覆盖。

## 9. 非本期范围

- 用户自行报名联赛；
- 用户自行创建或修改联赛球队；
- 图片裁剪和复杂媒体管理；
- WebSocket 实时推送；
- 彻底物理删除全部旧账号/资料表；
- 积分榜、赛程、杯赛、资产、财务和身价模块的新功能。
