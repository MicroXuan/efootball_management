# 个人赛事基础闭环设计

**日期：** 2026-09-25
**状态：** 设计已确认，待编写实施计划
**产品范围：** V0.1 内部原型

**英文版本：** [2026-09-25-individual-competition-loop-design.md](./2026-09-25-individual-competition-loop-design.md)

## 1. 目标

交付一套可以在本地完整验证的个人赛事闭环：

```text
创建赛事 → 开放报名 → 玩家报名 → 审核报名
→ 生成并发布循环赛程 → 提交与确认比分
→ 发布带版本的积分榜 → 完成赛事
```

第一版只实现个人赛事和一个单循环阶段，但领域边界必须保证未来加入战队参赛方、工资帽名单、淘汰赛阶段、申诉以及 OCR 辅助证据识别时，无需替换赛程、比赛、结果或积分榜核心。

## 2. 范围

### 2.1 本阶段包含

- 个人赛事的草稿、发布和完整生命周期管理。
- 公开赛事列表与赛事详情。
- 平台和区服参赛资格校验。
- 玩家选择自己名下的游戏账号报名。
- 报名审核，以及将通过审核的报名转换为正式赛事参赛方。
- 确定性的单循环赛程生成、预览和发布。
- 玩家提交比分、对方确认或拒绝，以及管理员代录结果。
- 不可变的比赛结果版本，并指定其中一个版本为当前正式结果。
- 只使用正式结果计算的版本化积分榜。
- 玩家和具有赛事作用域权限的管理员小程序流程。
- 包含 4 名参赛者、6 场比赛的本地演示数据和端到端验收路径。

### 2.2 延后实现

- 战队创建、战队报名、成员关系和战队名单。
- 工资版本、工资帽规则、赛季名单和单场阵容。
- 淘汰赛、组合赛制、晋级和种子排名。
- 申诉、裁判工作台和处罚。
- 证据文件存储、图片 OCR 和自动提取比分。
- 微信订阅消息。
- 主办方组织和独立的网页管理后台。

数据库可以为延后能力预留枚举值和可空扩展字段，但不得在本阶段暴露无法完整使用的半成品流程。

## 3. 角色与权限

### 3.1 玩家

已登录玩家可以浏览公开赛事、使用自己的游戏账号报名、在报名开放期间撤回报名、查看自己的比赛、提交比分、确认或拒绝对方提交的比分，以及查看积分榜。

### 3.2 赛事管理员

赛事管理员可以编辑其作用域内的赛事、执行赛事状态流转、审核报名、生成并发布赛程、录入正式结果，以及完成或取消赛事。用户成功创建赛事后，系统自动授予其该赛事作用域内的 `EVENT_MANAGER` 角色。

### 3.3 平台管理员

平台管理员可以创建和管理全部赛事。现有作用域鉴权仍然是最终权限依据：用户在赛事 A 中拥有管理员绑定，并不代表其能操作赛事 B。

以下权限需要通过幂等种子脚本创建，并分配给对应固定角色：

- `competition.create`
- `competition.manage`
- `competition.registration.review`
- `competition.schedule.manage`
- `competition.result.manage`

公开查询无需登录。报名和比分操作要求用户状态正常，并执行资源作用域权限或参赛方归属校验。

## 4. 领域模型

### 4.1 赛事

`Competition` 保存赛事名称、介绍、平台、区服、参赛类型、赛制、生命周期状态、报名时间范围、计划比赛时间范围、人数上限、创建人、乐观并发版本和时间戳。

初始取值如下：

- 参赛类型：本阶段使用 `INDIVIDUAL`，预留 `TEAM`。
- 赛制：本阶段使用 `ROUND_ROBIN`，预留 `DOUBLE_ROUND_ROBIN`、`SINGLE_ELIMINATION` 和 `GROUP_KNOCKOUT`。
- 生命周期：`DRAFT`、`REGISTRATION_OPEN`、`REGISTRATION_CLOSED`、`SCHEDULED`、`IN_PROGRESS`、`COMPLETED` 或 `CANCELLED`。

报名开放后，平台、区服、参赛类型和赛制不可修改。所有时间以 UTC 存储。

### 4.2 赛事规则版本

`CompetitionRuleVersion` 保存单调递增的规则版本号、积分值、具有顺序的同分规则以及创建信息。开放报名时绑定当前生效规则版本；赛事开始时锁定该版本。后续修改必须产生新版本，不能静默改变进行中的赛事。

初始默认规则为胜 3 分、平 1 分、负 0 分。第一版支持的同分比较项包括总积分、相互比赛积分、相互比赛净胜球、总净胜球、总进球数和胜场数。

### 4.3 报名

`CompetitionRegistration` 表示报名申请，而不是已经进入赛程的正式参赛方。它保存赛事、申请用户、用户自己的游戏账号、已同意的规则版本、当前状态、审核信息、撤回信息、乐观并发版本和时间戳。`CompetitionRegistrationStatusHistory` 追加保存每一次提交、审核、撤回和重新提交，包括操作者、原因与时间。

报名状态为 `PENDING`、`APPROVED`、`REJECTED` 和 `WITHDRAWN`。赛事与申请用户的唯一约束保证每名玩家在同一赛事中只有一条长期保留的报名记录；被拒绝或主动撤回的报名可在报名仍开放时重新提交，同时新增状态历史并记录新接受的规则版本。

只有当赛事处于 `REGISTRATION_OPEN`、当前时间位于报名窗口内、尚未达到人数上限，并且游戏账号的平台和区服与赛事一致时，系统才接受报名。

### 4.4 赛事参赛方

`CompetitionParticipant` 是赛程、比赛和积分模块使用的稳定参赛身份。它保存赛事、参赛类型、来源报名、录取顺序、显示名称快照、本阶段使用的个人用户 ID，以及未来战队引用的扩展位置。

比赛和积分榜不会直接关联用户或战队。未来战队报名通过后，同样创建类型为 `TEAM` 的参赛方；工资帽名单也关联参赛方，而不是侵入比赛基础结构。

### 4.5 阶段与比赛

`CompetitionStage` 用于隔离不同赛制的排程逻辑。第一版创建一个 `ROUND_ROBIN` 阶段，未来可以增加小组赛或淘汰赛阶段。

`CompetitionMatch` 保存阶段、轮次、确定性的比赛序号、主客双方参赛方、计划时间、生命周期状态、当前正式结果版本 ID、乐观并发版本和时间戳。状态包括 `SCHEDULED`、`AWAITING_RESULT`、`PENDING_CONFIRMATION`、`CONFIRMED` 和 `ADMIN_DECIDED`。

唯一约束防止同一阶段内比赛序号重复或双方重复对阵。赛程发布后不能被静默重新生成。

### 4.6 结果版本

`MatchResultVersion` 保存比赛、版本号、主队比分、客队比分、提交人、提交方、状态、可选的拒绝或管理员修改原因、未来证据元数据扩展位置和时间戳。状态包括 `PROPOSED`、`REJECTED`、`OFFICIAL` 和 `SUPERSEDED`。

每次提交比分都创建一个新版本。对方可以确认或拒绝提案，但不能确认自己提交的提案。确认操作在同一事务内把该版本设为正式版本，并将此前的正式版本标记为已取代。管理员可以直接创建正式版本，但替换已有正式结果时必须填写原因。正式历史永远不能被物理删除或原地覆盖。

### 4.7 积分榜快照

`StandingsSnapshot` 表示一次完整重算，保存赛事、单调递增的版本号、触发本次计算的结果版本、规则版本、生成时间及其积分行。

`StandingsRow` 保存参赛方、场次、胜、平、负、进球、失球、净胜球、基础积分、为未来处罚预留的调整积分、总积分、排名、同分状态，以及复现排序所需的全部同分比较值。

每次正式结果变化都根据完整的正式结果集合重新生成积分榜。重复处理会产生相同的积分行，不会重复累计积分。

## 5. 状态机

### 5.1 赛事状态

```text
DRAFT → REGISTRATION_OPEN → REGISTRATION_CLOSED
      → SCHEDULED → IN_PROGRESS → COMPLETED
                 ↘ CANCELLED
```

赛事完成前允许取消，取消后仍保留报名、赛程、结果和审计历史。没有已发布赛程的赛事不能开始。仍有比赛缺少正式结果时，赛事不能完成；未来可通过取消比赛或判罚流程处理该例外，但本阶段不开放这些入口。

### 5.2 报名状态

```text
PENDING → APPROVED
        → REJECTED ─┐
        → WITHDRAWN ┴→ PENDING（报名开放时重新提交）
```

审核通过操作必须在同一事务中准确创建一个正式参赛方。报名关闭后，已审核通过的报名不能撤回。

### 5.3 比赛结果状态

```text
SCHEDULED → AWAITING_RESULT → PENDING_CONFIRMATION
          → CONFIRMED
          → ADMIN_DECIDED
```

只有状态为 `CONFIRMED` 或 `ADMIN_DECIDED` 的比赛会计入积分榜。

## 6. 赛程生成

赛程生成使用纯函数实现的循环赛圆桌算法。参赛方按录取顺序和参赛方 ID 排序。参赛人数为奇数时加入一个虚拟轮空位，与轮空位配对时不生成比赛。

当参赛人数 `n` 为偶数时，系统生成 `n - 1` 轮和 `n(n - 1)/2` 场比赛。每名参赛方每轮最多出赛一次，每一对无序参赛组合只出现一次。

生成操作先创建草稿阶段和草稿比赛。发布前重复生成会在同一事务中只替换未发布草稿；同样的参赛顺序始终产生同样的对阵。发布后赛程锁定。第一版不会自动分配开球时间，管理员可以为每场比赛设置可选的计划时间。

## 7. 积分榜

默认积分为胜 `3`、平 `1`、负 `0`，排名依次比较：

1. 总积分；
2. 同分参赛方之间的相互比赛积分；
3. 同分参赛方之间的相互比赛净胜球；
4. 总净胜球；
5. 总进球数；
6. 胜场数。

如果比较后仍然完全相同，则使用录取顺序保证展示稳定，并把相关积分行标记为 `tiePending=true`。这样可以提供稳定接口，同时不会假装竞技层面的同分已经解决；未来可以通过公平竞赛分、抽签或附加赛处理。

全部计算只使用已经锁定的规则版本和正式比分。API 会返回积分榜快照版本，以及生成该快照所使用的结果版本和规则版本。

## 8. API

### 8.1 公开接口

- `GET /v1/competitions`
- `GET /v1/competitions/:id`
- `GET /v1/competitions/:id/matches`
- `GET /v1/competitions/:id/standings`

### 8.2 已登录玩家接口

- `POST /v1/competitions/:id/registrations`
- `DELETE /v1/competitions/:id/registrations/me`
- `GET /v1/me/competitions`
- `GET /v1/me/matches`
- `POST /v1/matches/:id/results`
- `POST /v1/matches/:id/results/:version/confirm`
- `POST /v1/matches/:id/results/:version/reject`

### 8.3 赛事管理接口

- `POST /v1/admin/competitions`
- `PATCH /v1/admin/competitions/:id`
- 开放报名、关闭报名、开始、完成和取消等生命周期接口；
- 报名审核接口；
- 赛程生成、预览和发布接口；
- 管理员结果录入与修正接口。

所有写操作都接收幂等键。依赖资源版本的操作还必须提交预期版本；操作过期时返回 `409`。

## 9. 小程序体验

底部导航调整为：

```text
球员 | 赛事 | 我的
```

玩家页面包括：

- 赛事列表及生命周期筛选；
- 包含概览、规则、报名状态、赛程和积分榜的赛事详情；
- 选择符合资格游戏账号的报名面板；
- 我的赛事和我的比赛；
- 比分提交、确认、拒绝和版本冲突恢复。

管理员页面包括：

- 赛事草稿编辑器；
- 报名审核队列；
- 赛程预览与发布；
- 管理员比分录入与修正。

客户端会区分参数校验、权限、生命周期、版本过期和网络失败。正式结果冲突不会被隐藏在通用重试提示后面。

## 10. 错误处理与一致性

- 数据库约束和事务保证报名唯一、参赛方唯一、赛程唯一、结果版本顺序以及积分榜版本顺序。
- 乐观并发版本保护赛事、报名和比赛的写操作。
- 幂等键防止重复点击、请求重试或网络重连产生重复业务记录。
- 权限拒绝返回 `403`，且不泄露私有资源信息；归属不匹配时根据现有约定返回资源不存在。
- 所有公开分页使用确定性的游标排序。
- 错误码属于稳定接口契约，并映射成可以指导用户解决问题的中文提示。
- 结果和积分相关日志只记录标识符与错误码；未来的证据内容和敏感令牌不得写入日志。

## 11. 测试

### 11.1 领域测试

- 合法与非法的赛事状态转换。
- 2 至至少 9 名参赛方的循环赛算法性质。
- 奇数参赛方轮空、无重复对阵和稳定重新生成。
- 胜平负积分以及多人同分时的相互战绩比较。
- 未解决同分的确定性展示顺序。

### 11.2 服务与持久化测试

- 报名资格、账号归属、唯一性、截止时间和并发。
- 重复审核请求只创建一个参赛方。
- 赛程生成和发布具有幂等性。
- 比分提交者和确认者限制。
- 过期结果确认失败，且不改变正式版本。
- 正式结果修正保留旧版本，并且只重算一次积分榜。
- 具有作用域权限的管理员不能修改其他赛事。

### 11.3 API 与小程序测试

- 从创建赛事到生成积分榜的 4 人端到端闭环。
- 公开接口只展示已发布赛事和已发布赛程。
- 小程序加载、空状态、校验错误、版本冲突和重试状态的视图模型测试。
- 现有身份、球员库、导入和 PESDATA 同步回归测试持续通过。

## 12. 验收场景

本地验收数据创建一个个人赛事，以及 4 名拥有匹配游戏账号的测试用户。4 人全部报名并审核通过。赛程生成应得到 3 轮、6 场不重复比赛。发布后，小程序可以查看这些比赛。玩家提交并确认比分后，每一个正式结果都会更新积分榜。修正一场正式结果会创建新结果版本和一个可复现的新积分榜快照。重复请求不会创建重复报名、参赛方、比赛、结果或积分行。

## 13. 扩展边界

- 战队报名在创建现有 `TEAM` 类型参赛方之前，增加战队归属和名单工作流。
- 工资帽把版本化赛季名单和单场阵容关联到参赛方；赛程与积分逻辑保持不变。
- 淘汰赛在阶段接口后增加排程与晋级策略；比赛结果继续复用同一套版本服务。
- 申诉引用结果版本，并可产生管理员修正版本；不会覆盖结果历史。
- 截图存储和 OCR 为结果提案补充证据元数据，但不能直接把未经确认的比分变成正式结果。
