# 小程序球员拍卖大厅设计

**日期：** 2026-10-10

**目标分支：** `codex/league-center-banner`

**范围：** 在保留现有微信群机器人全部能力的前提下，新增微信小程序拍卖大厅、用户出价接口和后台拍卖控制能力。

## 1. 背景与目标

现有系统已经具备微信群机器人拍卖：管理员在后台配置批次和拍品，机器人从普通微信群读取纯数字报价，服务端维护 30 秒倒计时，在 `20、10、3、2、1` 秒播报，成交或流拍后自动进入下一位，最后由管理员人工审核。

新增的小程序拍卖大厅不是替换现有机器人，而是增加一种更稳定的拍卖方式。球队负责人从微信群中的小程序卡片进入对应批次，在小程序内查看当前球员、价格、最高出价球队和倒计时，并使用已经登录的小程序身份出价。微信群继续承担组织、讨论、赛程查询和拍卖通知；Windows Bridge 是否在线不再影响小程序拍卖的计时和出价。

成功标准：

- 现有微信群查询、群内纯数字出价、机器人播报和 Windows Bridge 行为保持兼容；
- 管理员创建批次时可以选择“微信群出价”或“小程序出价”；
- 多个联赛可以同时进行拍卖，同一联赛同一时刻最多一个未结束的正式拍卖；
- 小程序用户只能代表自己在该联赛中的有效球队出价；
- 所有有效出价由数据库时间和事务锁裁定，重试不会产生重复报价；
- 小程序展示的倒计时以服务端截止时间为准，断网、切后台或手机时间不改变裁定；
- 小程序模式下 Bridge 离线只影响群通知，不暂停或回滚拍卖；
- 拍卖结果继续进入现有人工审核流程，不自动扣款、不自动修改阵容。

## 2. 产品边界

### 2.1 本期包含

- 管理后台为批次选择出价方式；
- 管理后台直接开始、暂停、继续和取消拍卖；
- 小程序拍卖入口、正在进行的拍卖列表和拍卖大厅；
- 小程序卡片携带 `batchId`，直接打开对应拍卖大厅；
- 小程序按用户身份读取批次并提交报价；
- 当前拍品、后续队列、有效报价记录和本人最近报价展示；
- 每秒状态同步，手机本地根据服务端时间计算平滑倒计时；
- 现有机器人对小程序拍卖发送开始、成交、流拍、下一位和完成通知；
- 体验版测试所需的固定页面路径与分享配置。

### 2.2 本期不包含

- 自动扣除球队资金；
- 自动写入球员所有权或阵容；
- 微信支付；
- WebSocket、SSE 或独立实时消息基础设施；
- 机器人自动发送小程序卡片；
- 从群聊身份自动登录小程序；
- 同一批次同时接受微信群和小程序两个渠道的正式报价；
- 同一联赛同时运行多个活动批次；
- 观众匿名围观或公开拍卖链接。

管理员手动从小程序转发卡片到微信群。未正式发布时，只有小程序管理员、项目成员和已配置的体验成员可以打开体验版卡片。

## 3. 核心决策

### 3.1 每批次选择一个出价渠道

`PlayerAuctionBatch` 新增出价渠道：

- `WECHAT_GROUP`：现有模式，微信群内发送纯数字报价；
- `MINIPROGRAM`：新增模式，小程序内提交报价。

已有数据迁移后默认是 `WECHAT_GROUP`，因此不会改变现有批次行为。一个批次不能同时接受两个渠道的正式报价，原因是微信群消息的原始发送时间和 HTTP 请求的服务端接收时间无法形成对所有参与者都可解释的统一排序。管理员可以为不同批次选择不同模式。

### 3.2 小程序模式仍绑定通知群

批次继续要求选择一个已启用 `PLAYER_AUCTION` 能力的微信群。该群用于：

- 分享小程序卡片；
- 机器人发送开始、成交、流拍、下一位和完成通知；
- 管理员在群内发送拍卖控制命令作为可选辅助入口。

小程序模式的业务状态不依赖通知是否发送成功。Bridge 离线、微信未登录、屏幕锁定或群通知失败时，服务端继续接受小程序报价并推进拍品；待管理员恢复机器人后，不补发已过期倒计时，只发送仍有意义的最新状态。

### 3.3 REST 轮询而不是首期 WebSocket

小程序每秒请求一次当前批次状态；接口返回 `serverNow`、`deadlineAt` 和 `deadlineEpoch`。客户端用 `deadlineAt - serverNow` 得到基准剩余时间，在两次请求之间使用本地单调计时更新画面。

报价使用独立 HTTP POST。接口返回报价裁定和最新批次快照，因此有效报价后页面立即重置为 30 秒，不必等待下一次轮询。该方案不新增长连接基础设施，也便于体验版在真实手机和弱网环境中验证。后续确有规模需求时可以增加 WebSocket，但不能改变 HTTP 报价接口和数据库裁定逻辑。

## 4. 用户流程

### 4.1 管理员创建与发布

1. 管理员进入现有“球员拍卖”后台。
2. 创建批次并选择出价方式：微信群出价或小程序出价。
3. 选择通知群、球员顺序、起拍价和最低加价。
4. 保存并准备拍卖。
5. 小程序模式显示固定分享入口 `/pages/auction-room/index?batchId=<id>`，并在后台提供可复制的批次编号和操作说明。
6. 管理员在小程序打开该批次，点击右上角转发到微信群。
7. 管理员可在后台点击“开始拍卖”，也可在绑定群发送现有的 `开始拍卖` 命令。

后台新增开始、暂停和继续按钮，确保机器人故障时仍能控制小程序拍卖。取消和人工审核继续使用现有入口。

### 4.2 球队负责人进入

用户可以通过以下入口进入：

- 微信群内的小程序卡片；
- 小程序联赛详情中的“球员拍卖”；
- 小程序“我的”或拍卖列表中的正在进行项目。

进入页面后必须已登录。服务端确认用户状态有效，并且拥有该联赛中状态为 `ACTIVE` 的 `LeagueTeam`。无球队用户可以只看到“没有该联赛出价资格”，不能读取完整报价明细或提交报价。其他联赛的球队不能出价。

### 4.3 出价

页面展示：

- 联赛名和批次名；
- 当前球员卡资料；
- 起拍价、最低加价、当前最高价和最高出价球队；
- 30 秒倒计时；
- 可直接填写的正整数金额；
- “最低有效价”快捷按钮；
- 当前拍品的有效报价记录；
- 后续球员队列和已完成结果；
- 当前用户代表的球队名称。

用户提交后按钮进入短暂加载状态，但页面倒计时继续。服务端返回：

- `VALID`：显示 `【球队名称】出价有效：⭐120⭐，倒计时重置为 30 秒。`；
- `BELOW_STARTING_PRICE`：提示最低起拍价；
- `BELOW_MINIMUM_INCREMENT`：提示当前最低有效价；
- `DEADLINE_PASSED`：提示该拍品已结束并刷新下一位；
- `PAUSED`、`INACTIVE`、`NO_ACTIVE_TEAM`、`WRONG_LEAGUE`：显示明确原因；
- 重复请求：返回第一次请求的相同结果，不产生第二条报价。

客户端不根据画面上的 `0` 自行判定成交。只有服务端状态变化才切换拍品。

### 4.4 自动推进与审核

现有 worker 保持 30 秒拍卖、有效报价重置 30 秒、`20、10、3、2、1` 标记、成交或流拍后自动进入下一位的规则。小程序模式中这些标记用于页面状态和可选群通知，不要求群通知成功。

最后一位结束后批次进入 `COMPLETED`。每位球员仍产生 `PENDING_REVIEW` 或 `NO_BID`，管理员继续在后台确认、调整或作废。审核不写财务和阵容。

## 5. 数据模型

### 5.1 批次

新增枚举 `PlayerAuctionBidChannel`：

```text
WECHAT_GROUP
MINIPROGRAM
```

`PlayerAuctionBatch.bidChannel` 非空，默认 `WECHAT_GROUP`。批次一旦离开 `DRAFT` 就不能修改渠道。

准备批次时，冲突检查从“同一个微信群”提升为“同一个联赛”：同一联赛最多存在一个状态为 `READY`、`ACTIVE`、`PAUSED` 或 `RECOVERY_REQUIRED` 的批次。不同联赛不互相阻塞。

### 5.2 报价来源

现有 `PlayerAuctionBid` 同时承载两类报价，并新增：

- `source`：`WECHAT_GROUP` 或 `MINIPROGRAM`；
- `idempotencyKey`：小程序请求幂等键，在 `userId + lotId` 作用域唯一；
- `submittedAt`：该渠道用于拍卖排序的规范时间；
- `receivedAt`：API 收到并持久化的时间，继续保留；
- 微信专属字段改为可空：`inboundMessageId`、`identityBindingId`、`wechatMessageId`、`wechatSortKey`、`wechatSentAt`。

微信群报价的 `submittedAt` 使用已经验证的 `wechatSentAt`，并继续以稳定排序字段处理同毫秒消息。小程序报价的 `submittedAt` 使用事务内数据库当前时间；客户端时间永远不参与裁定。

由于单个批次只允许一个渠道，排序逻辑无需比较两种时间源。现有微信群历史数据迁移为 `source=WECHAT_GROUP`，其他字段保持不变。

### 5.3 无新增资金与所有权数据

小程序拍卖复用 `PlayerAuctionReview`。本期不新增财务流水、阵容交易或球员所有权关系。

## 6. API 设计

所有小程序接口使用现有 `JwtAuthGuard`。

### 6.1 拍卖列表

```http
GET /v1/me/player-auctions?status=active
```

只返回当前用户拥有有效球队的联赛中的批次。列表可以包含 `READY`、`ACTIVE`、`PAUSED`、`COMPLETED`，默认重点展示 `READY/ACTIVE/PAUSED`。

### 6.2 拍卖大厅状态

```http
GET /v1/me/player-auctions/:batchId
```

返回：

- 批次、联赛和当前用户球队摘要；
- `serverNow`；
- 当前拍品、截止时间、epoch、当前价格和最低有效价格；
- 当前最高出价球队；
- 有效报价列表；
- 后续队列和已关闭结果；
- `canBid` 与不可出价原因；
- 分享标题和固定页面路径。

接口不返回微信联系人标识、其他用户 ID、失败报价的敏感诊断或后台审核备注。

### 6.3 提交报价

```http
POST /v1/me/player-auctions/:batchId/bids
Idempotency-Key: <uuid>
Content-Type: application/json

{ "amount": 120, "lotId": "...", "deadlineEpoch": 4 }
```

`lotId` 和 `deadlineEpoch` 防止用户在页面切换时把旧报价提交到下一位球员。服务端依次锁联赛、批次和当前拍品，在同一事务内获取数据库时间、校验用户球队、判断截止时间、计算最低有效价、写入报价、更新最高价并把截止时间重置为 30 秒。

幂等键重复时返回原始裁定。相同用户可以连续提交不同幂等键的更高报价；系统不禁止自己抬价，继续遵循最低加价规则。

### 6.4 管理后台控制

新增：

```http
POST /v1/admin/leagues/:leagueId/player-auctions/:batchId/start
POST /v1/admin/leagues/:leagueId/player-auctions/:batchId/pause
POST /v1/admin/leagues/:leagueId/player-auctions/:batchId/resume
```

请求使用 `Idempotency-Key` 和 `expectedVersion`。权限沿用 `league.auction.manage`。群内已有开始、暂停、继续、取消命令继续可用。

## 7. 并发、公平与时间

- 数据库时间是唯一裁定时间；
- 事务加锁顺序固定为联赛、批次、拍品，避免跨入口死锁；
- 准备和开始时锁定联赛，保证同一联赛只有一个未结束批次；
- 报价在截止时间之前进入事务并取得数据库时间才可能有效；
- 同时到达的报价以数据库锁取得顺序和 `submittedAt/id` 稳定排序；
- 每次有效报价将 `deadlineEpoch` 加一并设置新的 `deadlineAt`；
- 客户端携带旧 epoch 的请求返回 `AUCTION_EPOCH_CHANGED`，不误投到下一轮；
- worker 关闭拍品与报价使用同一锁顺序，因此只会有一方先完成，另一方按最新状态明确失败；
- API 实例重启不改变数据库中的截止时间，小程序轮询恢复后继续展示；
- 小程序模式启动时不因为 Bridge 状态进入 `RECOVERY_REQUIRED`。

## 8. 小程序设计

新增原生页面：

- `pages/player-auctions/index`：当前用户可参与的拍卖列表；
- `pages/auction-room/index`：拍卖大厅和分享页面。

联赛详情为拥有该联赛有效球队的用户展示“球员拍卖”入口。拍卖大厅采用现有暗色足球视觉：当前球员和倒计时是主要视觉层级，荧光绿只用于有效、可操作状态，错误和暂停有独立语义色。

页面生命周期：

- `onLoad` 读取 `batchId`；
- 未登录时保存目标路径并跳转登录，登录成功后返回；
- `onShow` 立即拉取状态并启动一秒轮询；
- `onHide/onUnload` 停止计时器；
- 从后台返回后立即重新同步，不能依赖离开前的倒计时；
- 连续网络错误采用 1、2、5 秒退避，页面保留最后状态并标记“正在重新连接”；
- 恢复网络后立即校准服务端时间；
- `onShareAppMessage` 返回批次标题、分享图和带 `batchId` 的页面路径。

页面提供自定义“分享拍卖”按钮（`open-type="share"`），同时支持右上角菜单转发。分享卡片只是入口，出价权限始终由 API 校验。

## 9. 管理后台设计

现有拍卖编辑器增加“出价方式”选择：

- 微信群出价：说明成员在群里发送纯数字；
- 小程序出价：说明成员点击小程序卡片进入大厅。

详情页根据渠道调整文案和报价时间列，显示报价来源。小程序模式显示：

- “打开小程序拍卖大厅”的路径说明；
- 当前服务端状态；
- 开始、暂停、继续、取消按钮；
- Bridge 离线警告仅提示“群通知不可用，拍卖仍继续”，不显示为拍卖故障。

微信群模式保持现有恢复语义和文案。

## 10. 群机器人兼容性

- `WECHAT_GROUP` 批次完全沿用现有纯数字报价逻辑和回复格式；
- `MINIPROGRAM` 批次收到群内纯数字时不记为报价，机器人回复一次简短说明：“本批次请点击小程序拍卖大厅出价。”并应用现有频率限制，避免刷屏；
- 两种模式都支持管理员群内控制命令；
- 两种模式都可发送结果通知；
- 只有 `WECHAT_GROUP` 模式因 Bridge 不可用进入恢复流程；
- 群查询赛程、绑定身份、多群多能力配置完全不变。

## 11. 错误与降级

- API 不可用：小程序显示重连状态，禁止盲目提交；服务恢复后以数据库状态为准；
- 用户重复点击：幂等键保证只产生一次报价；
- 用户无球队或球队退出：立即禁止出价；
- 批次链接错误或无访问权：返回统一不可用页面，不泄露其他联赛信息；
- 页面停留在旧球员：`lotId + deadlineEpoch` 阻止误投；
- Bridge 离线：小程序模式继续，后台和小程序提示群通知不可用；
- 小程序模式群通知积压：过期倒计时不补发，只保留成交、下一位和完成等可理解事件；
- 管理员并发操作：`expectedVersion` 冲突时刷新状态并要求重新确认；
- 批次取消：所有尚未结束拍品进入 `VOID`，小程序停止报价并展示取消状态。

## 12. 安全与隐私

- 所有出价接口必须登录；
- 权限基于服务端 `User → LeagueTeam` 关系，不信任客户端传入的球队 ID；
- 金额只接受正整数且不超过现有上限；
- 日志记录请求 ID、批次、拍品、用户和裁定，不记录 access token；
- 小程序只展示球队名称，不展示其他用户微信资料；
- 分享卡片不能授予权限，知道 `batchId` 也不能跨联赛出价；
- 管理员操作和人工审核继续写审计日志；
- 测试环境与正式环境使用不同 API 域名和数据，不在小程序包中放置服务密钥。

## 13. 测试与验收

### 13.1 单元测试

- 合同 schema：渠道、状态、详情和报价请求/响应；
- 报价服务：起拍价、最低加价、有效报价、过期、旧 epoch、幂等和权限；
- 并发：两支球队同时出价只有确定的最高价；
- worker：两种渠道都自动推进，小程序模式不依赖群通知；
- recovery：Bridge 离线只暂停微信群模式；
- 小程序 ViewModel：倒计时校准、最低有效价、状态文案、分享路径和断网恢复；
- 管理后台：渠道选择和控制按钮状态。

### 13.2 API 端到端测试

- 用户登录后读取自己联赛拍卖；
- 其他联赛用户不能读取完整房间或出价；
- 多联赛同时活动互不干扰；
- 同一联赛第二个批次不能准备或开始；
- 小程序有效报价重置 30 秒；
- 旧页面报价不能落到下一位；
- 同一幂等键重试只生成一条记录；
- 成交、流拍、自动下一位、最终完成和人工审核；
- 现有微信群拍卖 E2E 全部继续通过。

### 13.3 体验版真机验收

至少使用一个管理员和两名球队负责人的真实微信号：

1. 将测试者添加为体验成员；
2. 上传并设置体验版；
3. 管理员分享批次卡片到测试群；
4. 两台手机同时打开并交替报价；
5. 验证有效报价后两端在下一次同步内更新并重置 30 秒；
6. 验证切后台、锁屏、断网和恢复；
7. 验证两个联赛同时拍卖；
8. 关闭 Windows Bridge，确认小程序拍卖继续；
9. 恢复 Bridge，确认后续结果通知可继续发送；
10. 完成后台人工审核，确认资金和阵容没有自动变化。

## 14. 迁移与发布

1. 数据库新增渠道和通用报价来源字段，已有批次与报价回填为微信群模式；
2. API 先兼容新旧数据并保持现有机器人测试通过；
3. 管理后台增加渠道选择和控制按钮；
4. 小程序增加列表、房间、分享和出价；
5. 在测试 API 域名上进行体验版真机验收；
6. 小程序代码审核通过后发布正式版；
7. 日常新增批次、球员和价格只写后台数据，不再触发小程序代码审核。

首批正式拍卖保留微信群模式作为备用，但一个具体批次在开始前就固定出价渠道，不能运行中切换。

## 15. 完成定义

- 当前分支所有原有群机器人、API、后台和小程序测试继续通过；
- 新增迁移可从现有数据库安全升级；
- 管理员可创建两种模式的批次并直接控制状态；
- 小程序体验版可以通过群卡片进入指定批次；
- 两部手机可以完成完整竞价、自动推进和流拍流程；
- 多联赛并发、同联赛单活动批次约束有效；
- Bridge 离线不会中断小程序模式；
- 所有结果仍需管理员人工审核且不产生资金或阵容副作用。
