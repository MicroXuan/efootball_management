# 普通微信群机器人与球员拍卖设计

**日期：** 2026-10-09  
**状态：** 已完成会话设计确认，待书面规格审阅  
**产品范围：** 普通微信群接入、账号绑定、赛程查询与人工审核型球员拍卖  
**关联设计：**

- [个人赛事闭环设计](./2026-09-25-individual-competition-loop-design.zh-CN.md)
- [联赛、赛季、分组与杯赛体系设计](./2026-09-26-league-season-pyramid-design.zh-CN.md)

## 1. 目标

球队负责人目前主要在普通个人微信群中运营联赛。本功能在不要求成员迁移到企业微信的前提下，把现有 eFootball 管理系统接入一个长期在线的 Windows 微信机器人账号，使群成员可以：

- 在绑定联赛的微信群中查询已配置赛事的公开赛程；
- 查询与自己球队有关的赛程；
- 由管理员预先配置球员拍卖批次；
- 在群内通过纯数字消息竞价；
- 由服务端执行可恢复的 30 秒倒计时和成交判定；
- 成交后由管理员人工审核并手动完成后续资金、阵容操作。

成功标准：

- 普通微信群消息可以可靠地去重、识别群和发送者并进入现有 NestJS API；
- 一个微信群只绑定一个联赛，数据不会跨群或跨联赛泄漏；
- 微信联系人可以通过小程序一次性验证码绑定现有用户，无需重新注册；
- 拍卖状态不以 Windows 进程内存或微信群消息是否成功发出为准；
- 有效报价原子写入并把截止时间重置为 30 秒；
- 微信、Bridge 或 API 异常时系统保守暂停，不猜测成交结果；
- 首版不自动扣款、不自动加入阵容，只产生待人工审核的拍卖结果；
- 自动化仅用于获得授权的白名单群，并尽量减少发送频率和账号风险。

## 2. 约束与关键决定

### 2.1 微信接入边界

普通个人微信群没有满足本场景的官方双向机器人接口。部署方提供一台长期在线、登录专用机器人微信号的 Windows 10/11 电脑。

Windows 侧采用轻量 Bridge，而不是把拍卖业务放到微信电脑上。Bridge 以 `wechatauto-replica` 的微信 4.x 本地数据库读取能力为基础，发送使用可校验的桌面 GUI 操作。首期在目标电脑上固定并验收微信 4.1.15.13；任何升级必须先通过兼容性验收。

Bridge 不承担业务权威状态，不使用 DLL Hook、非官方网络协议、自动加好友、自动拉群或批量营销能力。接收侧只读白名单群和机器人私聊中的绑定命令；发送侧串行操作微信窗口，发送前确认目标群，发送后从本地数据库读回确认。

### 2.2 联赛与赛程来源

一个微信群只绑定一个 `League`。当前仓库尚未实现长期联赛的分级赛程，已经可用的赛程来自现有 `Competition` 和已发布的 `CompetitionStage`。

首版由管理员为群选择一个或多个现有 `Competition` 作为赛程来源。`查询赛程` 和 `我的赛程` 只读取这些来源的已发布比赛。未来联赛分组赛程落地后，查询服务改为读取联赛当前赛季下的竞赛容器，微信群命令和返回格式保持兼容。

### 2.3 身份绑定

业务身份继续使用现有小程序用户及其 `LeagueTeam`。微信 PC 本地群成员标识不能自动转换为小程序的 `wechatOpenId`，因此拍卖前必须建立一次身份映射。

用户在小程序点击“绑定群机器人”，系统生成 5 分钟有效、只能使用一次的验证码。用户私聊机器人发送 `绑定 123456`。验证成功后，服务端把机器人账号作用域下的微信联系人标识映射到当前小程序用户。绑定持续有效，直到用户主动解绑、管理员撤销或机器人账号更换。

公开的 `查询赛程` 不要求绑定；`我的赛程`、出价和管理员群命令要求绑定。

### 2.4 拍卖业务边界

管理员在现有管理后台创建拍卖批次，选择球员、安排顺序，并为每名球员单独设置起拍价和最小加价。管理员在群里发送 `开始拍卖` 启动已准备批次。

拍卖只记录出价和产生待审核结果，不校验球队余额或阵容规则，不写入财务流水，不创建阵容交易。管理员在后台人工审核成交，然后使用现有管理能力手动处理资金和阵容。

每名球员结束后系统等待管理员发送 `下一位`，不会自动开始下一个拍品。

## 3. 总体架构

```text
普通微信群
    │ 本地微信消息
    ▼
Windows Bridge
    │ HTTPS/WSS：入站事件、心跳、发送确认
    ▼
NestJS API
    ├── 微信设备、群与身份绑定
    ├── 命令路由和赛程查询
    ├── 拍卖状态机与截止时间 worker
    ├── MySQL 权威状态
    └── 数据库消息发件箱
    │ 待发送任务
    ▼
Windows Bridge
    │ 串行 GUI 发送并读回确认
    ▼
普通微信群
```

### 3.1 Windows Bridge

Bridge 是独立的 Windows 常驻进程，职责限定为：

- 检测微信进程、登录状态、目标版本、屏幕锁定状态和本地数据库可用性；
- 从微信本地数据库按稳定水位增量读取白名单群消息；
- 解析稳定消息 ID、群 ID、发送者微信标识、消息时间、类型和文本；
- 只上传白名单群的文本消息，以及机器人私聊中的绑定命令；
- 通过出站 WSS 或短轮询取得待发送任务；
- 串行打开目标会话、核对群名、粘贴文本、发送并读回确认；
- 本地持久化尚未被 API 确认的入站事件和发送确认；
- 定期发送设备、微信登录、监听水位和发送队列心跳；
- 在不确定目标窗口或连续失败时停止发送并报告故障。

Bridge 只主动连接服务端，不要求从公网开放 Windows 入站端口。设备凭证按机器人设备签发，可以撤销和轮换。

### 3.2 NestJS API

API 是唯一业务权威，职责包括：

- 验证 Bridge 设备身份及消息签名；
- 按微信稳定消息 ID 幂等接收入站事件；
- 解析命令并校验群、联赛、绑定用户和权限；
- 查询管理员选择的现有赛事赛程；
- 创建和消费绑定验证码；
- 管理拍卖批次、拍品、报价、截止时间和人工审核结果；
- 使用数据库事务串行处理同一活动拍品的并发出价；
- 由数据库时间驱动倒计时和关闭判定；
- 把所有微信回复写入数据库发件箱；
- 根据 Bridge 心跳执行自动暂停、恢复保护和熔断；
- 为管理员操作、报价、状态变化和发送失败保留审计记录。

首版不引入 Redis 或独立消息队列。MySQL 中的权威状态、入站去重表和发件箱已经足以支持单 API 部署和恢复；未来只有在多实例吞吐需要时才增加外部队列。

### 3.3 管理后台

现有后台新增“微信群机器人”功能区：

- 设备状态：Bridge 在线、微信登录、客户端版本、最后心跳、监听水位、发送队列和熔断原因；
- 群绑定：选择联赛、记录稳定群 ID 和显示名称、启停白名单；
- 赛程来源：为群选择一个或多个现有赛事；
- 拍卖批次：创建、编辑、排序、准备、取消和查看状态；
- 拍品配置：球员、起拍价、最小加价和顺序；
- 成交审核：确认、修改获胜方或价格、判定流拍、记录审核原因；
- 消息与审计：查看业务事件、发送结果和故障，不展示无关聊天内容；
- 总开关：立即暂停指定设备或全部自动发送。

## 4. 数据模型

名称为设计语义，实施计划可在不改变边界的前提下按仓库命名规范调整。

### 4.1 微信接入

`WechatBotDevice`

- 设备 ID、名称和凭证摘要；
- 机器人微信账号稳定标识；
- 状态、微信版本、最后心跳和最后监听水位；
- 熔断状态、原因和恢复时间；
- 创建、撤销和更新时间。

`WechatGroupBinding`

- 设备、稳定群 ID 和群名快照；
- 唯一绑定的 `leagueId`；
- 是否启用和最后确认时间；
- 乐观版本和审计时间。

同一设备下稳定群 ID 唯一；首版一个群只能绑定一个联赛。

`WechatGroupScheduleSource`

- 群绑定 ID 和 `competitionId`；
- 显示顺序和是否启用；
- 创建人和时间。

只允许选择可读取的赛事。查询时仍由赛程服务限制为已发布阶段。

`WechatIdentityBinding`

- 设备、微信联系人稳定标识和 `userId`；
- 绑定状态、绑定和解绑时间；
- 创建方式和撤销原因。

一个设备内微信联系人只能有一个有效用户绑定；一个用户在同一设备内也只能有一个有效微信联系人绑定。

`WechatBindingCode`

- 哈希后的验证码、用户、用途、过期时间；
- 使用时间、使用设备和微信联系人标识；
- 创建时间。

数据库不保存可重放的明文验证码。创建新验证码会使该用户尚未使用的旧码失效。

`WechatInboundMessage`

- 设备、稳定消息 ID、群或私聊标识、发送者标识；
- 微信消息时间、服务端接收时间、消息类型；
- 允许处理的命令文本；
- 处理状态、结果代码和关联业务实体；
- 创建和处理时间。

设备和稳定消息 ID 构成唯一约束。白名单之外以及非命令普通聊天不上传。

`WechatOutboxMessage`

- 目标设备、群或私聊标识；
- 业务幂等键、文本内容和优先级；
- 计划发送时间、领取租约、尝试次数和状态；
- Bridge 确认、读回消息 ID、失败原因和时间。

业务幂等键唯一，防止 worker 重启或 Bridge 重试产生重复消息。

### 4.2 拍卖

`PlayerAuctionBatch`

- 联赛、群绑定、名称和批次序号；
- 状态：`DRAFT`、`READY`、`ACTIVE`、`PAUSED`、`COMPLETED`、`CANCELLED`、`RECOVERY_REQUIRED`；
- 当前拍品、创建和启动管理员；
- 版本、开始、完成和取消时间。

一个群同时最多有一个 `ACTIVE`、`PAUSED` 或 `RECOVERY_REQUIRED` 批次。

`PlayerAuctionLot`

- 批次、球员或球员卡引用、顺序；
- 球员名称和展示信息快照；
- 起拍价、最小加价；
- 状态：`QUEUED`、`ACTIVE`、`PAUSED`、`PENDING_REVIEW`、`REVIEWED`、`VOID`、`NO_BID`；
- 当前最高价、最高报价和服务端截止时间；
- 暂停时剩余毫秒数；
- 启动、关闭和审核时间；
- 乐观版本。

`PlayerAuctionBid`

- 拍品、联赛球队、用户和微信身份绑定；
- 报价、微信消息 ID 和微信消息时间；
- 服务端接收时间、处理顺序和结果；
- 拒绝原因或成为最高报价的时间。

所有纯数字出价都可形成审计记录；只有有效报价更新拍品最高价和截止时间。

`PlayerAuctionReview`

- 拍品；
- 机器人计算的获胜球队和成交价；
- 管理员确认后的球队和价格，或流拍、作废决定；
- 审核管理员、原因和时间。

审核只确认拍卖记录，不创建 `RosterTransaction` 或 `FinanceLedgerEntry`。

## 5. 命令与权限

| 输入 | 适用位置 | 身份要求 | 行为 |
| --- | --- | --- | --- |
| `绑定 123456` | 私聊机器人 | 有效绑定码 | 绑定当前微信身份与小程序用户 |
| `帮助` | 白名单群 | 无 | 显示当前可用命令 |
| `查询赛程` | 白名单群 | 无 | 返回配置赛程来源中的未完成公开比赛 |
| `我的赛程` | 白名单群 | 已绑定且拥有该联赛球队 | 返回与该球队或用户关联的未完成比赛 |
| `开始拍卖` | 白名单群 | 已绑定联赛管理员 | 启动该群唯一已准备批次的首个拍品 |
| `暂停拍卖` | 白名单群 | 已绑定联赛管理员 | 冻结当前拍品剩余时间 |
| `继续拍卖` | 白名单群 | 已绑定联赛管理员 | 从冻结的剩余时间继续 |
| `下一位` | 白名单群 | 已绑定联赛管理员 | 在上一拍品关闭后启动下一拍品 |
| `取消拍卖` | 白名单群 | 已绑定联赛管理员 | 取消批次，保留已关闭结果和审计 |
| 纯十进制整数 | 白名单群 | 已绑定且拥有该联赛球队 | 对当前活动拍品出价 |

管理员群命令沿用现有联赛作用域权限，不根据群昵称或微信昵称授予权限。命令忽略首尾空白，首版不使用自然语言或大模型做意图识别。

## 6. 赛程查询

`查询赛程`：

1. 根据稳定群 ID 找到群绑定；
2. 读取启用的赛程来源；
3. 只查询已发布阶段且赛事未取消的比赛；
4. 优先展示未完成、有计划时间的比赛，再展示未安排时间的比赛；
5. 按赛事分组输出，内容超出单条限制时分页并进入发送队列；
6. 没有来源或没有未完成比赛时返回明确提示。

`我的赛程` 额外要求身份绑定。首版对现有个人赛事按 `individualUserId` 匹配；未来联赛赛程按 `LeagueTeam` 或 `SeasonEntry` 匹配。返回内容包括赛事、轮次、双方、计划时间、状态和已确认比分。

查询命令只读，不修改赛事状态。

## 7. 拍卖状态与报价规则

### 7.1 启动批次

管理员在后台把完整批次标记为 `READY`。系统验证：

- 群和联赛仍启用；
- 至少有一个拍品；
- 每个拍品拥有有效球员引用、正整数起拍价和正整数最小加价；
- 同一群不存在其他未结束批次。

群内 `开始拍卖` 将批次和首个拍品原子切换为活动状态，并发送本批次队列摘要和首个拍品信息。

首个拍品示例：

```text
提名拍卖：第37名球员拍卖开始！
************************
球员信息：【CF⭐车范根（Cha Bum-Kun），国籍，身高179cm，年龄33岁，惯用右脚，薪资500，综合能力评分96。】
提名者：49-上海申花-蜜酥
起拍价：⭐50⭐
最小加价：⭐10⭐
************************
请在 30 秒内发送纯数字出价，以机器人确认消息和服务端计时为准。
```

### 7.2 报价判定

在数据库事务和活动拍品行锁中依次验证：

- 入站消息未处理过；
- 消息来自该拍品所属群；
- 拍品处于 `ACTIVE`；
- 消息发生在当前有效截止时间之前；
- 微信身份已绑定启用用户；
- 用户拥有该联赛的活动球队；
- 首次报价不低于起拍价；
- 后续报价至少为当前最高价加最小加价；
- 报价为数据模型允许范围内的正整数。

不验证球队余额、工资帽、阵容容量或球员是否适配。有效报价写入后将截止时间设置为数据库当前时间加 30 秒，并回复：

```text
【球队名称】出价有效：⭐120⭐，倒计时重置为 30 秒。
```

无效报价不改变最高价和截止时间，返回简短明确的原因。相同微信时间的消息使用微信稳定排序字段和消息 ID 决定顺序，不依赖 Bridge 到达顺序。

### 7.3 倒计时与关闭

服务端 worker 按数据库截止时间生成 `30、20、10、5、4、3、2、1` 提示。倒计时提示是展示事件，不是状态权威。有效报价与倒计时任务并发时，发送前再次检查拍品版本和截止时间；属于旧截止时间的提示直接取消。

发送队列拥堵或报价密集时可以省略中间倒计时，只保留有效报价、临近结束提示和最终结果。任何提示延迟都不移动服务端截止时间。

截止时 worker 锁定拍品并再次确认没有更晚的有效报价：

- 有最高报价：状态改为 `PENDING_REVIEW`，保存机器人计算结果并宣布待管理员审核；
- 无报价：状态改为 `NO_BID` 并宣布流拍。

批次随后等待管理员发送 `下一位`。最后一个拍品结束后批次变为 `COMPLETED`。

### 7.4 暂停与恢复

人工暂停保存剩余时间并清空活动截止时间。恢复时以数据库当前时间加剩余时间生成新截止时间。暂停期间的普通数字消息记录为无效，不改变结果。

系统异常恢复采用第 8 节的保守状态，不直接等同于人工暂停。

## 8. 异常恢复与一致性

### 8.1 Bridge 断线

Bridge 心跳超过配置阈值后，API 原子地把活动批次改为 `RECOVERY_REQUIRED`，记录检测时间并冻结剩余时间。此时不能继续出价或自动成交。

Bridge 恢复后按持久水位补传消息。系统按微信消息时间和稳定排序字段重放断线检测时间之前的消息；符合当时活动窗口的有效报价更新恢复上下文。断线检测时间之后的报价不自动接受。管理员在后台查看恢复摘要后发送 `继续拍卖`，系统以恢复后的最高报价和完整 30 秒重新开始，避免群成员在不知道机器人掉线时失去公平竞价机会。

### 8.2 API 或数据库重启

进程内定时器不是权威。启动扫描发现截止时间已经过去但缺少已提交关闭事件时，将相关批次置为 `RECOVERY_REQUIRED`，而不是直接成交。入站缓冲重放完毕后由管理员确认继续或人工结束。

### 8.3 重复与乱序

- 入站唯一约束保证同一微信消息只处理一次；
- Bridge 必须等待 API 持久化确认后才能推进本地确认水位；
- 同一拍品的报价在数据库行锁中串行处理；
- 业务事件和发件箱使用唯一幂等键；
- Bridge 发送确认包含任务 ID 和读回微信消息 ID；
- 已确认发送任务不因连接重建再次发送。

### 8.4 发送失败

发送失败不回滚已经提交的报价或成交状态。发件箱采用有上限的退避重试。发送前必须再次确认群 ID、当前聊天标题和任务是否仍有效；发送后必须读回。连续失败、目标不确定、微信退出或屏幕锁定触发设备熔断。

熔断期间 API 保留发件箱和业务状态，并自动把活动拍卖置为 `RECOVERY_REQUIRED`。只有管理员明确恢复设备后才重新发送仍然有效的高优先级消息。过期倒计时不会补发。

## 9. 风控、隐私与安全

个人微信自动化不存在零风险保证。本设计通过限制能力和频率降低风险，不承诺规避微信的平台控制。

- 使用明确标识的专用机器人账号和获得成员知情的白名单群；
- 首期只开放一个测试群，通过完整验收后再逐群启用；
- 不进行主动营销、陌生人私聊、自动加好友、拉群或批量转发；
- 不使用非官方协议登录、DLL Hook 或无限重试；
- 发送单线程串行执行，并允许降级省略非关键倒计时；
- 为单群、单设备配置发送速率、队列长度和连续失败阈值；
- 提供设备级和全局立即停止开关；
- Windows 关闭睡眠但保持系统安全更新；微信客户端关闭自动更新并在升级前验收；
- 设备凭证和验证码只保存不可逆摘要，支持撤销和轮换；
- Bridge 到 API 使用 TLS，拒绝过期时间戳和重复请求；
- 只上传业务命令所需的最小消息字段，不上传白名单外聊天；
- 对命令正文设置短期保留策略，报价和管理员审计按联赛记录要求保留；
- 日志隐藏设备密钥、验证码、完整 OpenID 和无关聊天内容。

## 10. 测试与验收

### 10.1 自动化测试

- 命令解析：空白、全角字符、纯数字边界和普通聊天忽略；
- 绑定码：生成、哈希、过期、单次消费、并发消费、解绑和冒用拦截；
- 群隔离：错误设备、错误群、停用群和跨联赛数据拒绝；
- 赛程查询：多个来源、未发布赛事、取消赛事、排序、分页和本人过滤；
- 拍卖状态机：准备、开始、人工暂停、恢复、下一位、取消和全部完成；
- 报价规则：首次报价、最小加价、多人同秒报价、重复消息和超时报价；
- 每名球员独立起拍价和最小加价；
- 有效报价重置 30 秒，无效报价不重置；
- 旧倒计时任务在报价后失效；
- 有报价待审核、无人报价流拍、审核修改和作废；
- 断线补传、API 重启、乱序、出站重试、发送确认和熔断；
- 成交审核不会创建财务流水或阵容交易。

### 10.2 Windows 合同测试

- 目标微信版本和 Python/Bridge 运行环境预检；
- 从测试群读取稳定群 ID、发送者标识、消息 ID 和时间；
- 同一条消息重复扫描不会重复上传；
- Bridge 重启后从持久水位补传；
- 能唯一解析群成员微信标识用于绑定；
- 发送前正确选择并核对群；
- 发送后能读回相同文本并取得微信消息 ID；
- 锁屏、微信退出、群名不匹配和网络断开时安全失败；
- 连续运行、微信重启和 API 重连不会丢失已确认水位。

### 10.3 真实群验收

1. 使用机器人小号和测试群；
2. 两名以上用户通过小程序验证码绑定；
3. 配置现有赛事并验证公开赛程与本人赛程；
4. 创建至少三名球员的拍卖批次，每名球员使用不同起拍价和最小加价；
5. 验证有效、无效、同秒和临界截止报价；
6. 验证暂停、继续、下一位、流拍和人工审核；
7. 在活动拍卖中断开 Bridge，验证自动进入恢复状态和补传；
8. 验证所有结果未自动修改球队资金和阵容；
9. 观察一个完整联赛活动周期的发送失败、账号异常和人工暂停情况；
10. 管理员签字确认后才允许增加白名单群。

## 11. 发布顺序

本功能作为一个产品设计、按可独立验收的实施阶段交付：

1. 微信领域模型、Bridge 协议、设备心跳和发件箱；
2. Windows Bridge 的读消息、去重、发送和读回；
3. 小程序绑定入口和私聊绑定命令；
4. 群绑定、赛程来源和赛程查询；
5. 拍卖数据模型、后台配置和状态机；
6. 群内竞价、倒计时、人工审核和异常恢复；
7. Windows 实机验收、测试群试运行和受控上线。

每一阶段都必须保持现有 API、小程序和管理后台可构建、可测试。Windows 实机能力未通过前，生产群发送总开关保持关闭。

## 12. 首版明确不做

- 企业微信、公众号或微信客服接入；
- AI 对话、自然语言意图识别、RAG 或群聊摘要；
- 自动扣款、工资帽校验、阵容容量校验或自动加入球员；
- 自动开始下一名球员；
- 自动加好友、拉群、踢人、修改群公告或群发营销；
- 图片识别出价、语音出价或撤回消息反向修改报价；
- 联赛超级组、冠军组和杯赛赛程体系本身；
- 多机器人账号负载均衡或 Redis 集群；
- 对任何形式的零风控、零封号保证。

## 13. 后续演进

- 联赛分级赛程实现后，把群赛程来源从人工选择的 `Competition` 切换为联赛当前赛季的竞赛集合；
- 在管理员审核成交时提供可选的现有阵容交易草稿，但仍要求人工确认；
- 支持一个 Bridge 管理多个机器人账号，但每个账号保持独立凭证、水位和发送队列；
- 对稳定运行数据建立消息成功率、Bridge 在线率、熔断次数和恢复时长指标；
- 微信版本升级时通过可替换的 `WechatTransport` 适配器迁移底层实现，不改变 API 领域模型。
