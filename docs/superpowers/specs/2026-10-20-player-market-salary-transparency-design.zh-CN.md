# 球员市场工资透明化设计

**日期：** 2026-10-20

**状态：** 待书面确认

**范围：** 联赛内球员市场详情、申请确认区、详情 API 契约与工资报价一致性；市场列表移除工资展示

## 1. 目的与业务口径

参赛球队需要在联赛内的球员详情页、申请购买或强报前看清一名球员将占用多少工资帽。不同联赛有各自的工资档位，因此市场列表和联赛外的通用球员卡均不展示工资。工资是工资帽占用，不是按期从资金余额扣除的现金费用；购买或强报金额与工资分开展示。成功标准是详情展示的工资有明确联赛来源，且与最终成交的定薪规则一致，用户能在申请前看到本队工资帽的预计变化。

已归属球员以阵容保存的**实际工资**为主。若该工资与现行档位金额不同，另列**现行档位价**供解释，不静默改写实际工资。自由球员展示**预计签入工资**，依据所选球员卡的完整自动加点总评和联赛当前生效规则计算。所有金额继续使用系统现有的整数金额单位，不引入现金结算功能。

## 2. 当前实现与问题

- 球员市场列表已有 `card.salaryMinor`，页面统一称作“参考工资”。这个列表标签需要移除；工资只在带联赛和赛季上下文的球员详情中展示。
- 球员详情没有突出展示工资和工资帽影响，用户在提交申请前只能看到官方身价与报价输入。
- 市场有独立的档位匹配逻辑；购买审核通过时使用 `SalaryRulesService.quoteWithClient`，强报则沿用原阵容工资。两个报价路径需要共享同一规则选择与档位计算口径。
- 市场的兜底球员卡在没有持久化自动加点结果时会推导总评或退回初始总评；这样的值不能作为可靠的工资报价依据。普通购买审核在没有自动加点结果时也不会成交。

## 3. 方案选择

采用**服务端按联赛统一提供工资金额及来源**。小程序只在联赛内球员详情展示工资，不下载档位规则后自行计算。继续使用已有 `LeagueSalaryRuleVersion`、`LeagueSalaryTier` 和 `LeaguePlayerOwnership`，不新增工资账本或数据库列。

没有采用小程序本地套档位，因为规则切换、卡片状态和审核时点可能让展示与成交不一致。没有新增独立工资账本，因为阵容的工资、总评和规则版本快照已记录实际占用；本次需求是让其在市场可见且可解释。

## 4. 金额定义

| 球员状态 | 主金额 | 来源 | 现行档位价 |
|---|---|---|---|
| 自由球员 | 预计签入工资 | 所选卡最新完整自动加点结果的 `maxOverall`，按当前生效规则报价 | 与主金额相同，不重复展示 |
| 其他球队已归属 | 实际工资，也是强报预计占用 | 有效归属的 `salaryMinor` 快照 | 使用归属的 `maxOverallSnapshot` 按当前生效规则计算；不改变主金额 |
| 本队已归属 | 实际工资 | 本队有效归属的 `salaryMinor` 快照 | 同上 |

“现行档位价”只在与实际工资不同且可以计算时展示。比较时使用归属总评快照，不使用球员卡最新总评，避免把卡片数据变化误解释为工资规则变化。显示档位范围和规则版本或生效时间，帮助用户理解差异。若现行规则不存在，仍显示已归属球员的实际工资，并说明当前没有可用档位价。

自由球员必须有与市场展示卡片一致的持久化完整自动加点结果，才能显示预计工资。没有结果、没有生效规则或规则未覆盖总评时，金额为不可报价状态并说明原因；不使用 `overallRating`、临时推导总评或零元代替。市场卡片仍可展示球员资料，但不可把缺少可靠工资的卡片描述为可确认的签入成本。申请与审核阶段的现有服务端校验继续生效。

## 5. API 与数据流

### 5.1 报价服务

由服务端一个只读工资报价入口选择当前联赛生效规则并匹配档位；联赛内球员详情和普通购买审核复用相同的规则选择及匹配函数。规则按 `effectiveAt <= 当前时间` 选择最近生效版本，并在同一时点内以版本号决胜。报价结果包含金额、依据总评、命中档位范围、规则版本 ID 与版本号。无有效规则、无自动加点结果、未覆盖总评分别返回可供页面展示的原因，不伪造工资金额。

交易审核仍在数据库事务中重新报价。市场只读报价不锁定工资规则，也不保证未来审核时金额不变。

### 5.2 联赛球员详情响应

仅在需要 `leagueId`、`seasonId` 和 `playerId` 的球员市场详情响应中新增明确的工资展示结构，至少包含：

- `kind`：`ACTUAL`、`PROJECTED` 或 `UNAVAILABLE`；
- `salaryMinor`：主金额或 `null`；
- `basisOverall`：计算依据总评或 `null`；
- `salaryRuleVersionId`：报价引用的规则版本 ID，实际工资使用归属快照版本；
- `currentTier`：已归属球员按现行规则计算的金额、档位总评范围、规则版本 ID、版本号和生效时间；不可计算时为 `null`；
- `unavailableReason`：仅不可报价时提供的明确原因。

保留已有 `card.salaryMinor` 作为兼容字段，在新旧客户端共存期与详情主金额一致；新页面只读取明确的展示结构。契约测试保证详情中两个字段不会出现冲突。市场列表沿用现有响应契约，不新增工资展示结构；小程序列表不再渲染其工资字段。详情使用请求中的联赛 ID 查询该联赛规则和球员归属，不能使用其他联赛的报价。联赛外通用球员卡不请求或展示此结构。

### 5.3 本队工资帽影响

市场详情为当前参赛球队返回当前有效阵容工资总额、球队工资帽和预计交易后总额：

- 普通购买：当前总额 + 所选自由球员预计签入工资。
- 强报：当前总额 + 原归属的实际工资，符合强报沿用工资快照的现行规则。
- 本队球员或无法报价：不显示交易后金额。
- 工资帽未设置：明确显示“待管理员设置”，不把 `null` 当作 0。

若预计超帽，显示超出金额和“审核时可能无法成交”。不改变当前申请提交资格规则；最终审核仍会检查工资帽、阵容人数、卡片、规则和归属。详情在进入页面、返回页面及申请操作后刷新；页面注明“以审核时结果为准”。

## 6. 小程序展示

- 球员市场列表：移除现有“参考工资”，只展示球员资料、官方身价、归属和操作状态。
- 联赛内球员详情：在官方身价旁独立展示工资及依据。自由球员标“预计签入工资”，已归属球员标“实际工资”；如果现行档位价不同，展示差额和说明“强报沿用实际工资”。无报价显示具体原因，避免“未记录”这种模糊文案。
- 联赛外通用球员卡及其详情不展示工资，也不调用联赛工资报价接口。球队资产等现有联赛内阵容工资展示保持原有入口。
- 申请确认区：在报价输入之外展示“当前工资占用 / 工资帽 → 预计占用”和超帽提示。交易报价仍明确是购买或强报金额，不与工资混用。
- 对窄屏与常见手机宽度检查金额换行、长文案、按钮和卡片边界；新增或修改原生按钮时在微信开发者工具检查正常态与禁用态的文字居中和裁切。

## 7. 一致性、错误与边界

- 工资规则发布不自动改变已归属球员的实际工资。只有现有工资重算或其他明确的阵容操作会改变快照。
- 强报成交原样转移卡片、总评、规则版本和工资；现行档位价仅供比较。
- 申请提交后规则、球员卡、归属或球队工资帽可能变化。用户看到的是读取时点的预估，审核重新校验并以成交后的归属快照为实际金额。
- 自由球员缺少自动加点结果时不展示工资数字；审核的 `PLAYER_BUILD_REQUIRED` 等原因应映射为易懂提示。
- 页面不显示任何工资为现金扣款或余额支出的暗示；官方身价、申请/成交金额、工资占用使用不同标签。
- 不批量重算历史阵容，不改写既有交易或财务记录。

## 8. 验收与回归

1. 自由球员总评落在档位边界时，市场预计工资与 `SalaryRulesService` 审核报价一致；无有效规则或无完整自动加点结果时不展示虚假金额。
2. 已归属球员的实际工资取快照；新规则档位不同只产生现行档位价提示。强报预计占用和成交后占用仍为原工资。
3. 球队当前工资、工资帽、预计占用和超帽差额计算正确；工资帽为空时不当作零。
4. 申请后规则、归属或工资帽变化时，审核仍按事务内实时数据校验并返回可理解的结果。
5. 市场列表及联赛外球员卡均不出现工资；联赛内详情、申请确认、管理端申请审核、球队资产与现有阵容工资展示互相核对。分别用两个工资档位不同的联赛验证同一球员详情显示各自联赛的金额。复测后台联赛球队列表“现役球队 / 已退出”、球队详情及小程序“我的联赛”。
6. 小程序在窄屏和常见手机宽度检查卡片与按钮边界；涉及按钮改动时在微信开发者工具预览正常态和禁用态。
7. 部署前核对目标环境 API 响应与小程序解析。若目标环境无法验证，交付时明确列出未验收范围；不得以本地单元测试代替目标环境验收。

API 单元或端到端测试只连接显式指定的本机隔离数据库，数据库名包含 `test` 或 `verify`。测试生成的持久化数据须自动清理并复查；不得从项目 `.env` 继承共享数据库连接。
