# 后台联赛导航收口与独立强报期设计

日期：2026-10-20

## 目标与已确认规则

后台联赛工作区目前将十余个业务页面平铺为一级横向标签，入口拥挤，后续新增模块还会加重溢出。目标是减少一级入口、缩小标签间距，同时保留清楚的功能归属和现有页面地址。管理员需要在后台为每个赛季设置独立起止时间的强报期；强报不受转会窗口控制，普通购买和协商转会仍遵循各自原有的转会窗口规则。

一个赛季可有多个互不重叠的强报期。截止时间只禁止新提交与修改报价；已提交申请保留，管理员可在截止后审核，用户仍可撤回。不同强报期对同一球员的有效申请使用同一队列，按首次有效提交时间排序，跨期不清空或重排。

## 方案取舍

采用“少量一级入口 + 组内二级导航”以及专用的强报期模型。它保留直接链接，后续增加窗口或审核类型时不必继续扩充一级横栏。

不采用继续平铺标签：只缩小间距不能解决长期扩展。不采用转会窗口中的“允许强报”开关：它无法表达与转会期完全独立的起止时间，也会让提交和审核继续依赖错误的窗口。暂不引入覆盖全部赛季阶段的通用日历/规则引擎；现有转会、身价、提名窗口仍保持各自的数据与服务边界。

## 后台导航与布局

一级导航按以下顺序呈现：用户与球队、赛季管理、分组与赛程、杯赛中心、窗口设置、审核、财务、球员拍卖；若启用微信群机器人，将其放入“更多”入口。分组与赛程、杯赛中心是两个独立一级入口，不合并为“赛事”。

“窗口设置”的二级导航为转会窗口、身价窗口、提名期、强报期、赛季日历；赛季日历按《当前赛季阶段日历设计》展示各阶段和管理员手动事项，不显示比赛。“审核”的二级导航为球员申请、身价审核、消失审核、协商转会。“财务”的二级导航为工资规则、财务与交易。球员拍卖继续独立，以免实时操作与普通审核混在一起。二级导航只在对应分组页面出现，当前项依据 URL 确定，而非仅靠组件内部状态。

保留全部已有页面 URL 与深链接。一级分组入口进入稳定的默认子页；刷新任意子页仍高亮正确的一级和二级入口。一级标签采用紧凑间距与内边距，不以压缩文字到不可读或让选中态越界为代价；窄屏使用容器内滚动或可访问的溢出菜单，不让导航越过视口。二级导航同样可键盘操作并有可见选中态。

## 强报期管理

为赛季新增 `ForcedOfferWindow`：ID、赛季 ID、名称、开始时间、截止时间、创建管理员、版本及审计时间。时间区间使用 `[startsAt, endsAt)`：开始时刻可提交，截止时刻起不可提交或改价。服务端拒绝开始时间不早于截止时间、跨赛季引用以及同一赛季任何重叠区间；相邻区间允许衔接。页面显示“未开始 / 进行中 / 已结束”，提供创建与编辑未来强报期的入口。

已开始的强报期不可追溯修改开始时间；有申请后不可缩短截止时间。允许延长截止时间，但必须继续满足不重叠约束。已有关联申请的强报期不可删除；需要新增轮次时创建新强报期。页面展示所用时区与完整起止时间，提交时由服务端决定当前状态，前端状态只作提示。

## 申请、队列与审核

新增强报申请关联强报期，不再依赖转会窗口 ID。普通购买继续关联转会窗口。服务端按申请类型分别选择并校验窗口；小程序市场列表与球员详情分别返回可购买窗口和可强报窗口，不再用同一个 `activeTransferWindowId` 决定两种按钮。无进行中的强报期时，强报按钮说明“当前不在强报期”，但普通购买不受影响；反之亦然。

提交或补价时，服务端在事务内重查当前强报期、球队资格、球员归属和报价约束。强报期结束后禁止补价，包括处于 `REQUOTE_REQUIRED` 的申请；撤回仍可用。已提交申请不因强报期结束而自动过期，管理员审核时不再以窗口已关闭为驳回条件，而要重新检查归属、球队人数、工资帽、有效身价和既有队列顺序。若截止后身价上升而原报价已不足，不能要求用户在已关闭窗口补价；审核明确判定为资格失效或驳回并写明原因，不能悬置在不可操作的补价状态。

同一赛季同一球员的强报队列跨窗口延续，按 `firstValidSubmittedAt` 和 ID 稳定排序；新轮次申请排在旧轮次尚有效申请之后。已有的同队同球员有效申请不可重复提交。审核首位成交后，按现有归属变化规则处理后续申请，不因不同轮次而改变优先级。

## 旧数据与发布兼容

数据库迁移只新增强报期及申请的可选强报期关联，将原转会窗口关联改为可选；不删除旧申请、不制造假强报期，也不写演示数据。既有普通购买继续按原规则；迁移前已提交的强报保留原时间与队列位置，允许在窗口结束后完成审核，不再被“转会窗口关闭即过期”的批处理误伤。窗口来源在服务层显式区分，不能把强报期 ID 塞进 `transferWindowId` 冒充转会窗口。

API 契约增加强报期管理与市场查询字段，强报提交使用明确的强报期 ID；服务端以申请类型校验 ID 类型和赛季。新小程序使用含窗口类型与 ID 的新版本市场契约；旧版市场契约继续服务普通购买与历史记录，旧版强报写入明确返回“需更新小程序”，不能按转会窗口偷偷接受。新强报记录不得伪装成含 `transferWindowId` 的旧记录；旧契约无法表达的记录不返回错误形状。按“数据库迁移 → 兼容 API → 新小程序发布 → 开放强报期”的顺序发布，开放前核对旧版读取行为。所有旧页面地址与普通购买接口保持可用。

## 错误与验收

强报期未开放、窗口已截止、窗口重叠、报价不足、球员归属变化、球队人数/工资帽不合格分别返回可辨认错误；前端说明原因，不使用笼统“服务器错误”。并发提交以现有锁顺序和幂等键保护，同一球员队列顺序由服务端决定。管理员操作保留版本检查和审计记录。

先用失败测试覆盖窗口边界、同赛季多轮不重叠、强报与转会期独立、截止后禁止提交/补价但保留审核/撤回、跨期队列、旧申请兼容以及资格变化。随后验证后台一级/二级导航、深链接和窄屏溢出；回归普通购买、协商转会、球员申请审核、后台现役/已退出球队列表、球队详情、小程序“我的联赛”及市场入口。数据库测试只连显式指定的本机隔离测试库；部署前按项目约束核对目标迁移状态并受控上线，不在共享数据库 seed 或清理测试数据。

本轮不重做球员市场交易规则、拍卖流程或赛季日程，不建设通用规则引擎。
