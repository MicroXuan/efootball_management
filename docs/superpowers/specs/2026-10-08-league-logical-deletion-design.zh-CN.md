# 联赛逻辑删除设计

## 背景

本地共享开发数据库长期积累了大量自动化测试和人工调试创建的联赛。现有 `League.status = ARCHIVED` 是正常业务归档状态，归档联赛仍会出现在管理后台的“已归档”页签，也应保留历史查看能力，因此不能把业务归档当作测试数据删除。

需要为联赛增加独立的逻辑删除标记。维护人员直接修改数据库字段后，被标记的联赛及其下属页面在管理后台、小程序和公开接口中均不可见，但数据库中的球队、赛季、比赛、阵容、财务和审计记录必须保留。

## 目标

- 在 `leagues` 表增加 `is_deleted` 字段。
- 维护人员可通过数据库手动隐藏或恢复联赛。
- 被逻辑删除的联赛不出现在任何联赛列表中。
- 通过已知地址访问被逻辑删除联赛及其下属资源时，不泄露其存在性，统一表现为资源不存在。
- 保留联赛及全部关联数据，不执行级联删除。
- 保留现有 `ACTIVE / ARCHIVED` 业务状态及其语义。

## 非目标

- 不在管理后台或小程序增加删除、恢复按钮。
- 不新增逻辑删除或恢复 HTTP 接口。
- 不自动判断哪些联赛是测试数据。
- 不物理删除联赛或清理关联记录。
- 不为逻辑删除增加操作者、原因或独立删除时间字段。

## 数据模型

在 Prisma `League` 模型增加：

```prisma
isDeleted Boolean @default(false) @map("is_deleted")
```

迁移在 `leagues` 表增加：

```sql
is_deleted BOOLEAN NOT NULL DEFAULT FALSE
```

默认值保证现有联赛迁移后继续正常显示，无需回填。列表索引应把 `is_deleted` 放在现有状态和时间排序字段之前，以支持常用的可见联赛查询。

现有 `updated_at` 继续表示最近一次业务更新。Prisma 写入时会维护 `@updatedAt`；维护人员直接执行 SQL 时，如需同步记录修改时间，应显式设置 `updated_at = NOW()`。

推荐的手工操作为：

```sql
UPDATE leagues
SET is_deleted = TRUE, updated_at = NOW()
WHERE id = '<league-id>';

UPDATE leagues
SET is_deleted = FALSE, updated_at = NOW()
WHERE id = '<league-id>';
```

## 可见性规则

### 列表

所有面向用户或管理员的联赛集合只返回 `is_deleted = FALSE` 的记录，包括：

- 管理后台联赛目录；
- 小程序公开联赛列表；
- 当前用户参与或管理的联赛列表；
- 管理员授权范围中用于页面导航和选择器的联赛列表。

`ACTIVE / ARCHIVED` 筛选仅在 `is_deleted = FALSE` 的集合内生效。逻辑删除记录不会进入“已归档”页签，也不计入页面数量。

### 详情和下属资源

已删除联赛的联赛详情、工作区、球队、赛季、阵容、工资规则、转会窗口、赛事、积分榜、财务、身价和审计等联赛范围页面均不可访问。

对于包含 `leagueId` 的入口，服务必须先确认联赛满足：

```text
id = requestedLeagueId AND isDeleted = false
```

不满足时统一返回现有的联赛不存在错误和 HTTP 404，不返回 403，也不暴露联赛是否曾经存在。

对于只携带 `teamId`、`seasonId`、`competitionId` 等下属资源 ID 的入口，查询必须通过关联条件排除 `league.isDeleted = true`，或在返回数据前通过统一可见性检查确认其所属联赛未删除。

### 写操作

被逻辑删除联赛不允许通过现有业务接口继续修改。创建赛季、编辑球队、阵容交易、赛程、工资、财务、身价等写操作均使用与详情读取相同的可见性检查，并以 404 终止。

逻辑删除和恢复本身只通过维护人员手工修改数据库完成。

## 实现边界

新增一个可复用的联赛可见性检查组件，负责按 `leagueId` 判断 `isDeleted = false`，并返回统一 404。路由守卫和无法通过查询关系自然过滤的服务调用该组件，避免每个页面自行定义不同错误。

同时在数据查询边界显式加入过滤条件：

- `AdminLeaguesService` 和公开 `LeaguesService` 的列表、详情查询；
- 管理员权限范围和导航所依赖的联赛关系查询；
- 从球队、赛季、赛事等下属资源反查联赛的入口；
- 不经过通用守卫的公开接口。

不采用 Prisma 全局查询改写。全局改写会改变内部维护、迁移和审计查询的语义，也难以可靠覆盖事务客户端及嵌套关系查询。显式过滤加统一检查服务更容易审查和测试。

## 数据保留与恢复

逻辑删除只修改 `leagues.is_deleted`。关联表不更新、不归档、不删除，外键保持不变。

把 `is_deleted` 恢复为 `FALSE` 后，联赛按原 `status` 恢复可见：

- 原状态为 `ACTIVE` 时重新出现在启用列表和公开列表；
- 原状态为 `ARCHIVED` 时重新出现在已归档列表；
- 原有球队、赛季、比赛和财务历史保持原样。

## 测试策略

采用测试驱动实现，并覆盖以下行为：

1. 迁移后现有联赛默认 `isDeleted = false`。
2. 管理后台联赛列表不返回逻辑删除记录，数量不包含逻辑删除记录。
3. 小程序公开联赛列表不返回逻辑删除记录。
4. 已删除联赛的公开详情和后台工作区返回 404。
5. 已删除联赛的球队、赛季及至少一个代表性下属资源入口返回 404。
6. 已删除联赛的写操作返回 404，且不产生数据变更。
7. `isDeleted = false` 的启用和归档联赛保持原有行为。
8. 将字段恢复为 `false` 后，联赛按原状态重新可见。
9. 管理后台现有页面不出现删除或恢复按钮。

完成后运行 contracts、API 单元测试、API E2E、管理后台测试和整仓 `pnpm verify`。

## 验收标准

- 数据库中可手动把目标联赛的 `is_deleted` 设置为 `TRUE` 或 `FALSE`。
- 设置为 `TRUE` 后，后台、小程序及所有联赛范围页面均不可见或返回 404。
- 设置为 `FALSE` 后，无需恢复关联数据即可重新显示。
- 归档联赛与逻辑删除联赛保持独立语义。
- 整仓验证通过，且不存在对关联业务数据的物理删除。
