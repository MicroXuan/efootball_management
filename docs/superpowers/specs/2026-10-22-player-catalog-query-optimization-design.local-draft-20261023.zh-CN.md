# 球员库查询优化设计

日期：2026-10-22

状态：用户已确认方向，待按实施计划执行

## 1. 目标与现状

小程序球员库保留每次 20 张、滚动加载、搜索和筛选的现有交互。当前 `PlayerCatalogService.latestVersions()` 对每个列表或详情请求读取指定发布序号之前的全部 `player_card_versions`，在 Node.js 内去重、筛选、排序，最后才截取一页。现有配置数据库只约 200 张卡；目标是支持至少 50,000 张有效卡以及持续增加的历史版本，不让单次请求的数据传输和应用内存随全库线性增长。

## 2. 正确性约束

- 卡片的身份是 `playerCardId`，同一现实球员的多张卡分别显示；一张卡的旧版本只用于历史快照。
- 首次请求读取最新发布序号；分页游标继续固定这一发布序号。发布发生在两页之间时，不重复或漏掉卡片。
- 最新版本为 `INACTIVE` 时，该卡不出现在公开列表；不能回退展示旧的 `ACTIVE` 版本。
- 用户于 2026-10-23 选择与 PESDATA **大致同序**，不要求逐张同序。公开卡片列表改为 `packReleaseDate DESC`（无日期排末尾）、`overallRating DESC`、`publishedAt DESC`、`playerCardId ASC`。PESDATA 的 `agentDate` 已映射到 `packReleaseDate`；同一天官网可能有其他内部优先级，因此不承诺同日逐张一致。
- 保留现有搜索语义：将查询及中文名、英文名、卡名、球员包中文名和英文名做 `normalizeSearchText` 后，执行包含匹配；筛选条件 `position`、评分范围、`cardType`、`cardPackId` 不变。
- 小程序与公共 API 的响应结构和每页默认数量不变。游标对客户端仍为不透明字符串；内部需携带新排序键和固定发布序号，旧游标在切换期需可安全处理，游标无效仍返回 `INVALID_CURSOR`。
- 已发布但下架的卡可以从直接详情入口读取并显示 `INACTIVE` 状态，以保持收藏、持有和交易历史可查看；从未发布的卡仍为 404。

## 3. 查询设计

新增 `PlayerCatalogReadRepository`，把最新版本判断、筛选、游标条件、排序及 `LIMIT (limit + 1)` 下推至 MySQL。使用参数化 SQL；先通过 `NOT EXISTS` 排除同卡在固定发布序号内的更晚版本，再对留下的最新版应用 `ACTIVE` 与筛选条件。`NOT EXISTS` 依赖已有的 `(player_card_id, release_sequence)` 唯一索引。只在数据库返回的至多 101 张卡上做响应映射，不在服务端保留全库数组。

球员库列表只按上述简化规则排序，不单独保存官网逐卡位置；现有小程序球员包分组继续保留，所以屏幕上同日卡片的视觉次序也可能与官网不同。若将来需要逐张同序，再另行设计来源顺序快照。

`player_card_versions` 已有规范化中英文球员名；再增加 `normalized_card_name`、`normalized_pack_name_zh`、`normalized_pack_name_en`，由现有 `normalizeSearchText` 分别生成并在发布事务中写入；旧版本通过受控分块回填。数据库对五列分别执行包含匹配，避免把字段拼接后出现跨字段误命中，保持现有 Unicode 规范化行为。普通 B 树索引不能直接加速前置通配符包含搜索；先用 50,000 张卡的隔离库基准验证。若搜索性能不达验收目标，再单独设计倒排索引，不能悄悄改成前缀搜索。

列表通用排序、球员 ID 详情、球员包 ID 详情使用针对实际 SQL 的组合索引。迁移先加列和候选索引；在隔离库和目标环境只读 `EXPLAIN` 核对后，删除无用候选索引或补足缺失索引。索引不是替代查询下推的修复。

`getPlayer`、`getCard`、`listPacks`、`getPack` 也移除 `latestVersions()` 全量装载。球员与卡片详情按 ID 定位，球员包列表在 SQL 内聚合、排序和分页，包详情只取该包的卡。对于包详情，如果一包卡片数超过既有响应适用范围，先实测并另行定义分页契约，不擅自截断卡片。

## 4. 迁移与发布

1. 在本机隔离的 `verify` 数据库执行迁移、回填和 50,000 张卡基准；单元/API/e2e 测试命令必须显式提供本机 `DATABASE_URL`。
2. 目标环境先只读执行 `pnpm db:status`，核对迁移状态、行数和索引；按受控流程先部署迁移与回填，再让新 API 承接流量。
3. 新 API 保持现有接口契约；小程序无需因查询内部实现变化重新发布。目标环境核对实际 API 响应及小程序解析。
4. 复测后台联赛球队“现役球队 / 已退出”、球队详情、小程序“我的联赛”、球员库、卡片详情和球员包；失败时定位修复。

## 5. 验收

- 50,000 张卡、包含多次更新与下架版本的隔离数据库上，普通列表、筛选、搜索、深度游标分页、卡详情及球员包查询返回正确结果，且每个列表请求只向 Node.js 返回一页数据。
- 对比旧接口金样本：搜索 Unicode 语义、状态过滤和响应契约一致；卡片 ID 顺序按新规则预期变化，核对日期优先、同日评分优先与稳定翻页。
- 在发布发生于两页之间时，旧游标继续得到原发布快照，不重复或漏卡。
- 记录 `EXPLAIN ANALYZE`、接口响应时间与数据库读取行数；是否满足上线性能目标由隔离库基准和目标环境只读验证共同决定，不用 200 张卡的现状推断 50,000 张卡性能。
