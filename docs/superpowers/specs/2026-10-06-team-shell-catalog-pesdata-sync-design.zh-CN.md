# 联赛球队队壳目录与 PESDATA 同步设计

## 1. 背景

当前联赛球队同时保存负责人、球队编号、球队名称、简称、队徽、阵容、工资和资金等信息。管理员创建球队时需要手工填写球队名称与简称，队徽尚未形成可复用的球队目录。

本次需求把“经营球队”和“队壳”拆分为两个独立概念：

- 经营球队代表用户在某个联赛中的经营主体，承载编号、负责人、阵容、工资、资金、成绩和赛季资格；
- 队壳只代表对外展示身份，包含球队名称、简称和队徽；
- PESDATA 只作为队壳素材来源，不同步真实球队阵容，也不约束经营球队可以持有哪些球员。

最终展示格式为：

```text
[队徽] 编号-球队名
       （用户在当前联赛中的称呼）
```

## 2. 目标

- 管理员创建经营球队时可以从本地球队目录中搜索并选择队壳；
- 后端可以在已获授权的前提下同步 PESDATA 的球队名称、简称和队徽；
- PESDATA 队徽保存到系统自己的对象存储，小程序不直接依赖来源站图片；
- 管理员可以为同一用户在不同联赛设置不同称呼；
- 同一联赛内，同一个队壳同一时间只能被一支经营球队使用；
- 每支经营球队任何时候都必须绑定一个队壳；
- 队壳可以更换、转让或交换，但不能带走阵容、工资、资金、成绩或球队编号；
- 来源站不可用或接口变化时，已经发布的本地球队目录和现有联赛功能不受影响；
- 所有创建、同步、更换和交换操作形成具体、可理解的审计记录。

## 3. 非目标

- 不同步 PESDATA 真实球队阵容；
- 不让小程序或管理后台浏览器直接请求 PESDATA；
- 不在创建球队时实时依赖 PESDATA 可用性；
- 不根据 PESDATA 球队自动约束经营球队的球员归属；
- 不因来源列表暂时缺少球队而自动删除本地目录项；
- 不在未确认授权范围时复制或公开分发来源图片；
- 不把“编号-球队名-用户称呼”保存成冗余拼接字符串。

## 4. 核心领域模型

### 4.1 经营球队 `LeagueTeam`

`LeagueTeam` 继续作为联赛内的经营主体，保留：

- `leagueId`；
- `ownerUserId`；
- `teamNumber`；
- `ownerAlias`：管理员为用户在该联赛设置的称呼；
- 阵容、工资、资金、比赛与赛季关系；
- 状态、版本和审计字段。

新增必填的 `catalogTeamId`，指向当前使用的队壳。

球队名称、简称和队徽仍在 `LeagueTeam` 保存当前展示快照，便于现有接口兼容、稳定展示和人工覆盖，但其来源由 `catalogTeamId` 追溯。显示文本在 API 或前端组合，不新增完整展示字符串字段。

约束：

- `(leagueId, ownerUserId)` 唯一，保持一个用户在同一联赛只有一支经营球队；
- `(leagueId, teamNumber)` 唯一；
- `(leagueId, catalogTeamId)` 唯一，保证同一联赛内一个队壳只被使用一次；
- `catalogTeamId` 最终为非空，保证每支经营球队始终拥有队壳。

不同联赛可以使用同一个目录队壳。

### 4.2 队壳目录 `TeamCatalogItem`

新增队壳目录，建议字段：

- `id`；
- `sourceType`：`PESDATA` 或 `CUSTOM`；
- `sourceExternalId`：来源球队稳定编号，自定义队壳可为空；
- `sourceLeagueExternalId`；
- `sourceLeagueName`；
- `nameZh`、`nameEn`、`nameJa`；
- `shortName`；
- `remoteLogoUrl`：仅用于来源追溯；
- `storedLogoUrl`：自有对象存储公开地址；
- `logoChecksum`；
- `sourceChecksum`；
- `sourceUpdatedAt`、`lastSyncedAt`；
- `status`：`ACTIVE`、`SOURCE_UNCONFIRMED`、`DISABLED`；
- `createdAt`、`updatedAt`。

来源唯一约束为 `(sourceType, sourceExternalId)`。自定义队壳由管理员填写名称并上传队徽，也作为正式目录项参与分配，而不是绕过目录直接写入 `LeagueTeam`。

### 4.3 队壳变更历史

新增结构化队壳分配历史，或者以足够完整的专用审计元数据记录：

- 经营球队；
- 变更前与变更后的队壳；
- 操作类型：创建分配、更换、转让、交换；
- 相关的另一支经营球队；
- 操作管理员；
- 原因；
- 操作时间。

历史赛季继续使用 `SeasonEntry` 中的球队名称、简称、编号和队徽快照。后续更换队壳不能改写历史赛季显示。

## 5. PESDATA 同步架构

采用“后台同步、本地审核、本地发布”的方式：

```text
PESDATA 联赛/球队接口
          ↓
PesdataTeamClient（签名、请求、限速、重试）
          ↓
PesdataTeamMapper（来源字段标准化）
          ↓
球队目录同步运行（分页、检查点、差异）
          ↓
队徽校验与自有对象存储
          ↓
管理员审核并发布
          ↓
TeamCatalogItem → 后台创建球队与小程序展示
```

复用现有 PESDATA 客户端的配置、签名、限速、超时和重试边界，但球队响应使用独立 schema 与 mapper，避免和球员同步逻辑耦合。来源接口或字段变化时，只修改 PESDATA 适配层。

### 5.1 同步模式

- `sample`：同步少量联赛和球队，用于首次字段及图片验收；
- `full`：遍历全部联赛和球队；
- `incremental`：只处理新增、摘要变化、上次失败或来源待确认项；
- `resume`：从未完成运行的检查点继续。

同步默认只生成待审核差异，不直接影响已发布目录，也不自动更新已经分配给经营球队的名称或队徽。

### 5.2 队徽处理

仅在授权包含球队名称和队徽使用时执行复制：

1. 后端下载来源图片；
2. 校验 HTTP 状态、MIME、实际文件格式、文件大小和像素范围；
3. 计算内容哈希，拒绝无效或异常文件；
4. 必要时生成统一展示规格；
5. 上传到自有对象存储；
6. 使用来源编号与内容哈希生成稳定对象键；
7. 在目录中保存 `storedLogoUrl`，保留 `remoteLogoUrl` 仅供追溯。

建议对象键：

```text
team-crests/pesdata/<source-team-id>/<content-hash>.webp
```

小程序和公开 API 只返回自有对象存储地址，不返回来源站图片地址。

### 5.3 来源变化规则

- 新球队生成新增差异；
- 名称或队徽变化生成待审核更新；
- 管理员发布后更新目录；
- 已分配的经营球队不被自动覆盖，管理员可选择把目录新版应用到指定经营球队；
- 来源列表暂时缺少球队时标记 `SOURCE_UNCONFIRMED`，不自动删除或释放队壳；
- 协议、签名或响应结构变化时整次运行失败，既有目录继续可用。

## 6. 创建经营球队流程

后台表单顺序：

1. 输入 6 位用户编号并确认用户；
2. 设置该用户在当前联赛的称呼 `ownerAlias`；
3. 填写球队编号；
4. 按洲、来源联赛或球队名搜索本地队壳目录；
5. 选择一个在当前联赛未被占用的队壳；
6. 自动带出名称、简称和队徽；
7. 展示最终预览；
8. 提交创建。

预览格式：

```text
[队徽] 3-阿贾克斯
       （tidus）
```

创建事务必须同时校验：

- 用户存在且状态可用；
- 用户在当前联赛没有其他经营球队；
- 球队编号未占用；
- 队壳目录项处于可用状态；
- 队壳在当前联赛未被占用；
- 当前赛季等既有业务前置条件满足。

审计操作名使用“创建联赛球队”，元数据包含用户、联赛称呼、球队编号和队壳，不使用模糊的“其他后台操作”。

## 7. 队壳更换、转让与交换

队壳变化只影响球队名称、简称、队徽和目录来源绑定，不能修改：

- 负责人；
- 用户的联赛称呼；
- 球队编号；
- 阵容及球员归属；
- 工资、资金和财务流水；
- 比赛成绩；
- 赛季参赛资格。

### 7.1 更换队壳

经营球队选择一个当前联赛未占用的新队壳。事务内直接把球队从旧队壳切换到新队壳，旧队壳随后回到可选池。任何时刻都不提交无队壳状态。

### 7.2 转让队壳

把甲队队壳转给乙队时，甲队必须在同一事务中获得另一个未占用队壳。乙队原队壳释放回可选池。后台提交前必须明确展示三方变化：

- 甲队：原队壳 → 替代队壳；
- 乙队：原队壳 → 甲队原队壳；
- 乙队原队壳：释放。

### 7.3 交换队壳

甲乙两支经营球队可以直接交换现有队壳。由于复合唯一约束会在逐条更新时产生瞬时冲突，实现应使用受控事务和锁，并通过安全的临时分配策略或数据库支持的原子方式完成，不能暂时写入空值。

### 7.4 并发与审计

更换、转让和交换都必须：

- 锁定联赛、相关经营球队和队壳分配；
- 使用乐观版本或等价的并发保护；
- 在一个事务中完成所有变化；
- 冲突时整体回滚；
- 记录“更换球队队壳”“转让球队队壳”或“交换球队队壳”等具体操作；
- 保存变更前后队壳、相关球队、管理员和原因。

## 8. 迁移策略

现有 `LeagueTeam` 已经保存名称、简称和队徽，迁移分阶段进行：

1. 创建队壳目录表和可空 `catalogTeamId`；
2. 根据每支现有经营球队的名称、简称和队徽创建历史自定义队壳；
3. 把对应目录项回填到经营球队；
4. 校验不存在空绑定和同联赛重复绑定；
5. 添加 `(leagueId, catalogTeamId)` 唯一约束；
6. 把 `catalogTeamId` 改为非空；
7. 上线新版创建、更换和交换入口。

迁移不修改阵容、财务、比赛或赛季历史。

## 9. 接口建议

后台目录接口：

- 查询已发布队壳，支持洲、来源联赛、名称和占用状态筛选；
- 创建和更新自定义队壳；
- 查看 PESDATA 同步运行与差异；
- 发布或拒绝同步差异；
- 把已发布目录版本应用到指定经营球队。

经营球队接口：

- 创建时提交 `ownerUserId`、`ownerAlias`、`teamNumber`、`catalogTeamId`；
- 更新联赛称呼；
- 更换队壳；
- 转让队壳；
- 交换两支球队的队壳。

公开球队响应继续返回组合展示所需的独立字段：

- `teamNumber`；
- `name`；
- `shortName`；
- `logoUrl`；
- `ownerAlias`。

前端负责排版，不依赖预先拼接的展示字符串。

## 10. 错误处理

- 队壳在当前联赛已占用：拒绝创建或更换；
- 用户在当前联赛已有经营球队：拒绝重复创建；
- 经营球队未指定队壳：契约与数据库双重拒绝；
- 对象存储上传失败：该条同步差异不能发布；
- 来源图片无效：记录单条失败，其他球队继续处理；
- PESDATA 限流或临时故障：限速、退避并允许恢复；
- PESDATA 协议变化：中止运行，不污染已发布目录；
- 并发更换或交换：版本冲突并提示管理员刷新；
- 目录项被禁用但仍有球队使用：保留现有绑定，禁止新分配，等待管理员处理。

## 11. 测试与验收

### 11.1 数据与服务测试

- PESDATA 联赛、球队列表和详情 schema 校验；
- 多语言名称、来源编号与队徽映射；
- 图片 MIME、实际格式、大小、尺寸和内容哈希校验；
- 相同图片不重复上传；
- 同步检查点、重试、增量和恢复；
- 来源缺失不自动删除；
- 目录发布不会自动覆盖已分配球队；
- 同联赛队壳唯一、跨联赛可复用；
- 所有经营球队必须拥有队壳；
- 创建、更换、转让和交换事务回滚；
- 队壳变化不修改阵容、工资、资金、成绩和赛季资格；
- 历史赛季继续读取原快照。

### 11.2 管理后台验收

- 可以设置联赛称呼；
- 可以按洲、联赛和名称搜索队壳；
- 已占用队壳不可选择并显示占用球队；
- 创建前可预览队徽、编号、名称和称呼；
- 支持创建自定义队壳；
- 更换、转让和交换页面明确展示影响范围；
- 审计日志使用具体中文操作名称。

### 11.3 小程序验收

- 显示队徽；
- 显示“编号-球队名”；
- 显示括号内的联赛称呼；
- 队徽加载失败时有稳定占位；
- PESDATA 不可用时，已同步球队仍正常展示；
- 队壳变化不改变阵容与其他经营数据。

## 12. 上线顺序

1. 队壳目录、迁移和约束；
2. 自定义队壳及对象存储能力；
3. 后台创建球队接入队壳目录与联赛称呼；
4. 小程序展示格式；
5. 队壳更换、转让和交换；
6. PESDATA 球队样本同步与人工验收；
7. PESDATA 全量及增量同步；
8. 运行监控、故障恢复和操作文档。

正式启用 PESDATA 队徽同步前，必须确认现有授权覆盖球队名称与队徽的获取、保存和展示。
