# 非概念实况双端高级视觉重构设计

日期：2026-10-01  
状态：已完成方向与架构确认，等待书面规范复核  
适用范围：微信原生小程序、React/Ant Design 管理后台

本规范取代 `2026-10-01-football-ui-style-iteration-design.zh-CN.md` 中已经落地但效果不足的视觉决策。旧规范仍作为迭代历史保留；后续页面设计与实现以本规范为准。

## 1. 目标与成功标准

产品面向 eFootball 玩家、球队负责人、联赛管理员和平台管理员。小程序承担联赛浏览、球队与赛季参与、比赛和球员卡体验；管理后台承担长期、高密度的赛事运营工作。

本轮重构的目标不是继续叠加足球装饰，而是建立一套能支撑成熟商业产品的双端设计系统：

- 小程序保持全暗色，具有比赛日的沉浸感，但不依赖满屏荧光绿。
- 管理后台使用深色导航框架和浅色数据工作区，适合长时间阅读与操作。
- 联赛、赛季、球队、赛事和球员卡形成一致但不单调的信息层级。
- 页面在小屏、长中文、大量数据、加载、空状态和错误状态下仍然稳定。
- 不修改 API、数据库、权限模型或核心业务流程。
- 不引入在线字体、新 UI 框架、动画库或大型装饰图片。

成功标准：主要正文清晰可读；未选中导航仍然可见；卡片边界明确；联赛使用独立圆角卡片；当前赛季入口清晰；用户能在三步内从联赛列表进入当前赛季；双端共享相同的状态语义。

## 2. 设计观点：赛事日精密感

设计方向命名为“赛事日精密感”。视觉基调来自职业俱乐部的数据部门和比赛日运营台，而不是通用电竞霓虹或模板化 SaaS。

核心观点是：**联赛不是一张静态信息卡，而是一条正在发生的赛季。**

产品的标志性组件是“赛季轨道”。它用真实业务状态表达报名、确认、赛程和结算阶段，并同时出现在小程序联赛详情、当前赛季页面以及管理后台赛季工作区。它不是装饰性时间线，而是帮助用户判断当前阶段和下一步行动的导航结构。

荧光绿只表示此刻最重要的状态、主操作和焦点。正文、卡片边界和导航层级由中性色、表面明度、字号、间距和字重承担。

## 3. 五项高级设计原则

### 3.1 有观点，而非模板

- 使用赛季轨道、真实联赛徽标、球队和球员内容建立产品身份。
- 不使用无业务含义的编号、英文眉题、玻璃面板或发光装饰。
- 小程序和后台不强行做成相同主题，而是共享状态语义和组件逻辑。

### 3.2 字体承担功能

- 中文界面使用系统原生字体栈，避免在线字体带来的加载时间和字体闪烁。
- 页面标题依靠字重、字距和留白建立个性，不使用楷体或廉价的伪窄体标题。
- 比分、排名、工资、日期和赛季编号使用等宽数字或本地 DIN 风格回退字体，启用表格数字。
- 不同层级使用固定字号阶梯，不在页面内随意发明字号。

### 3.3 克制配色

- 共享视觉只使用石墨黑、冷灰白、中性描边、单一赛场绿和必要的语义色。
- 荧光绿的目标视觉面积不超过约 5%。
- 正文、未选中导航和普通边框禁止使用绿色。
- 成功、警告、危险和禁用状态不能全部映射为品牌绿。

### 3.4 会呼吸的层级

- 使用 4/8 基础间距系统，形成 8、12、16、24、32、48 的稳定节奏。
- 页面、模块、卡片和控件使用不同圆角层级，不再全部胶囊化。
- 卡片依靠表面明度差、中性描边和必要的轻阴影分层，不使用绿色细边框包围所有内容。

### 3.5 图像有意图

- 联赛使用官方上传徽标，球员使用真实卡图或头像，球队使用真实队徽。
- 图片必须有固定比例、留白、安全区和失败回退规范。
- 缺少素材时使用名称首字、球队缩写或轻量球场纹理，不使用通用图库图片。
- 不猜测、重绘或随意改变官方徽标的颜色和比例。

| 抬升表面 | `#1C262B` | 赛季入口、选中分段、次级层级 |
| 强描边 | `#344047` | 独立卡片和主要边界 |
| 弱描边 | `#2D393F` | 行分隔和内部区域 |

| 强调色上文字 | `#111810` | 绿色按钮上的文字与图标 |

| 赛场强调 | `#B6F13A` | 选中指示线和少量关键状态 |

危险、警告和信息状态继续使用独立语义色，并保证颜色不是唯一识别信号。

### 4.3 字体与数字

中文与正文：

```css
-apple-system, BlinkMacSystemFont, "PingFang SC", "Microsoft YaHei", sans-serif
```

数据与编号：

```css
"DIN Alternate", "Arial Narrow", "SFMono-Regular", Consolas, sans-serif
```

数字使用 `font-variant-numeric: tabular-nums`。后台正文基准为 14–16px，小程序正文基准为 24–28rpx。正文行高保持 1.5–1.7。

### 4.4 圆角层级

| 层级 | 小程序 | 管理后台 |
| --- | --- | --- |
| 页面级或沉浸式头图 | 28–32rpx | 20–24px |
| 独立内容卡片 | 22–26rpx | 16–18px |
| 卡片内入口 | 16–20rpx | 12–14px |
| 输入框和按钮 | 14–18rpx | 8–12px |
| 状态标签 | 胶囊 | 胶囊 |

胶囊只用于标签、筛选和短状态，不用于所有按钮、标签页或大面积容器。

## 5. 核心体验链路

### 5.1 联赛列表

- 每个联赛是独立圆角卡片，卡片之间至少保留 16rpx 的可见间距。
- 卡片顶部展示真实徽标、联赛名称、简短描述和中性的进入图标。
- 当前赛季展示为卡片内抬升表面，包含赛季名称和状态，但列表整卡只承担“进入联赛详情”一个主动作。
- 无赛季的联赛显示清楚的“尚未发布赛季”，不伪装成可操作状态。

### 5.2 联赛详情

- 顶部使用真实徽标、联赛名称、平台和赛制建立上下文。
- 当前赛季轨道展示报名、确认、赛程和结算阶段。
- 数据指标只展示最能支持决策的三个值，例如参赛球队、比赛轮次和我的球队。
- 使用明确的“进入当前赛季”主按钮，避免联赛卡片内部出现互相冲突的嵌套点击区域。
- 我的球队、赛事规则等入口使用普通列表行，不与当前赛季争夺主焦点。

### 5.3 当前赛季

- 页面顶部展示赛季名称、所属联赛和当前阶段。
- 当前行动在首屏可见，例如确认参赛、等待审核、查看赛程或提交比赛结果。
- 截止时间、当前轮次和参赛状态使用结构化数据组件。
- 球队列表、赛程和积分榜按赛季状态逐步开放，未开放状态说明原因和下一步。

### 5.4 管理后台映射

- 侧边栏未选中菜单使用清晰的浅色文字和统一线性图标。
- 选中菜单使用深灰抬升表面、白色文字和 3px 绿色状态条，不使用绿色正文。
- 联赛工作区顶部展示面包屑、联赛名称和管理员身份。
- 用户与球队、赛季管理、工资规则、转会窗口和财务流水使用紧凑分段导航。
- 赛季管理页复用赛季轨道，并在同一视图中显示当前赛季、历史赛季和主要操作。

## 6. 双端组件体系

### 6.1 小程序组件

- `PageHeader`：页面标题、返回和必要上下文。
- `SegmentedControl`：两到四个互斥视图切换。
- `EntityArtwork`：联赛徽标、球队队徽和球员图片的统一容器。
- `LeagueCard`：联赛摘要和当前赛季预览。
- `SeasonRail`：阶段、当前状态和下一步。
- `StatusBadge`：状态文字、圆点和语义色。
- `MetricCard`：比分、排名、工资和人数等数据。
- `ActionRow`：详情页次级入口。
- `FloatingTabBar`：球员、联赛、我的三项导航。

### 6.2 管理后台组件

- `ApplicationShell`：可读侧栏、顶部身份区和浅色工作区。
- `WorkspaceHeader`：面包屑、标题、状态和主要操作。
- `SectionTabs`：联赛工作区功能导航。
- `DataCard`：表单、列表和指标的统一表面。
- `SeasonRail`：与小程序共享状态语义的桌面版本。
- `StatusTag`：中性、成功、警告、危险和禁用状态。
- `DataTable`：清晰表头、稳定行高、可滚动和固定操作列。
- `FormSection`：带可见标签、帮助文本和就地错误的表单分组。

组件应通过语义令牌配置，不在页面内重复定义颜色、圆角或阴影。

## 7. 页面扩展规则

- 球员：保留三列浏览效率，但加强卡图比例、评分层级、名称截断和卡种识别；绿色只标记选中筛选或状态。
- 球队：用队徽、球队名称和工资/阵容数据建立身份，阵容成员使用可扫描的列表或网格。
- 赛事：复用赛季轨道逻辑展示报名、赛程、结果确认和结束状态。
- 比赛：比分是第一视觉层级，双方球队和确认状态是第二层级，提交操作独立分区。
- 个人中心：优先展示身份、已绑定球队和下一步行动，不使用大量装饰卡片。
- 后台数据页：保留高密度表格，页面卡片数量从业务分组出发，不把每个数字都做成指标卡。

## 8. 交互与反馈

- 小程序主要触控区不小于 44pt；桌面操作保留清晰键盘焦点。
- 交互反馈使用颜色、透明度或阴影变化，不改变布局尺寸。
- 微交互控制在 150–220ms；退出动效略快于进入动效。
- 支持减少动态效果；不使用持续循环动画。
- 加载状态预留最终内容尺寸，避免页面跳动。
- 空状态说明原因和下一步；错误状态说明发生了什么及如何重试。
- 禁用状态同时通过文字、透明度和原生禁用属性表达。

## 9. 图像规范

- 联赛徽标容器使用 1:1 比例，保留至少 10% 内边距，不裁切主体。
- 球员卡和头像使用固定比例并预留尺寸，优先 WebP；失败时回退到姓名首字或球队缩写。
- 后台缩略图保持与小程序一致的素材来源和比例。
- SVG 图标使用同一图标族、同一层级内统一线宽；导航图标默认 20–24px。
- PNG 图标仅保留微信原生 TabBar 等平台限制场景。

## 10. 性能约束

- 不加载在线字体，不新增动画库或 UI 框架。
- 不使用高成本全屏 `backdrop-filter`、大面积发光或持续动画。
- 业务图片懒加载，设置固定宽高或纵横比，避免累计布局偏移。
- 页面渐变只用于小范围品牌区域，普通卡片使用纯色表面。
- 复用现有 React 懒加载和微信原生组件；不改变数据请求策略。
- 设计重构不得显著增加首屏资源体积或阻塞交互时间。

## 11. 可访问性

- 普通正文对比度至少 4.5:1；大文字、图标和次级信息至少 3:1。
- 颜色不能作为状态的唯一表达；必须同时提供文字、形状或位置提示。
- 图片和图标提供准确的替代文本或可访问性标签。
- 表单使用可见标签、帮助文本和字段附近的错误提示。
- 后台键盘顺序与视觉顺序一致，弹窗和抽屉正确管理焦点。
- 固定头部、底部导航和操作栏尊重安全区，不遮挡滚动内容。

## 12. 响应式与验收范围

必须验证：

- 375px 小屏手机。
- 大屏手机和微信开发者工具常用设备。
- 手机横屏。
- 768px、1024px 和 1440px 桌面宽度。
- 最大系统字号、长中文、超长联赛名称和缺少图片。
- 加载、空、错误、无权限、禁用、处理中和版本冲突状态。
- 后台表格横向滚动、弹窗、抽屉和键盘导航。
- 减少动态效果模式。

## 13. 实施边界与迁移策略

本轮只重构视觉层和展示组件。API、数据库、权限、路由和业务流程保持不变。

实施顺序：

1. 建立共享语义令牌、圆角、间距和字体体系。
2. 重构小程序联赛列表、联赛详情和当前赛季链路。
3. 重构管理后台应用框架、联赛工作区和赛季管理页。
4. 将已验证组件扩展到球员、球队、赛事、比赛和个人中心。
5. 统一加载、空、错误和无权限状态。
6. 完成多尺寸、对比度、交互和性能验证。

每一阶段都应保持现有功能可用，不采用一次性全局替换造成大面积不可验证改动。

## 14. 设计自评与补齐计划

| 标准 | 分数 | 依据 | 继续补齐 |
| --- | ---: | --- | --- |
| 有观点，而非模板 | 9.3 | 赛季轨道由真实联赛状态生成 | 在比赛、赛事和后台保持同一语义，不滥用 |
| 字体承担功能 | 9.0 | 中文阅读与数字数据明确分工 | 实机检查 Windows 与微信字体回退 |
| 克制配色 | 9.5 | 绿色控制在关键状态和主操作 | 对所有页面执行语义色审计 |
| 会呼吸的层级 | 9.4 | 固定间距和圆角层级 | 验证小屏、长中文和高密度表格 |
| 图像有意图 | 8.8 | 使用真实徽标和球员素材 | 建立素材质量、比例、留白和失败回退规范 |
| 综合 | 9.2 | 视觉、业务和性能约束达到平衡 | 实施后通过截图复审重新评分 |

评分不是完成标准。实施后必须以真实页面、真实数据和多尺寸截图重新复审；任何低于 9 分的项目都要记录具体差距和下一轮修正动作。
