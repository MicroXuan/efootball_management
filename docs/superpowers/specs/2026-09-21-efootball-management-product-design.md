# 实况赛事助手产品设计文档

> 文档类型：完整平台蓝图 + V1.0 可执行 PRD  
> 文档版本：1.0  
> 编写日期：2026-09-21  
> 产品形态：微信小程序 + 主办方 Web 后台 + 平台运营后台  
> 技术基线：CloudBase 混合架构、独立后端 API、MySQL

## 1. 文档说明

### 1.1 文档目标

本文档用于统一产品、设计、研发、测试和运营对项目的理解，并回答以下问题：

- 产品服务谁，解决什么问题；
- 平台由哪些业务模块组成；
- 玩家、战队、主办方、裁判和平台人员分别可以做什么；
- 一项赛事如何从创建走到归档；
- 报名、赛程、结果、积分与申诉如何运作；
- 首版必须开发什么，哪些功能暂不开发；
- 核心数据如何建模；
- 系统需要满足哪些性能、安全和可运维要求；
- 如何衡量产品是否成功。

### 1.2 当前假设

- 产品主要面向中文用户和微信生态。
- 产品不直接运行《eFootball / 实况足球》游戏，只管理资料、阵容、赛事和比赛结果。
- 比赛数据首版采用参赛双方手动上报、截图举证、对方确认；赛事管理员可代录和裁定。
- 玩家端使用微信小程序，复杂赛事操作使用 Web 后台。
- 首版同时服务普通玩家与赛事主办方，但以赛事管理闭环为优先。
- 球员卡数据由平台维护，不假设存在稳定可用的官方数据接口。
- 本产品为非官方社区工具，品牌、素材和游戏数据的使用需单独完成版权与合规评估。

### 1.3 产品暂定名称

本文档使用“实况赛事助手”作为暂定名称。正式品牌命名不影响业务设计。

### 1.4 术语

| 术语 | 定义 |
|---|---|
| 平台用户 | 登录小程序或后台的自然人账号 |
| 参赛玩家 | 在某项赛事中实际参赛的自然人 |
| 游戏账号 | 玩家在指定平台和区服中的游戏身份 |
| 游戏球员 | 哈兰德、亚马尔等现实足球运动员在游戏中的角色 |
| 球员卡 | 某名游戏球员在特定版本或卡包中的具体卡片 |
| 战队 | 多名参赛玩家组成的长期组织 |
| 参赛方 | 一项赛事中的个人玩家或战队 |
| 主办方 | 创建和运营赛事的个人或组织 |
| 正式结果 | 已确认或裁定、可用于积分及晋级的比赛结果 |
| 结果版本 | 对比赛结果的每一次上报、修正或裁定记录 |
| 赛事阵容 | 玩家为某项赛事提交并可能被锁定的球员卡名单快照 |

## 2. 产品定位与目标

### 2.1 产品定位

实况赛事助手是面向《eFootball / 实况足球》玩家、战队和民间赛事主办方的一体化管理平台，以赛事管理为核心，以球员卡数据库和阵容工具作为内容入口。

### 2.2 用户问题

#### 玩家侧

- 球员卡、卡包和属性资料分散，查询与对比效率低；
- 个人阵容和赛事阵容难以统一管理；
- 报名、赛程、比分确认和申诉依赖微信群；
- 历史比赛、排名和荣誉无法长期沉淀。

#### 战队侧

- 成员、出战名单和比赛安排缺乏统一工具；
- 战队战绩和荣誉分散；
- 队长需要在群聊与表格之间重复维护数据。

#### 主办方侧

- 报名审核、分组、赛程、比分和积分依赖表格；
- 比赛结果缺乏双方确认和审计记录；
- 争议证据、裁判意见和最终裁定难以追踪；
- 赛程变化和结果确认需要大量人工催促。

### 2.3 产品价值

- 玩家：查球员、管阵容、找赛事、打比赛、沉淀战绩与荣誉；
- 战队：管成员、报赛事、排出战、看战绩；
- 主办方：低成本完成报名、赛程、比赛、积分和仲裁；
- 平台：通过球员内容获客，通过真实赛事形成留存和网络效应。

### 2.4 核心业务闭环

```text
球员内容获客
→ 玩家建立身份或加入战队
→ 发现并报名赛事
→ 查看赛程并完成比赛
→ 上报、确认或裁定结果
→ 更新积分、晋级和荣誉
→ 玩家回到下一场比赛或下一项赛事
```

### 2.5 北极星指标

每周在平台内成功完成并正式生效的比赛场次。

该指标同时反映赛事供给、玩家参与、比赛完成和结果流程质量。

## 3. 产品形态与系统边界

### 3.1 玩家微信小程序

- 微信登录与玩家档案；
- 游戏账号管理；
- 球员卡及卡包查询；
- 收藏、阵容与赛事阵容；
- 战队创建与加入；
- 赛事发现、报名、赛程、积分榜；
- 比赛签到、结果上报、确认与申诉；
- 战绩、荣誉、公告和通知。

### 3.2 主办方 Web 管理后台

- 创建与配置赛事；
- 设置赛制、积分及比赛规则；
- 审核报名和锁定名单；
- 分组、抽签、生成及调整赛程；
- 管理比赛结果、延期和异常；
- 指派裁判与处理申诉；
- 发布公告、发送通知和导出数据；
- 查看赛事运营数据与操作日志。

### 3.3 平台运营后台

- 用户、主办方、赛事与权限管理；
- 球员卡、卡包及基础字典管理；
- 公开赛事审核与风险处置；
- 举报、反馈和数据纠错处理；
- 首页内容与平台公告配置；
- 平台数据、系统配置和审计日志。

### 3.4 业务域

1. 身份域：用户、游戏账号、角色、认证和权限；
2. 游戏资料域：现实球员、球员卡、卡包、属性和技能；
3. 阵容域：阵容、阵型、首发、替补和赛事快照；
4. 战队域：战队、成员、申请、邀请和历史关系；
5. 赛事域：赛事、规则、报名、阶段、分组、轮次和赛程；
6. 比赛域：签到、比分、证据、结果版本和正式结果；
7. 数据域：积分榜、排名、战绩、处罚和荣誉；
8. 运营域：公告、通知、审核、举报、风控和审计。

### 3.5 V1.0 不做

- 自动读取游戏官方比赛数据；
- 小程序内直播推流和大型视频托管；
- 内置即时聊天；
- 电竞竞猜、现金奖金托管和模拟抽卡付费；
- AI 自动识别比赛录像或截图；
- 跨游戏赛事；
- 完整内容社区；
- 专业级高级比赛数据分析；
- 双败淘汰、瑞士轮等复杂赛制；
- 多语言与多地区运营。

## 4. 用户角色与权限

### 4.1 权限模型

采用 RBAC 角色权限与资源作用域相结合的模型。每次受保护操作同时判断：

1. 用户是否登录且账号正常；
2. 用户拥有什么角色；
3. 角色作用于全平台、组织、赛事还是战队；
4. 当前资源是否属于该作用域；
5. 当前业务状态是否允许操作；
6. 操作是否需要更高角色复核。

同一用户可以同时是 A 战队队长、B 赛事参赛者和 C 赛事裁判。

### 4.2 角色定义

#### 游客

可浏览公开球员、卡包、赛事、赛程、积分榜、战队和玩家主页；不能收藏、报名、上报结果或申诉。

#### 注册用户

可维护资料、收藏球员、创建阵容、申请或创建战队、关注赛事、接收站内通知。未完善游戏账号前不得正式报名。

#### 认证玩家

可报名、提交赛事阵容、签到、上报及确认结果、发起申诉，并获得排名、战绩和荣誉。V1.0 的认证主要指资料完整性认证。

#### 战队成员

可查看队内公告与赛程、响应出战邀请、退出战队和查看个人战队数据。

#### 战队管理员

可审核申请、邀请成员、管理公告、协助报名和提交出战名单；移除成员和退赛等能力由队长授权。

#### 战队队长

可管理战队资料、成员和角色，代表战队报名、提交名单、处理比赛与申诉，以及转让或解散战队。

#### 认证主办方

可创建、复制和提交公开赛事，管理主办方团队。普通用户只允许创建非公开测试赛事。

#### 赛事负责人

对指定赛事拥有最高业务权限，可发布、暂停、取消赛事，管理工作人员、赛程、结果、申诉和归档。

#### 赛事管理员

可审核报名、维护名单、生成赛程、代录结果、催办和发布普通公告；默认无权删除赛事或对重大申诉终审。

#### 裁判

仅能处理被指派的赛事或比赛，可查看规则与证据、要求补充材料、提出意见或作出授权范围内的裁定。

#### 内容编辑

负责球员、卡片、卡包、基础字典、资讯和数据纠错，不参与赛事裁定。

#### 平台运营

负责主办方与公开赛事审核、举报、违规、推荐位、平台公告和运营数据。

#### 超级管理员

负责平台人员、权限、系统配置、安全事件和完整审计；人数应严格限制并启用二次验证。

### 4.3 权限矩阵

`允许`表示默认允许；`范围`表示仅限本人、所属战队或授权赛事；`审批`表示需更高权限批准。

|---|---|---|---|---|---|---|
| 编辑个人资料 | 允许 | 允许 | 允许 | 允许 | 允许 | 允许 |
| 管理战队成员 | — | 范围 | — | — | — | — |
| 代表战队报名 | — | 范围 | — | — | — | — |
| 创建赛事草稿 | 申请后 | 申请后 | 范围 | — | 允许 | 允许 |
| 发布公开赛事 | — | — | 审批 | — | 审批 | 审核 |
| 审核报名 | — | — | 范围 | — | 范围 | 特殊介入 |
| 生成或调整赛程 | 申请 | 申请 | 范围 | 建议 | 范围 | 特殊介入 |
| 上报本人比赛 | 范围 | 范围 | 代录 | 记录 | 代录 | — |
| 确认对手结果 | 范围 | 范围 | — | — | — | — |

### 4.4 高风险操作

以下操作必须二次确认并写入审计日志：

- 解散战队、转让队长；
- 取消或暂停已发布赛事；
- 报名截止后新增正式参赛者；
- 发布后变更规则或赛程；
- 修改已生效比赛结果；
- 扣分、禁赛、取消资格；
- 重算并发布积分榜；
- 封禁用户或暂停主办方权限。

## 5. 完整平台功能架构

### 5.1 玩家小程序

#### 首页

- 登录状态与全局搜索；
- 下一场比赛、待确认结果、待补充报名；
- 热门及正在报名赛事；
- 热门卡包、最新球员；
- 平台公告和常用入口。

#### 球员库

- 中英文名搜索和模糊搜索；
- 按位置、总评、卡片类型、卡包、俱乐部、国籍、技能、惯用脚筛选；
- 卡包列表与详情；
- 球员卡详情、属性、技能、风格、状态和同名卡；
- 收藏、对比、加入阵容、分享和数据纠错；
- 热门球员和最近浏览。

#### 阵容中心

- 创建、复制、删除和分享阵容；
- 选择阵型、首发、替补、队长和场上位置；
- 位置及赛事规则校验；
- 保存赛事阵容快照。

#### 战队中心

- 创建、搜索和加入战队；
- 战队主页、成员、公告、赛程、数据和荣誉；
- 入队申请、邀请、角色和成员状态；
- 战队赛事报名、名单和出战安排；
- 赛季工资概览、名单工资和单场阵容工资校验。

#### 赛事中心

- 全部赛事、我的赛事、搜索与筛选；
- 赛事详情、规则、公告、参赛方、赛程、积分榜、淘汰图和数据榜；
- 个人或战队报名、资料补充、撤回和候补；
- 比赛签到、结果上报、确认、拒绝、延期和申诉；
- 获奖名单和赛事荣誉。

#### 消息中心

- 报名、赛程、比赛、结果、申诉、战队、公告和系统通知；
- 已读状态；
- 微信订阅消息授权；
- 从消息跳转关联业务页面。

#### 我的

- 玩家资料、游戏账号、收藏、阵容、战队、赛事、比赛、战绩、荣誉、申诉；
- 主办方入口；
- 设置、隐私、帮助、反馈和账号注销。

### 5.2 主办方后台

- 组织工作台、组织资料、成员和权限；
- 赛事列表、创建、复制、归档；
- 基本资料、报名、赛制、积分、比赛、证据、申诉和奖项设置；
- 报名审核、候补、补位、名单锁定和导入导出；
- 分组、种子、抽签、自动赛程和冲突检测；
- 比赛列表、签到、延期、代录、修正、弃权和裁判指派；
- 申诉证据时间线、裁判意见、裁定和复核；
- 积分榜、榜单、处罚、重算和版本；
- 工资版本选择、两层工资帽、赛事覆盖、豁免和异常名单；
- 公告、定向通知和发送记录；
- 工作人员、数据范围和操作日志；
- 比赛完成率、弃权率、争议率和赛事进度。

### 5.3 平台后台

- 用户查询、账号状态、违规、封禁、注销与数据导出；
- 主办方认证、风险等级和权限暂停；
- 球员、球员卡、卡包、俱乐部、国家、位置、技能和风格管理；
- 平台球员卡工资、工资版本、批量调价和发布；
- 批量导入、重复检测、数据版本和纠错审核；
- 赛事审核、推荐、风险处置、强制暂停和下架；
- Banner、公告、帮助、协议和敏感词；
- 用户、赛事、转化、留存和资源用量分析；
- 后台人员、角色权限、系统配置、登录日志和审计日志。

## 8. 赛事生命周期与状态机

### 8.1 赛事状态

```text
草稿 → 待审核 → 报名中 → 报名截止 → 进行中 → 已结束 → 已归档
                   ↓           ↓
                 已暂停       已取消
```

#### 草稿

主办方填写基本资料、时间、资格、赛制、积分、比赛、申诉和奖项规则。系统执行必填、时间和规则冲突检查。

#### 待审核

平台审核主办方身份、内容、奖项或收费信息、规则完整性及是否冒用官方名义。审核结果为通过、驳回、要求补充或暂停。审核通过后由主办方确认发布。

#### 报名中

玩家接受规则，选择游戏账号，填写资料并提交阵容。系统检查资格、重复报名、人数、区服、平台、阵容和禁赛状态。主办方可通过、驳回、要求补充或列入候补。

#### 报名截止

停止普通报名，完成待审核、候补和退赛处理，分配编号与种子，锁定正式名单及赛事阵容。

#### 进行中

生成并发布赛程，处理提醒、签到、结果、超时、延期、申诉、裁定、积分和晋级。

#### 已结束

所有必要比赛已生效或裁定，影响名次的申诉已关闭，最终排名及奖项已确定。

#### 已归档

赛事默认只读，仅允许查看、分享、导出、受控数据修正和平台投诉。

### 8.2 报名状态

```text
草稿 → 已提交 → 待审核 → 已通过
                    ↓          ↓
                  待补充     已退赛
                    ↓
                  已驳回
```

报名资料在关键字段修改后可自动回到待审核状态。

### 8.3 比赛状态

```text
待排期 → 待比赛 → 已签到 → 比赛中 → 待上报 → 待对方确认 → 已生效
                                          ↓              ↓
                                        有争议 ← 对方拒绝
                                          ↓
                                      裁判处理中
                                          ↓
                              已裁定 / 重赛 / 取消
```

只有已生效或已裁定的正式结果参与积分和晋级。

## 9. 报名、赛程与比赛规则

### 9.1 报名字段

#### 个人赛

- 玩家、游戏账号、平台、区服、游戏昵称和 UID；
- 联系方式、地区、赛事阵容；
- 自定义问卷、附件和规则同意记录。

#### 战队赛

- 战队、队长、联系方式；
- 正式名单、替补名单及各自游戏账号；
- 战队赛事阵容、Logo、自定义问卷和规则同意记录。

### 9.2 重复报名

默认规则：同一用户和同一游戏账号在同一赛事中只能属于一个正式参赛方。赛事可以配置同一俱乐部是否允许多支队伍。

### 9.3 名单变更

- 报名截止前：用户可撤回并重提，队长可调整名单；
- 名单锁定后：提交申请、主办方审核、记录原因并通知相关人员；
- 赛事进行中：默认只因退赛、封禁或不可抗力允许替换。

### 9.4 排期方式

V1.0 支持：

- 固定时间：主办方指定；
- 时间窗口：双方在规定区间内自行协商。

延期申请包含原时间、新时间、原因、对方意见和可选证据。双方同意且不超轮次截止时间时可自动通过，否则管理员审批。

### 9.5 签到

赛事配置签到窗口。签到是判罚证据之一，不直接等同比赛结果。单方或双方未签到均进入管理员处理，不默认自动判负。

### 9.6 结果上报

V1.0 必填：

- 比分；
- 是否加时及点球；
- 对局完成时间；
- 至少一张结果截图；
- 可选备注。

流程：

1. 一方上报、对方确认：结果生效；
2. 双方独立上报且一致：可自动生效；
3. 双方上报不一致：冻结并进入争议；
4. 一方上报、对方超时：默认转管理员，不直接自动确认；
5. 管理员代录：必须填写原因并引用证据，通知双方并提供异议期。

### 9.7 结果不可覆盖

每次上报、修正或裁定均生成独立版本。正式结果只指向当前生效版本，旧版本永久保留。

## 10. 积分、排名与晋级

### 10.1 默认积分

- 胜：3 分；
- 平：1 分；
- 负：0 分；
- 弃权负：0 分；
- 双方弃权：双方 0 分。

赛事允许在开始前配置其他积分值。

### 10.2 默认同分顺序

1. 总积分；
2. 相互比赛积分；
3. 相互比赛净胜球；
4. 总净胜球；
5. 总进球数；
6. 胜场数；
7. 公平竞赛分；
8. 抽签或附加赛。

赛事开始后不得直接修改排序规则。

### 10.3 弃权与处罚

默认弃权比分为 0:3，并标记为判罚比分。系统分别保存实际比分、官方比分和判罚类型。判罚比分默认不计入射手等个人数据。

扣分记录必须包含对象、分值、原因、规则依据、操作者、生效时间和申诉状态。扣分不改变比赛胜平负统计。

### 10.4 积分榜版本

比赛生效、比赛修正、处罚生效或撤销、合法规则调整均触发重算。每次重算生成快照和版本号。重复触发不得重复累计。

### 10.5 淘汰赛

平局处理可配置加时、点球、重赛或多回合总比分。晋级只由正式结果触发。修改上一轮结果且下一轮已开始时，系统必须阻止静默修改并提示连锁影响。

## 11. 申诉与仲裁

### 11.1 可申诉事项

- 比分不一致；
- 未到场或恶意拖延；
- 网络中断；
- 使用违规球员或非法阵容；
- 冒名参赛、代打或其他违规；
- 不当言论；
- 管理员处理错误。

### 11.2 申诉状态

```text
草稿 → 已提交 → 待受理 → 调查中 → 待裁定 → 已裁定 → 已关闭
                         ↓
                       待补充
```

特殊状态：已撤回、不予受理、平台复核中。

### 11.3 证据

支持申诉类型、事实描述、期望处理、截图、外部录像链接、聊天记录和发生时间。系统保留提交人、提交时间和文件摘要。

### 11.4 裁定

- 维持原结果；
- 修正比分；
- 判定单方或双方弃权；
- 安排重赛；
- 警告、扣分、赛事内禁赛或取消资格；
- 移交平台处理。

### 11.5 利益冲突

裁判属于比赛任一方、所属战队、曾参与结果录入或管理相关组织时不得处理。系统提示冲突并要求重新指派。

### 11.6 两级处理

1. 赛事内部裁定；
2. 平台复核。

平台仅复核主办方明显违背公开规则、拒绝处理、全平台处罚、收费或其他严重违规，不替代普通比分仲裁。

## 12. 工资帽系统

### 12.1 目标与定义

工资帽用于限制赛事中的球员卡预算，不涉及真实工资或货币。系统采用“平台基础工资 + 赛事覆盖”的混合模式，并同时校验：

- 赛季报名总名单工资帽：正式、替补和预备名单的工资总和；
- 单场出战阵容工资帽：该场首发和比赛替补的工资总和。

单场阵容只能从已锁定的赛季名单选择球员。

### 12.2 工资计算优先级

由高到低依次为：

1. 赛事对具体球员卡设置的工资；
2. 赛事对卡片类型设置的调整规则；
3. 平台为具体球员卡维护的基础工资；
4. 平台依据满级总评计算的兜底工资。

同一现实球员的不同球员卡可以拥有不同工资。界面必须展示平台工资、赛事调整、最终工资和调整原因。

### 12.3 平台工资版本

平台内容编辑可以单张设置、批量导入、按总评生成和批量调价。每次正式发布生成不可变工资版本，可查看历史并回滚到历史版本生成新的发布版本。

赛事在报名开始时绑定工资版本；名单锁定后同时锁定工资与规则快照。赛事进行中调价默认只影响下一阶段或下一赛季。强制影响当前阶段时必须产生规则版本、填写原因、通知参赛方并提供调整窗口。

### 12.4 赛事覆盖与豁免

主办方可以：

- 设置赛季名单与单场阵容工资帽；
- 设置最低工资；
- 按卡片类型加减工资；
- 覆盖具体球员卡工资；
- 禁用特定球员卡；
- 设置同名球员与高工资球员数量限制；
- 配置青年球员、基础卡、门将、本队球员或伤病替换等结构化减免。

具体球员覆盖高于卡片类型调整。所有豁免必须结构化配置，不能只存在于规则正文。

### 12.5 名单流程

```text
队长选择球员卡 → 实时计算总工资 → 展示已用、剩余和超额
→ 校验人数、重复球员和工资帽 → 提交 → 审核
→ 锁定名单、工资版本和每张卡的当时工资
```

超过赛季工资帽时禁止提交，并标出导致超额的球员及需要减少的金额。

### 12.6 单场阵容流程

```text
从赛季名单选择球员 → 设置首发和替补 → 实时计算单场工资
→ 校验人数、位置和工资帽 → 提交并锁定 → 保存比赛阵容快照
```

超过单场工资帽、使用未注册球员或违反数量限制时禁止提交。开赛后不能由参赛方自行替换；管理员代改必须填写原因并保留修改前后记录。

### 12.7 异常与处罚

- 锁定后因管理操作导致超帽：名单标记工资异常，暂停提交新阵容，通知队长和管理员；
- 赛后发现超帽：通过正式申诉或裁定流程处理，可配置警告、判负、扣分、重赛、取消球员或战队资格；
- 处罚不能静默修改比赛或积分。

### 12.8 页面与后台能力

战队端新增工资概览、名单编辑器和单场阵容编辑器，展示上限、已用、剩余、利用率、工资来源和异常。

主办方后台支持启停工资帽、设置两层上限、选择平台工资版本、配置覆盖与豁免、查看各队工资分布、导入导出覆盖值和处理异常名单。

平台后台支持工资版本、批量计算、人工修正、发布、历史和回滚。

### 12.9 权限

| 操作 | 队长 | 赛事管理员 | 赛事负责人 | 平台内容编辑 |
|---|---|---|---|---|
| 查看赛事工资 | 允许 | 允许 | 允许 | 允许 |
| 编辑战队名单 | 本队 | 代操作 | 代操作 | — |
| 设置赛事工资帽 | — | 草稿阶段 | 允许 | — |
| 覆盖赛事球员工资 | — | 需授权 | 允许 | — |
| 修改平台基础工资 | — | — | — | 允许 |
| 发布平台工资版本 | — | — | — | 高级权限 |
| 强制调整锁定名单 | — | 申请 | 允许 | — |

### 12.10 验收标准

- 每张可参赛球员卡都有可计算工资；
- 赛事覆盖高于平台工资；
- 名单和单场阵容实时显示已用及剩余额度；
- 超过任一工资帽均不能提交；
- 单场阵容不能使用未注册球员；
- 锁定后保存规则、工资版本和每张卡的工资快照；
- 后续调价不改变历史比赛；
- 影响当前赛事的调价产生规则版本和通知；
- 管理员代改保留前后数据和原因；
- 处罚通过正式裁定执行。

## 13. 通知与异常处理

### 13.1 通知渠道

1. 站内消息：所有重要状态必须生成；
2. 微信订阅消息：用户授权后发送；
3. 主办方群通知：作为系统外补充。

重要业务不得只依赖微信订阅消息。

### 13.2 通知事件

- 报名提交、通过、驳回或待补充；
- 名单锁定、赛程发布或变化；
- 比赛即将开始；
- 对手提交结果、结果待确认；
- 申诉受理、补充证据和裁定；
- 晋级、淘汰和获奖；
- 赛事暂停、取消或规则变更。

### 13.3 异常默认处理

| 异常 | 默认处理 |
|---|---|
| 一方未签到 | 进入管理员判定，不自动判负 |
| 双方未签到 | 标记异常，等待管理员处理 |
| 一方未上报 | 提醒双方，超时转管理员 |
| 双方比分不一致 | 冻结结果，进入争议流程 |
| 截图模糊 | 要求补充证据 |
| 比赛中断 | 依据完成时间和规则续赛或重赛 |
| 玩家退赛 | 后续比赛按赛事规则判负或取消 |
| 战队解散 | 进行中赛事内冻结解散操作 |
| 赛事取消 | 通知参赛方并保留记录 |
| 管理员误改 | 通过结果版本修正，不删除原记录 |
| 积分异常 | 暂停榜单发布，修复后生成新版本 |
| 微信通知失败 | 保留站内消息并提供重发 |
| 重复提交 | 使用幂等键阻止重复业务记录 |

### 14.3 P1 争取完成

- 卡包、收藏和简版阵容；
- 战队公告、出战确认和成员表现统计；
- 微信订阅消息；
- 赛事复制、候补、补位和延期；
- 数据导入导出、分享海报；
- 主办方认证和球员纠错。

### 14.4 P2 后续版本

- 球员详细对比、自动加点；
- 约战、社区和高级数据；
- 射手榜、助攻榜；
- 双败淘汰和瑞士轮；
- 图片自动识别、直播与回放；
- 会员、付费赛事和多语言。

### 14.5 首版限制

- 一项赛事只选择一个平台与区服组合；
- 允许单一赛制或“小组循环 + 单败淘汰”；
- 一个用户在同一赛事只代表一个正式参赛方；
- 证据支持图片和外部视频链接，不上传大型视频；
- 排名由规则计算，不允许管理员直接拖拽；
- 改变名次必须通过比赛修正或处罚；
- 不处理支付、奖金托管和退款；
- 不提供即时私聊；
- 不自动识别比分截图；
- 球员数据由后台维护。

## 15. 核心需求与验收标准

### FR-001 微信登录与玩家建档

需求：允许游客浏览；受限行为触发登录；首次登录创建唯一用户；用户可添加多个游戏账号；报名必须选择符合赛事要求的游戏账号。

验收：

- 拒绝授权后仍可浏览公开内容；
- 重复登录不创建重复用户；
- 被封禁用户只能访问申诉与帮助；
- 重复绑定游戏账号可被识别或进入审核；
- 删除游戏账号前检查进行中赛事关联。

### FR-002 球员搜索

需求：支持中英文搜索，按位置、卡片类型、卡包和总评筛选，支持综合、总评和日期排序，分页加载。

验收：

- 中英文关键字命中正确球员；
- 多条件执行 AND 逻辑；
- 翻页不重复、不漏项；
- 数据发布后搜索结果同步更新；
- 普通查询在正常网络下目标响应时间小于 2 秒。

### FR-003 创建赛事

需求：支持草稿、个人赛与战队赛、循环赛、单败淘汰、组合赛制、积分与排名配置、时间与申诉配置、提交审核前校验。

验收：

- 未完成草稿可保存；
- 时间关系不合法时不能提交；
- 核心规则缺失时不能公开审核；
- 发布后小程序与后台资料一致；
- 赛事开始后禁止直接变更核心赛制。

### FR-004 赛事报名

需求：根据赛事类型展示表单，校验平台、区服、资格和人数，支持草稿、补充材料，并记录用户接受的规则版本。

验收：

- 不符合资格时显示明确原因；
- 重复提交不产生重复报名；
- 截止后普通用户不能提交；
- 影响已报名用户的规则变更要求重新确认；
- 审核结果生成通知；
- 完整保留状态历史。

### FR-005 自动生成赛程

需求：循环赛使用标准轮转算法，淘汰赛支持轮空与种子，发布前可调整，生成操作幂等。

验收：

- 单循环任意两方只相遇一次；
- 双循环双方各一次主客场；
- 奇数参赛方每轮最多一方轮空；
- 非 2 的幂参赛数可正确补轮空；
- 同一参赛方不在同一时间安排两场；
- 未发布的重新生成不污染正式赛程；
- 发布后重新生成需要明确确认。

### FR-006 比赛结果

需求：仅比赛双方和授权管理员可提交；结果包含比分与证据；对方可确认或拒绝；管理员可代录；正式结果保存版本历史。

验收：

- 非参赛方无法提交；
- 负数比分或非法点球比分无法提交；
- 双方一致时按规则自动生效；
- 双方不一致时不得更新积分；
- 已生效结果不能直接删除或覆盖；
- 每次修正可查看人员、时间和原因。

### FR-007 积分榜

需求：只计算正式结果，使用赛事积分与同分规则，支持处罚扣分、重新计算和版本记录。

验收：

- 结果生效后自动更新；
- 结果撤销后正确回退；
- 扣分不改变比赛统计；
- 同分排序符合规则；
- 任意排名可追溯到比赛和处罚；
- 重复计算不重复累计。

### FR-008 申诉与裁定

需求：相关参赛方在时限内发起，裁判可请求补证，裁定可以修正正式结果并触发积分及晋级重算。

验收：

- 过期申诉只能申请特别受理；
- 利益冲突裁判不能受理；
- 双方可查看允许公开的证据和时间线；
- 裁定不能绕过审计；
- 连锁影响必须明确提示；
- 下一轮已完成时不能静默更改上一轮晋级者。

### FR-009 工资帽

需求：平台为具体球员卡发布版本化基础工资；赛事可以覆盖具体卡片或卡片类型，配置结构化豁免，并同时限制赛季名单和单场阵容工资。

验收：

- 每张可参赛球员卡均能得到确定的最终工资；
- 赛事具体卡覆盖、类型调整、平台基础工资和兜底工资按既定优先级计算；
- 超过赛季名单或单场阵容工资帽时禁止提交；
- 单场阵容不能使用未注册球员；
- 名单和比赛阵容保存当时工资、工资版本和规则快照；
- 后续工资发布不改变历史名单和比赛；
- 管理员代改和强制调价写入审计并通知受影响参赛方；
- 工资违规处罚只能通过正式裁定生效。

## 16. 核心数据模型

所有核心表包含 `id`、创建及更新时间、创建及更新人、并发版本号；需要软删除的业务表包含 `deleted_at`。正式比赛、裁定、处罚和审计数据不得物理删除。

### 16.1 用户与权限

- `users`：微信标识、昵称、头像、手机号、地区、状态、协议与授权；
- `game_accounts`：用户、平台、区服、昵称、UID、认证状态；
- `roles`、`permissions`、`role_permissions`：角色与权限；
- `user_role_bindings`：用户、角色、作用域、有效期和授权人；
- `user_restrictions`：限制类型、范围、原因和有效期。

### 16.2 游戏资料

- `football_players`：现实足球运动员基础资料；
- `player_cards`：游戏版本、卡片类型、卡包、位置、总评和风格；
- `player_card_attributes`：初始和满级属性；
- `skills`、`player_card_skills`：技能字典及关联；
- `card_packs`、`card_pack_items`：卡包与卡片；
- `player_favorites`：用户收藏；
- `data_corrections`：纠错建议与审核。

### 16.3 阵容

- `squads`：用户阵容、阵型、公开状态；
- `squad_slots`：球员卡、位置、首发替补与队长；
- `competition_squad_submissions`：赛事报名时的阵容快照及锁定状态。

### 16.4 战队

- `teams`：名称、Logo、地区、平台、队长和状态；
- `team_memberships`：成员、游戏账号、角色、加入离开时间；
- `team_applications`、`team_invitations`：申请和邀请；
- `team_announcements`：队内公告。

### 16.5 主办方

- `organizer_organizations`：组织资料、认证和风险状态；
- `organizer_memberships`：组织成员和角色；
- `organizer_verifications`：申请资料与审核。

### 16.6 赛事

- `competitions`：主办方、类型、平台、区服、人数、时间、状态和当前规则；
- `competition_rules`：规则版本、结构化配置、正文、生效时间和修改原因；
- `competition_stages`：小组赛或淘汰赛等阶段；
- `competition_registrations`：报名对象、状态、资料和接受的规则版本；
- `registration_members`：战队报名成员；
- `competition_participants`：通过审核后的正式参赛方；
- `competition_groups`：分组；
- `competition_rounds`：轮次及时间窗口。

报名记录与正式参赛方分离，避免候补和驳回数据进入赛程。

### 16.7 比赛

- `matches`：阶段、轮次、双方、时间、状态和当前正式结果；
- `match_checkins`：签到记录；
- `match_result_submissions`：每一次独立结果上报；
- `match_evidence`：结果或申诉证据；
- `official_match_results`：当前正式结果及版本；
- `match_result_revisions`：正式结果修正链。

### 16.8 申诉与处罚

- `appeals`：申诉类型、描述、状态和处理人；
- `appeal_statements`：双方陈述；
- `appeal_assignments`：裁判指派和利益冲突检查；
- `appeal_decisions`：裁定、规则依据和结果调整；
- `penalties`：处罚对象、类型、扣分和有效期。

### 16.9 积分与荣誉

- `standings_snapshots`：积分榜版本；
- `standings_rows`：场次、胜平负、进失球、积分、处罚和排名；
- `honors`、`user_honors`、`team_honors`：荣誉定义及归属。

### 16.10 通知与审计

- `notifications`：站内通知；
- `notification_deliveries`：微信等渠道发送记录；
- `audit_logs`：操作者、角色、作用域、对象、修改前后、原因、IP 和设备。

### 16.11 工资帽

- `player_card_salary_versions`：平台工资版本、状态、生效时间和发布人；
- `player_card_salaries`：球员卡、基础工资、计算来源和人工修正；
- `competition_salary_cap_rules`：赛事绑定版本、两层上限、最低工资和生效阶段；
- `competition_salary_overrides`：具体卡片或卡片类型的调整和原因；
- `competition_salary_exemptions`：豁免类型、对象、比例、金额和数量限制；
- `competition_roster_players`：报名名单中球员卡、当时工资、来源、版本和锁定状态；
- `match_lineup_players`：比赛阵容中球员卡、首发替补、当时工资、豁免和阵容版本。

工资和规则快照必须随名单及比赛保存，历史数据不得按当前价格重新计算。

## 17. 技术架构

### 17.1 架构决策

V1.0 使用 CloudBase 混合架构，而不是小程序直接修改核心数据库：

```text
微信小程序 ─┐
             ├─ NestJS REST API（CloudBase 云托管）─ CloudBase MySQL
主办方后台 ─┤                         ├─ 云存储
平台后台 ───┘                         ├─ 云函数/异步任务
                                       └─ 微信登录与订阅消息
```

所有关键写入经由后端 API，执行权限、状态、事务、幂等和审计检查。

### 17.2 推荐技术

- 小程序：原生微信小程序 + TypeScript；
- Web：Vue 3 + TypeScript + Vite + Pinia；
- 后端：Node.js + NestJS + REST + OpenAPI；
- ORM：Prisma 或 TypeORM；
- 数据库：CloudBase MySQL；
- 部署：Docker + CloudBase 云托管；
- 文件：CloudBase 云存储；
- Web 托管：CloudBase 静态网站托管；
- 定时及异步任务：云函数或后台任务；
- Redis 与独立搜索服务：按验证后的性能需求再引入。

### 17.3 服务端模块

- Auth、Users、Players、Squads；
- Teams、Organizers；
- Competitions、Registrations、Scheduling；
- Matches、Appeals、Standings；
- Notifications、Admin、Audit。

V1.0 采用模块化单体，不拆微服务。

### 17.4 异步任务

- 报名、比赛和结果提醒；
- 截止时间处理；
- 确认超时；
- 积分榜重算；
- 图片处理；
- 批量导入导出；
- 赛事归档。

所有任务可重试，并使用业务幂等键防止重复影响。

### 17.5 环境

- 本地开发；
- 测试环境；
- 生产环境。

测试与生产的数据库、存储、微信配置、密钥和日志必须隔离。禁止使用生产数据直接覆盖测试环境。

### 17.6 可迁移性

- 使用标准 MySQL；
- 业务逻辑集中在独立 API；
- 后端容器化；
- 小程序和 Web 不直接依赖数据库表结构；
- 文件访问封装为存储服务；
- 避免将核心规则散落在客户端或大量独立云函数中。

## 18. 安全与非功能要求

### 18.1 身份与权限

- 服务端完成微信凭证交换并建立业务登录态；
- 后台采用扫码或受控账号登录；
- 敏感后台角色启用二次验证；
- 登录令牌支持过期与刷新；
- 客户端按钮可见性不能替代服务端鉴权。

### 18.2 文件安全

- 限制格式、大小和真实 MIME；
- 随机存储路径，禁止覆盖同名文件；
- 证据文件使用受控临时访问地址；
- 业务删除不立即清除审计证据；
- 外部链接校验协议和域名。

### 18.3 数据安全

- 数据库最小权限；
- 敏感字段加密；
- 密钥不进入代码仓库；
- 自动备份与定期逻辑导出；
- 执行恢复演练；
- 审计日志不可由普通管理员修改；
- 注销后按规则匿名化数据。

### 18.4 性能目标

- 普通 API P95 小于 800ms；
- 搜索 API P95 小于 1.5s；
- 主要页面可交互时间小于 2.5s；
- 积分榜在结果生效后 10 秒内更新；
- 列表统一分页，图片使用缩略图和懒加载。

### 18.5 可用性

- 月度目标 99.5%；
- 核心写入失败必须明确提示；
- 上报支持安全重试；
- 消息发送失败不回滚业务状态；
- 异步任务有失败告警和人工重试入口。

### 18.6 一致性

以下操作必须事务化或具备等效的一致性保证：

- 报名名额占用；
- 正式参赛者生成；
- 比赛结果生效；
- 淘汰赛晋级；
- 积分更新；
- 处罚生效；
- 角色授权。

### 18.7 并发和幂等

- 使用版本号避免管理员相互覆盖；
- 结果生效使用数据库事务；
- 报名临界名额使用锁或原子更新；
- 提交接口支持幂等键；
- 重复任务不得生成重复通知或积分。

### 18.8 可观测性

- API 错误和慢查询日志；
- 异步任务和消息发送日志；
- 管理员操作日志；
- 服务健康检查；
- 数据库、存储和预算用量告警；
- 异常比赛与积分重算告警。

- 品牌赛事；

- 多端和更多游戏；

## 21. 发布计划

### 内部开发版

- 完成账号、球员库和赛事基础模型；
- 使用测试数据验证权限和状态机。

### Alpha

- 仅内部成员和受邀主办方；
- 运行一项 8～16 人赛事；
- 重点验证报名、赛程、结果和积分。

### Beta

- 运行一项 32～64 人真实赛事；
- 开放战队能力；
- 验证通知、申诉、积分准确性和主办方工作量。

### 正式发布

- 支持 128 人个人赛和 32 支战队；
- 发布基础球员卡库；
- 开放主办方申请；
- 上线客服、备份和故障响应。

## 22. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 球员数据来源不稳定 | 球员库无法持续更新 | 建立后台导入、人工维护、来源和版本记录 |
| 游戏素材版权 | 卡面或 Logo 被投诉 | 明确非官方属性，评估授权，建立快速下架机制 |
| 赛事规则差异过大 | 配置系统失控 | V1.0 限定赛制模板，只开放必要配置 |
| 恶意或虚假上报 | 结果可信度下降 | 截图、版本、双方确认、裁判和处罚 |
| 主办方滥权 | 玩家信任下降 | 规则版本、修改留痕、平台复核 |
| 订阅消息限制 | 用户错过比赛 | 站内消息为主，微信消息为补充 |
| 赛事高峰并发 | 报名或积分异常 | 幂等、事务、队列和压力测试 |
| CloudBase 费用失控 | 超预算或停服 | 用量告警、预算监控、资源生命周期策略 |
| 平台绑定过深 | 迁移困难 | 标准 MySQL、自有 API、容器化 |
| MVP 范围膨胀 | 延期 | 冻结 P0，P1 按进度取舍 |
| 工资定价失衡或频繁变动 | 阵容趋同、名单突然违规 | 版本锁定、分布预览、当前阶段保护和调价窗口 |
| 申诉量过大 | 运营成本上升 | 证据规范、裁定模板、明确受理范围 |
| 个人信息泄露 | 合规和信任风险 | 最小收集、权限隔离、脱敏和注销机制 |

## 23. 待确认业务参数

以下参数不阻塞架构，但必须在对应模块开发前确定：

- 正式产品名称和视觉品牌；
- 首批支持的平台和区服；
- 球员数据来源、更新频率和版权策略；
- 游戏账号认证强度；
- 首批合作主办方和测试赛事规模；
- 默认结果确认时限和申诉时限；
- 是否允许收费赛事；
- 玩家联系方式的可见范围；
- 阵容提交是否进入首个公开版本；
- 主办方认证材料；
- 用户违规和封禁规则；
- 客服与平台复核的服务时限。
