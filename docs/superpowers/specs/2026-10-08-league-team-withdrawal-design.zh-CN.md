# 联赛球队永久退出与恢复设计

## 背景

联赛中的球队可能永久退赛。现有 `LeagueTeam.status` 已包含 `ACTIVE`、`ARCHIVED` 和 `NEEDS_NUMBER`，API 也允许通过通用更新请求写入 `ACTIVE / ARCHIVED`，但后台没有明确的退出与恢复操作，列表、小程序入口和部分业务操作也没有统一按球队生命周期过滤。仅手工修改状态会造成球队仍在部分页面出现或仍可继续交易。

本功能把 `ARCHIVED` 明确定义为“已退出联赛”。退出只冻结球队的后续业务活动，不删除或改写已经形成的历史数据。

## 目标

- 联赛管理员可以在球队详情中将现役球队永久移出联赛，并填写原因。
- 已退出球队不再出现在后台默认球队列表、小程序“我的球队”及其他现役球队选择器中。
- 已退出球队不能继续报名、交易、调整阵容、提交身价或产生新的球队业务记录。
- 后台提供“已退出”列表，管理员可以查看并恢复球队。
- 已产生的赛季报名、比赛、赛程、积分榜、阵容和财务记录保持不变。
- 历史赛事继续显示退出球队，并以“已退赛”标识其当前生命周期状态。

## 非目标

- 不支持“仅退出当前赛季”。
- 不物理删除球队或其关联记录。
- 不释放球队编号、队壳、球员归属或历史资产给其他球队。
- 不自动取消、判负或重排已经创建的比赛和赛程。
- 不自动结算球队余额、球员或工资。
- 不允许球队负责人自行永久退出，首版只允许有权限的后台管理员操作。

## 数据模型与状态语义

继续使用现有字段，不新增数据库迁移：

```text
LeagueTeam.status = ACTIVE   当前参与联赛并允许业务操作
LeagueTeam.status = ARCHIVED 已永久退出联赛，仅保留历史和后台恢复入口
LeagueTeam.status = NEEDS_NUMBER 历史兼容状态，不改变现有语义
```

球队编号、`catalogTeamId`、阵容归属、账本和赛季记录在退出时全部保持原值。因此恢复不需要重建数据，也不会因为编号或队壳已被其他球队占用而失败。

退出原因和恢复原因保存在现有审计日志中，不新增 `withdrawn_at`、`withdrawal_reason` 等字段。`updated_at` 和 `version` 随状态变化正常更新。

## 管理操作

通用球队编辑接口不再承担生命周期变更。新增两个语义明确、幂等且受版本控制的管理员操作：

```text
POST /v1/admin/leagues/:leagueId/teams/:teamId/archive
POST /v1/admin/leagues/:leagueId/teams/:teamId/restore
```

请求包含：

```json
{
  "expectedVersion": 1,
  "reason": "球队主动退出联赛"
}
```

`reason` 去除首尾空白后必须为 1–512 个字符。两项操作均要求 `Idempotency-Key`，并在同一事务内锁定球队、检查联赛可见性和当前版本、更新状态、递增版本、写入审计日志。审计动作分别为：

- `league-team.archive`
- `league-team.restore`

重复提交同一幂等键返回第一次的结果。不同幂等键对已经处于目标状态的球队返回当前结果，不重复写审计记录。版本不匹配时继续使用现有 `VERSION_CONFLICT`。

退出仅允许从 `ACTIVE` 进入 `ARCHIVED`；恢复仅允许从 `ARCHIVED` 进入 `ACTIVE`。`NEEDS_NUMBER` 不参与这两个动作。

现有通用 `PATCH /teams/:teamId` 的请求契约移除 `status` 字段，防止绕过原因、审计和状态机直接修改生命周期。

## 可见性与操作权限

### 管理后台

球队列表增加状态筛选：

- “现役球队”：只返回 `ACTIVE`，作为默认页签。
- “已退出”：只返回 `ARCHIVED`，显示退出状态并允许进入只读详情和执行恢复。

`NEEDS_NUMBER` 保持现有兼容处理，不混入“已退出”；需要编号的记录仍在现有维护路径中处理。

后台可以读取已退出球队的基本资料及历史摘要，但不能对其执行队壳更换、队壳转让、阵容交易、工资重算、财务录入、身价提交等业务操作。上述入口在服务边界统一拒绝，并返回 `409 TEAM_ARCHIVED`。恢复操作是唯一允许修改已退出球队状态的入口。

### 小程序与用户接口

小程序“我的球队”、联赛当前球队列表和现役球队选择器只返回 `ACTIVE`。用户通过已知球队地址访问已退出球队时返回 404，避免继续进入业务页面。

用户报名、比赛报名、阵容交易、财务和身价等写操作必须在产生回执、审计、账本或领域写入前确认球队为 `ACTIVE`。已退出球队按资源不可用处理，不产生任何新记录。

### 历史赛事

已经形成的赛季报名、赛事参与者、赛程、比赛结果和积分榜不删除、不撤回、不重新计算。历史查询仍返回原有球队名称、快照和结果。

在 `CompetitionParticipantSummary` 和 `StandingsRowResponse` 增加 `teamLifecycleStatus: ACTIVE | ARCHIVED | null`。团队参赛者通过 `seasonEntry.leagueTeam.status` 派生该值；个人参赛者或没有球队关联的历史快照返回 `null`。赛程/比赛使用参与者摘要，积分榜使用积分行，因此两个入口都能对 `ARCHIVED` 显示“已退赛”。历史名称继续使用既有快照，不因球队退出而消失。

退出后不允许该球队新建赛事报名或进入新的赛季，但现有赛事的只读历史仍可查看。

## 后台交互

球队详情页对 `ACTIVE` 球队显示危险操作“退出联赛”。点击后打开确认框：

- 明确提示不会删除历史比赛、阵容和财务数据；
- 要求输入退出原因；
- 显示球队名称，避免误操作；
- 提交期间禁用重复点击。

`ARCHIVED` 球队详情只显示历史摘要和“恢复球队”。恢复同样要求原因和二次确认。成功后返回对应列表并刷新数据。

列表中的“状态”列同时展示阵容合规状态和球队生命周期状态，避免当前页面只显示“合规/超帽”而看不到球队已退出。

## 一致性与并发

- 所有生命周期变更使用 `expectedVersion`，状态更新使用 `updateMany` 同时匹配 `id`、`leagueId`、当前状态和版本。
- 可见性和状态检查必须发生在幂等回执回放、审计、账本及其他领域写入之前；恢复端点除外，它需要读取已退出球队。
- 退出与正在执行的球队交易竞争时，以数据库锁和版本检查决定唯一成功方，失败操作不得留下部分写入。
- 逻辑删除的联赛仍优先返回 404；不能通过球队恢复接口绕过联赛 `is_deleted`。

## 测试策略

1. 契约测试：退出/恢复请求必须包含合法版本和非空原因，通用更新请求拒绝 `status`。
2. 服务测试：退出将 `ACTIVE` 改为 `ARCHIVED`、递增版本并写一条审计；恢复执行相反变更。
3. 幂等与并发测试：重复键不重复写审计；错误版本和非法状态转换不修改数据。
4. 列表测试：后台默认列表只含现役球队，“已退出”列表只含归档球队；小程序和“我的球队”不包含归档球队。
5. 写入保护测试：归档球队不能报名、交易、调整阵容、录入财务或提交身价，且回执、审计、账本和领域表计数不变。
6. 历史测试：已存在的赛程、结果和积分榜仍返回该球队，并带“已退赛”展示状态。
7. 恢复测试：同一球队原编号、队壳、阵容和历史数据不变，恢复后重新进入现役列表并可继续业务操作。
8. UI 测试：确认框要求原因，现役/已退出页签正确切换，已退出球队没有业务编辑按钮且可以恢复。
9. 整仓运行 lint、typecheck、单元测试、E2E 和构建。

## 验收标准

- 管理员可以从球队详情永久退出并恢复球队，两项操作都有原因、版本控制和审计记录。
- 已退出球队不会出现在任何现役球队列表或小程序业务入口中，也不能产生新的球队业务数据。
- 已产生的历史赛事和业务记录完整保留；赛事页面对归档球队显示“已退赛”。
- 恢复后无需重建球队或关联数据，原编号、队壳、阵容、财务和历史继续可用。
- 不新增数据库字段，不物理删除或级联修改历史数据。
