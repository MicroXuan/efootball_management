# PESDATA 球员卡对账与发布设计

日期：2026-10-22

状态：用户已确认方向与“管理员看差异报告后一键发布”方式，待按实施计划执行

## 1. 目标与可承诺范围

系统每天读取 PESDATA 球员卡列表，识别新增、内容更新与来源下架；管理员查看差异报告后，一键发布所有已验证的有效变更。发布成功后，小程序公开球员库与本次**可信来源观察**的卡片编号集合对齐。同步任务成功不代表已发布；任务结束、差异待发布、发布中和已生效必须分别显示。

PESDATA 当前接入方式是按偏移量分页的列表及单卡详情，未提供项目可用的固定版本快照、稳定游标或变更通知。因此两次完整列表观察一致只能降低漏页、误下架风险，不能证明任意瞬间与实时官网绝对一致。界面和文档不得宣称实时或绝对一致。若站方以后提供正式变更流、快照版本或删除事件，应优先接入并替代观察式对账。

## 2. 身份与差异

- `sourceId + PESDATA playerId` 是卡片身份；`base_pes_id` 仅关联现实球员。相同来源卡片编号再次出现时更新原卡；新编号创建新卡；重复而未变化不创建卡或发布版本。
- 差异分类为 `ADDED`、`UPDATED`、`UNCHANGED`、`REMOVAL_CANDIDATE`、`REMOVAL_CONFIRMED`、`FAILED`。列表摘要变化触发详情读取；旧卡详情即使摘要不变，也要在受限速约束的滚动复核中周期性重读。
- 用业务字段的规范化内容计算更新校验值；不把同步时间、响应字段顺序或不影响展示与业务的瞬时元数据变化当成球员卡更新。保留原始详情校验值用于诊断。
- 来源列表中消失的卡不是自动删除。只有完整可信扫描、第二次相同编号集合、单卡详情明确为失效或经过可识别的确认性不存在结果，才能标记 `REMOVAL_CONFIRMED`；网络错误、协议错误、列表变化或模糊响应均停留在待确认状态。
- 对已下架卡重新出现，沿用原 `player_cards.id` 发布 `ACTIVE` 版本；不得创建重复卡。

## 3. 每日运行与可信扫描

每天由部署环境配置的定时入口创建一次 `INCREMENTAL` 对账运行；沿用现有分布式租约、暂停、继续、限速与失败重试。不得因多个 API 实例重复启动同一天的运行。执行时间、请求预算和超时由部署配置；初次全量导入验收前不自动启用。

1. 第一遍完整读取列表，保存每页来源报告的总数、偏移、返回条数、编号与列表摘要校验值。任何请求或协议失败、页重复、编号重复、总数在本遍变化、实际唯一编号数不等于来源总数，均标记扫描不可信，停止下架判定。
2. 第二遍从头完整读取列表，执行相同校验，并比较两遍编号集合及来源总数。若不同，任务报告“来源扫描期间变化”，不产出可发布的下架项；可在请求预算内重试，仍不一致则等待下次运行。
3. 对本地正式卡和可信来源清单作集合差。新卡和摘要变化卡获取详情；没有摘要变化的旧卡按最久未复核优先的滚动队列检查详情。失败卡只进入重试队列，不伪装为不存在。
4. 对仅在本地存在的卡执行独立详情复核。当前 `PesdataClient` 把 404 归类为协议错误，实施中必须区分确认性不存在与协议变更；不能把任意非 2xx 当作删除证据。无法确认的卡进入 `REMOVAL_CANDIDATE`，不进入一键发布。

为支持 50,000 张及任务恢复，扫描结果按 `runId + pass + externalId` 分块持久化到独立暂存表，在数据库内比较集合。完成后保留运行摘要和差异报告；原始暂存行按受控保留策略归档或清理，不让每天两遍扫描无限膨胀。任何清理先遵守仓库的数据安全约束。

## 4. 差异审核与原子发布

- 管理后台显示本次来源总数、本地有效卡数、新增、更新、确认下架、待确认、失败和不变数量；可以查看每项可读名称、来源编号及变化字段。
- 管理员点击“一键发布有效变更”，服务端重新验证运行完成且扫描可信、候选数据未过期、各批次状态可发布，再按受控批次发布。失败和 `REMOVAL_CANDIDATE` 自动排除，并在结果中明确计数。
- 既有 `PlayerImportPublisher` 保持批次原子性与幂等性。下架走同一发布/版本路径，将正式卡状态置 `INACTIVE` 并写一条新版本；绝不物理删除 `player_cards`、历史版本、已有持有或交易记录。若某批次失败，仅该批次不生效，报告精确失败并允许安全重试；不得报告“全量已生效”。
- 发布后的只读校验比较来源可信编号集合与本地公开 `ACTIVE` 编号集合；若有待确认或失败，报告仍存在差异，不把同步完成或部分发布标成“完全一致”。

## 5. 性能与运行边界

- 普通每日运行完整扫描列表，但只请求新增、摘要变化、失败重试和滚动复核对象的详情；不每天请求全部卡片详情。滚动复核预算配置为在来源允许的速率内覆盖全库，并显示“最近一次详情复核时间”。
- 若业务要求**每天所有能力值和图片也与官网完全一致**，必须获得站方可信的详情变更标记、变更流或足够的全量请求预算；仅靠列表摘要及有限滚动复核不能保证这一点。
- 首轮上线不自动发布；用户已选择管理员查看差异报告后一键发布。定时扫描完成到管理员发布之间属于“待生效”状态。
- 来源图片 URL 可随站方变化或失效；图片是否镜像到自有存储是独立运维决策，不能把 URL 字符串相同当作图片内容一定相同。

## 6. 迁移、回归与验收

- 先在本机隔离 `verify` 数据库测试双遍扫描、集合差、更新、下架、恢复、失败与幂等；所有 API/e2e 测试命令显式指定本机 `DATABASE_URL`，不得继承共享 `.env`。
- 新表/字段发布前只读核对目标环境 `pnpm db:status`，先迁移、再部署新 API 和后台；不得在共享数据库运行开发态迁移或测试数据清理。
- 用模拟 50,000 张卡验证分片扫描内存、暂存表增量、发布批次数量和页面响应。来源列表在扫描中插入、删除、重排、重复或失败时不得误下架。
- 回归后台联赛球队“现役球队 / 已退出”、球队详情、小程序“我的联赛”、球员库、卡片详情、已持有卡、收藏和交易历史；在目标环境核对真实 API 与前端解析。无法验收的环境范围必须明示。
