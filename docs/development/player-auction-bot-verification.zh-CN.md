# 微信群球员拍卖验收手册

本文用于开发环境自动验收和专用 Windows 电脑上的真实微信群验收。拍卖的权威状态在 API/MySQL；Windows Bridge 只负责读取白名单群消息和串行发送。个人微信自动化不存在零风控保证，必须使用专用机器人账号、固定微信版本、低频白名单群和失败即停策略。

## 1. 上线边界

- 一个微信群只能绑定一个联赛，一个联赛可以绑定多个微信群；后台为每个群独立选择“赛程查询”“球员拍卖”或两者。
- 只有已启用且勾选“球员拍卖”的群可创建或准备拍卖；存在未结束批次时，不允许停用该群或移除其拍卖能力。
- 用户在小程序获得 5 分钟一次性验证码，私聊机器人发送 `绑定 123456`；出价和管理命令都依赖该绑定。
- 只有具备 `league.auction.manage` 权限的已绑定用户能发送管理命令。
- 群成员出价只发送纯数字，例如 `120`。有效回复必须为 `【球队名称】出价有效：⭐120⭐，倒计时重置为 30 秒。`
- 每名球员有出价或无人出价结束后，系统都会自动开始下一位；最后一位结束后自动完成批次，不再使用日常 `下一位` 命令。
- 审核只记录结果，不扣款、不写财务流水、不创建阵容交易，也不改变球员归属。
- Bridge 默认 `send_enabled = false`。完成本手册前不得打开真实发送。

## 2. 自动化验收

先启动 MySQL、应用迁移和种子数据：

```bash
pnpm dev:db
pnpm db:migrate
pnpm --filter @efm/api exec prisma db seed
pnpm --filter @efm/api test:e2e -- player-auctions.e2e-spec.ts --runInBand
pnpm verify
pnpm db:status
git diff --check
```

`player-auctions.e2e-spec.ts` 模拟两个已绑定球队和三名不同价格的球员，验证低价拒绝、有效出价、30 秒重置、精确倒计时、成交与流拍自动推进、后台审核、重复消息、心跳丢失后的恢复，以及审核前后财务/阵容/归属不变。

## 3. Windows 测试群准备

先完成 [Windows 微信 Bridge 部署与验收](../deployment/windows-wechat-bridge.zh-CN.md)，保持 `send_enabled = false`：

1. 微信版本固定为已经在目标电脑验证的 `4.1.15.50`，并在 `bridge.toml` 明确设置 `expected_wechat_version = "4.1.15.50"`；机器人账号只加入授权测试群。
2. `doctor` 确认微信已登录、桌面未锁定、数据库可读、API 鉴权正常。
3. 管理后台启用设备，把拍卖测试群绑定到目标联赛并勾选“球员拍卖”；同一联赛可另绑赛程群，但确认没有第二个联赛占用同一群。
4. 至少准备两名小程序用户、两支当前联赛的有效球队，并分别完成私聊验证码绑定。
5. 给一名测试用户授予联赛拍卖管理权限。
6. 在后台“球员拍卖”创建三名球员的批次，分别设置不同的起拍价和最低加价，保存并准备。
7. 先在 `--dry-send` 下确认入站可读、outbox 可见且不会操作微信，再短时开启真实发送。

## 4. 正常拍卖清单

逐项记录时间、批次 ID、球员、发送者、Bridge Git 提交、微信版本和结果；不要记录设备令牌或无关聊天正文。

- [ ] 管理员发送 `开始拍卖`，第一位球员进入 `ACTIVE`，截止时间约为服务端数据库时间后 30 秒。
- [ ] 低于起拍价的数字被拒绝，并在出价审计中记录具体原因。
- [ ] 第一支球队发送合法纯数字，群回复为 `【球队名称】出价有效：⭐价格⭐，倒计时重置为 30 秒。`
- [ ] 第二支球队未达到“当前价 + 最低加价”时被拒绝；达到后成为新最高价并再次重置 30 秒。
- [ ] 群内倒计时只出现 `20、10、3、2、1`，绝不发送 `30、5、4、0`；拥塞时允许跳过提示，但服务端截止时间不得改变。
- [ ] 截止后有报价的球员为 `PENDING_REVIEW`；无人报价的球员为 `NO_BID`。
- [ ] 第一位结束后，群内先出现本轮结果，再自动出现第二位开拍消息；第二位已为 `ACTIVE` 且获得新的 30 秒截止时间。
- [ ] 无人出价的球员自动记为 `NO_BID` 并进入下一位；最后一位结束后批次自动变为 `COMPLETED`。
- [ ] 后台能查看所有有效/无效报价、微信消息 ID、发送时间、球队和判定结果。
- [ ] 后台对成交结果验证“确认计算结果”“调整球队/价格（必填原因）”“作废（必填原因）”；对流拍结果只显示“确认流拍”和“作废”。
- [ ] 在后一位拍卖进行时审核前一位，当前拍卖、截止时间和最高价均不受影响。
- [ ] 审核完成后，球队资金、财务流水、阵容交易和球员归属都没有自动变化。

## 5. 恢复演练

1. 新建测试批次并开始第一位球员，完成一次有效报价。
2. 在倒计时内停止 Bridge 或让心跳超时。后台必须显示 `RECOVERY_REQUIRED`，当前球员保守暂停。
3. 在故障检测后发送数字。恢复上传后该报价必须记录为 `RECOVERY_REQUIRED`，不能成为最高价。
4. 对同一个微信消息 ID 重复上传，API 返回 `DUPLICATE`，不得新增第二条报价或第二条回复。
5. 先人工核对微信群最后可见消息和后台入站水位，再由有权限管理员恢复。
6. 恢复后必须重新给完整 30 秒，不沿用不确定的旧截止时间。
7. 再次报价并结束球员，核对待审核结果和出价时间线。

## 6. 数据库证据

验收时保存以下只读查询的计数或导出（不要修改生产数据）：

- `player_auction_batches`：批次状态、当前拍品、恢复原因和版本；
- `player_auction_lots`：顺序、单独价格、截止时间、epoch 和人工审核状态；
- `player_auction_bids`：每个纯数字消息的判定、微信顺序键和服务端接收时间；
- `player_auction_reviews`：计算结果与人工结果分列保存；
- `wechat_inbound_messages` / `wechat_outbox_messages`：入站去重、发送任务和回读确认；
- `finance_ledger_entries`、`roster_transactions`、`league_player_ownerships`：审核前后应无拍卖引起的新增或变更。

## 7. 停用与回滚

- 紧急停止时，先在后台停用设备或打开发送熔断，再结束 Windows 计划任务，并把 `send_enabled` 改回 `false`。
- 不确定消息一律保留为 `AMBIGUOUS`，先人工核对微信群，禁止直接重发。
- 活动拍卖因心跳、微信登录、锁屏或发送熔断进入恢复保护时，不要直接改数据库状态。
- 需要终止业务时，由管理员在后台或群内取消批次并记录原因；取消不可恢复。
- 令牌泄露时立即轮换设备令牌；微信升级、群改名或机器人账号更换后，保持发送关闭并重做完整验收。更换机器人账号需要重新绑定身份。

验收记录必须明确“仓库自动化通过”和“目标 Windows 电脑真实测试通过”是两个独立门禁。只有两者都通过，才可为授权联赛启用真实发送。
