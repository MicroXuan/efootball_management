# 球员库每日对账上线与使用

## 功能边界

每天按后台设置的时区和时间开始两遍官网卡片编号扫描。两遍完整、页数/总数和编号集合一致才生成差异。新增与摘要变化的卡取详情；原有卡的资料和图片每天分批复核。官网缺失的卡先单独查详情：明确失效，或连续两个相邻业务日期的可信完整扫描都缺失且详情也无法证明仍在售，才进入“已确认下架”。网络错误、漏页、单次缺失、仍能读到正常详情的卡不会自动下架。

扫描只生成报告。管理员检查报告后点击“一键发布有效变更”，系统分批发布新增、更新和已确认下架；失败和待确认项跳过。下架写入 `INACTIVE` 版本，保留原卡 ID、历史版本及关联记录。管理员未发布前，小程序仍显示上一次已发布的目录。

发布按批次提交，发布过程中小程序可能短暂看到部分批次已经生效的中间状态。当前版本在**全部有效批次处理完后**核对公开卡片编号集合，并在报告里标记完全或部分生效；它不提供单一瞬间的全库原子切换。

## 部署顺序

1. 确认目标环境的数据库主机和库名，备份数据库；在**目标环境**执行 `pnpm db:status`。不要仅凭本机状态判断生产已迁移。
2. 目标环境依次应用这三项迁移：`20261023120000_player_catalog_daily_reconciliation`、`20261023121000_player_catalog_reconciliation_cursor`、`20261023122000_player_catalog_reconciliation_lookup_indexes`。使用项目的受控 `pnpm db:migrate` 流程，不运行 `migrate dev` 或 seed。
3. 重新部署 API 和管理后台。此功能未修改小程序代码；小程序通过现有公开球员库接口读取发布后的版本。
4. 初始保持每日定时开关关闭。在管理后台“每日球员库对账”点击“立即人工对账”，等待两遍扫描与详情复核结束。检查可信状态、官网总数、当前公开数、失败和待确认项。
5. 管理员确认差异后点击“一键发布有效变更”，等待页面显示剩余批次为 0。复查公开球员库：新增可见、已确认下架不可见、旧卡重新出现后沿用原卡 ID。若有失败或待确认项，报告应保持“部分生效”，处理后重新扫描或重试发布。
6. 只有首轮可信对账、有效变更全部发布，且官网卡片总数与公开卡片数相符时，才能在后台设定 IANA 时区（例如 `Asia/Shanghai`）和每日时间并启用定时任务。

## 首轮耗时和日常检查

若现有库远少于官网约 5 万卡，首轮会抓取每张新增卡详情。默认每秒 1 次请求，仅 5 万次详情请求的理论下限就约 14 小时；官网限流和重试会增加耗时。之后每天两遍列表约 1,000 页，再加新增、变更和最多 500 张旧卡资料复核。实际耗时要在目标环境观察，不能使用本机数据库扫描基准估算官网耗时。

每天查看最新任务是否“扫描可信”，对比官网总数与公开数，审查“待确认下架”“同步失败”和“已确认下架”。大批量缺失达到异常阈值时会暂停下架。两遍偏移分页仍无法提供官网的原子快照，发布后也不能承诺实时绝对一致。

扫描暂存每天约增加 10 万条记录（按 5 万卡计算）。长期保留需监控磁盘；归档或清理必须按已结束的**精确任务 ID**预览、备份并在事务内执行，同时保留差异报告和审计。参见 [本机基准](../performance/2026-10-23-pesdata-reconciliation-50k.md)。

## 本次验证范围

只在本机隔离的 `efootball_catalog_verify` 库应用迁移并运行测试与 5 万卡合成基准；未连接或改动体验/生产数据库，未部署任何项目。目标环境的接口结果、前端解析、官网实际扫描和正式小程序展示仍需按上面的顺序验收。
